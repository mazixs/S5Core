# Реализация плана производительности S5Core

План: [2026-09-21](../performance-plan-2026-09-21.md). Реализация и измерения: 2026-09-21/22, Go 1.26.6. Основной стенд: Linux amd64, i7-11700K, GOMAXPROCS=16 у прокси. Дополнительно проверен настоящий ARMv8-роутер; его результаты выделены отдельно.

## Исходное состояние и границы

Baseline - рабочее дерево поверх `c0f137a9f79b748dd5bb8f24a0c1d7559cb4d890`, с ранее внесенными исправлениями H01-H05/R01. Они сохранены. [Статус Git до работы](../benchmarks/performance-implementation-2026-09-21/git-status-before.txt) и [хеши файлов](../benchmarks/performance-implementation-2026-09-21/baseline-hashes.json) описывают это дерево точнее SHA коммита.

Снимок и сырые результаты находятся в `/tmp/s5core-implementation-20260921/`. В baseline для измерения отдельных процессов добавлен только такой же диагностический запуск профилей, как в candidate. Без `S5_PROFILE_DIR` он не включает профилирование. Криптография, padding, MTU 1400 и WS shaping 256-4096 одинаковы. Пароли тестовые, только в локальном стенде. Замеры выполнялись до коммита и push. Публикация кода и этих материалов в Git не означает развертывание или canary: рабочие службы не обновлялись.

## Изменения

| Пункт | Реализация и решение |
| --- | --- |
| PERF-00 | Opt-in стенд в `cmd/httpsprobe/performance_linux_test.go`: отдельные бинарники, настоящий TLS origin, HTTP/1.1/2, new/reuse, размер и SHA-256, upload/stream/mixed, CPU/RSS прокси и генератора, SDK, scrape и flush. Скрипты `performance-ab.py`, `performance-summary.py`, `performance-netem.sh`. Профили пишутся только диагностической сборкой в локальные файлы; публичного pprof нет. Выполнены desktop, ARM loopback и изолированный netem; рабочий WAN и canary остаются отдельным этапом. |
| PERF-01 | `obfs.conn.Read` объединяет только целые кадры, уже полученные в `readBuf`, и остаток payload. После первого payload новое сетевое чтение не выполняется. Сохранены FIN/control/keepalive/replay/AEAD и observer. Данные, пришедшие вместе с ошибкой транспорта, сначала доставляются; terminal error становится постоянной, timeout можно повторить. После завершенного большого Read/Write вызывается `runtime.Gosched()` вне mutex. Это оказалось необходимым для mixed latency; ниже отдельное обоснование. |
| PERF-02 | `WriteBufferSize: DefaultMaxFrame` в WS upgrader. Не зависит от произвольного пользовательского shaping max. На типичном batch 22752 B: 8 -> 6 allocs/op. Рост удерживаемого heap двух концов WS около 4%. Дополнительно проверенный bounded pool не принят: возвращает аллокации в горячий путь. |
| PERF-03A | Явные `PROXY_AUTH_MODE=member-only/password-fallback`; `auto` сохраняет старое поведение. Отказ member key не превращается в повторную попытку с паролем. |
| PERF-03B | `ws.NewDialer` хранит два ограниченных кеша по 16 сессий для неизменной конфигурации, отдельно crypto/tls и uTLS. Endpoint/SNI/CA/pins/fingerprint меняются созданием нового Dialer. Клиент создает его один раз; `WS_TLS_SESSION_CACHE=false` дает A/B и откат. Browser presets без PSK-extension не модифицируются и сохраняют full handshake. |
| PERF-04 | Автоматический кеш без DNS TTL не добавлен. Есть сравнение числового IP и localhost, а также opt-in измерение настоящего `DNSResolver.ResolveAll`. Нужен DNS рабочего маршрута для решения о TTL-aware кеше. Старые resolver/context/Rules/Rewriter/fallback сохраняют контракт. |
| PERF-05 | Доменные правила нормализуются и компилируются при запуске: exact map и wildcard suffix по границам labels. Найденная стоимость 10000 правил устранена. Профили не показали основания переводить quota/billing/telemetry в отложенный учет или менять deadline semantics. Добавлена проверенная отдача управления между завершенными большими чтениями/записями. |
| PERF-06 | Отдельные профили клиента и сервера поддерживаются; production `default.pgo` не добавляется без репрезентативного профиля и независимой приемки. Результат лабораторного PGO и статус целевой приемки приведены ниже. |

Правила wildcard, базового домена, IDN, trailing dot и ошибочных имен сохранены. Бенчмарк поиска с 0/10/1000/10000 правил: [сравнение](../benchmarks/performance-implementation-2026-09-21/routes-benchstat.txt). Для 10000 правил lookup уменьшился примерно с 728 мкс до 77 нс. Создание maps оплачивается один раз на конфигурацию, а не на CONNECT. Нулевой список в реальном клиенте и раньше обходил поиск, поэтому выигрыш microbenchmark для 0 правил не объявляется ускорением обычного CONNECT.

Отдельный A/B на реальных процессах с тем же конечным кодом, меняющий только matcher на исходный алгоритм, подтвердил эффект на CONNECT. При 10000 правилах и совпадении последнего правила p50 полного HTTPS уменьшился 1,713 -> 1,059 мс для obfs и 2,361 -> 1,689 мс для WSS. По 1000 наблюдений на вариант, 2 независимых прогона; [сводка](../benchmarks/performance-implementation-2026-09-21/routes-process-abba.md). Это дорогой случай линейного списка, не средняя стоимость любого набора правил. В стенде применены короткие синтетические имена, чтобы 10000 правил помещались в лимит Linux на одну строку окружения.

Без доменных правил сравнение IP и localhost дало разницу setup около 22 мкс для obfs и 21 мкс для WSS. Системный resolver localhost: cold 86 мкс, p50 5 мкс, p95 10 мкс, p99 23 мкс, 100 вызовов. Условия плана для нового DNS-кеша здесь не выполняются. Эти результаты не характеризуют публичный DNS.

## Почему потребовалась дополнительная проверка mixed

Первый вариант объединения дал сильный прирост bulk, но не прошел tail latency при одновременной непрерывной загрузке. На 10200 малых reused-запросах p99 вырос с долей миллисекунды до нескольких миллисекунд. Повтор с уменьшенными аллокациями генератора подтвердил проблему. В профильном прогоне scheduler delay клиента составил около 7,7 мс за весь прогон, server mutex contention около 2,4 мс; это не подтверждает гипотезу о глобальном Store lock как причине наблюдавшихся задержек.

Проверены отдельные варианты: передача управления только после Read, ограничение Read до 4 КиБ и до 2 КиБ. Ограничение 2 КиБ сохранило latency, но потеряло нужный прирост throughput. Эти варианты в рабочий код не перенесены. Принята отдача управления после завершенного большого Read **и** Write. Mutex сначала освобождается, нет ожидания таймера/сети и накопления новых данных, малые операции идут прежним путем. Большой постоянно готовый relay уступает очередь другим горутинам. Результат проверяется заново отдельной полной A/B-серией, а не прибавляется к процентам первого прототипа.

Отдельно исследованы редкие полные ответы WSS около 223-230 мс. Захват TCP показал zero-window и затем window update, после которого отправка не продолжалась около 205 мс. Пример: update `2617094`, окно `52224`, пауза `1790024450.047355 -> 1790024450.252553`. Это наблюдение транспортного ожидания на loopback с большим MSS, а не задержка DNS/TLS: первые HTTP-байты приходили примерно за 2 мс. В изолированной серии 600 ответов с дополнительным сетевым pacing этот выброс не повторился. Отсутствие такого выброса в короткой серии не считается доказательством для WAN. Глобальные TCP socket buffers не менялись.

## Память WS и TLS

[WS benchmark](../benchmarks/performance-implementation-2026-09-21/ws-buffer-benchstat.txt): для 22752 B снижение allocations 8 -> 6; значимого ускорения полного HTTPS только от PERF-02 не заявляется. Совместный эффект измеряется по конечному коду.

Два прогона на 1000 и 10000 открытых WS-соединений: heap на пару client/server около 19188 -> 19956 байт при 10000, примерно +768 байт, или +4%. RSS всего стенда не вырос устойчиво. Это обычные WS adapters без TLS/obfs и без kernel socket memory; такие числа нельзя выдавать за бюджет 10000 полных WSS-туннелей на роутере. При большой настройке WS_MAX_FRAME постоянный буфер остается 4096 B.

Создание новой пары WS стоит столько же по времени: 97,33 -> 97,28 мкс (`p=1.000`, n=6), но выделяет 30,55 -> 35,35 КиБ, **+4,80 КиБ / +15,7%**, 135 -> 136 allocs. [Сравнение](../benchmarks/performance-implementation-2026-09-21/ws-create-benchstat.txt). Это временные allocations при обычном WS upgrade, отдельно от TLS и постоянного heap. Эту цену нельзя скрывать за уменьшением allocations на длительной передаче.

Из-за этой цены отдельно проверен ограниченный pool, до 128 buffers на upgrader. Он уменьшил heap на 10000 idle pairs до 15092 B/pair и вернул upgrade к 30,55 КиБ. Однако типичная запись 22752 B выросла с 6 до **13 allocs/op**, с 55 до 221 B/op; значимого ускорения не появилось. [Проверка pool](../benchmarks/performance-implementation-2026-09-21/ws-pool-benchstat.txt). Прототип отвергнут, в основной код не внесен. Принятый вариант уменьшает расходы активной передачи при ограниченной дополнительной памяти; бюджет полного WSS на целевом сервере остается отдельной проверкой.

TLS benchmark проверяет `DidResume`, а также полную доставку эха и ticket: примерно 707 -> 608 мкс, около -14%. Resumed handshake в этом Go увеличивает временные allocations примерно на 17 КиБ (+9% B/op). Это отдельная стоимость churn; ограниченный кеш принадлежит конфигурации, а не каждому соединению. Pin проверяется и на resumed session, в том числе отдельным тестом uTLS. Новый Dialer с неверным CA/SNI/pin не наследует доверие старого.

**CPU имеет отдельную цену.** Для download obfs суммарные CPU-seconds/GiB клиента и сервера снизились с 3,94 до 2,49 (new) и с 4,20 до 2,53 (reuse), примерно на 37-40%. На устройстве с жестким лимитом CPU этот компромисс требует отдельной приемки.

Пиковый RSS полных процессов в той же серии: obfs client 16,31 -> 16,38 МиБ, server 27,27 -> 26,06 МиБ; WSS client 18,35 -> 18,52 МиБ, server 28,68 -> 27,82 МиБ. В этом наборе нагрузки нет роста выше 5%. Это high-water mark `/proc/PID/status`, включая предыдущие сценарии процесса; он не заменяет бюджет тысяч полных idle WSS-соединений.

Локальная функциональная матрица прошла без ошибочных HTTP-ответов или несовпадений размера/SHA-256:

- 4/16/64 одновременных запроса: по 1856 ответов на уровень, direct/plain/obfs/WSS, HTTP/1.1 и HTTP/2, new/reuse, download/upload. HTTP/2 может использовать один туннель для нескольких запросов; это не доказательство 64 отдельных H2-туннелей.
- Старый клиент с новым сервером и наоборот: по 928 ответов, obfs/WSS. Оба направления поддерживают независимый откат.
- Member-only, member с password-fallback и password: по 928 ответов; RequireAuth включен, периодический учет и scrape активны. Cold/hot Argon2id и revoke/expiry/quota также покрыты существующими интеграционными тестами полного race-прогона.
- Пять uTLS-профилей chrome/firefox/safari/ios/go: по 104 ответа. Отдельные TLS-тесты проверяют DidResume, неверные CA/SNI/pins и pin на resumed uTLS.
- Четыре непрерывных передачи по 35 секунд: download/upload-stream через obfs/WSS, HTTP/2. Общее время 141 с; прежний idle timeout не обрывает активную передачу.

### Настоящий ARM и влияние генератора

Использован доступный ARMv8-роутер: Linux 4.9-ndm-5 aarch64, 3 CPU, инструкции AES/PMULL, около 1 ГиБ RAM. Клиент, сервер и HTTPS origin/генератор запущены отдельными временными процессами на loopback. Прокси ограничены `GOMAXPROCS=1`, member-auth, настоящий учет и scrape включены. Хеши загруженных бинарей проверены. Рабочие службы и их конфигурация не менялись; временные процессы завершены, каталоги удалены. Это проверка исполнения на целевой архитектуре, а не WAN.

Первая короткая серия с **одним Go P также у генератора** прошла HTTP/1.1/2, new/reuse, download/upload/mixed через obfs/WSS, но показала ухудшение obfs mixed p99: например, HTTP/1.1 new 178,609 -> 190,756 мс. Этот результат не принят как успешная tail-проверка. [Исходная серия](../benchmarks/performance-implementation-2026-09-21/arm-abba.md).

Повтор с теми же бинарями прокси и тремя Go P у origin/генератора устранил это ухудшение. Генератор использовал около 0,71 -> 0,96 CPU в mixed, поэтому его искусственное ограничение меняло измеряемую очередь при возросшей скорости bulk. В повторе, 2 независимых прогона на вариант, 1000 малых и 20 больших наблюдений на сценарий:

### Задержки, потери и авторизация

В отдельных user/network namespaces проверены крайние сочетания: RTT 20 мс / loss 0% / 1000 Мбит/с, 50 мс / 0,1% / 100 Мбит/с и 100 мс / 1% / 10 Мбит/с. MTU lo=1500; обрабатываются оба направления туннеля. По 20 малых ответов и одному измеренному ответу 8 МиБ после трех прогревов, obfs/WSS, baseline/candidate. Все тела доставлены полностью и прошли SHA-256. Последняя пара тестов заняла 352 и 338 с: восстановление TCP после потерь существенно ограничивает скорость. [Исходные времена](../benchmarks/performance-implementation-2026-09-21/netem-smoke.json); `netem-*.log` сохраняют qdisc и TCP counters. Это smoke, не статистическая приемка WAN.

В первом WSS-замере при 50 мс / 0,1% встречалось 1,44 -> 3,99 с. Поэтому выполнены еще **6 чередующихся прогонов на вариант**, по 5 измеренных передач и 3 прогрева. Отставание не подтвердилось: pooled-p50 5,03 -> 3,14 с, однако широкий разброс есть у обеих версий, и CI хвоста пересекает ноль. [Повторная серия](../benchmarks/performance-implementation-2026-09-21/netem-50-repeat.md). Ни исходный выброс не объявляется регрессией, ни новая медиана - гарантированным WAN-ускорением. Полный release-порог 3% требует более представительного сетевого стенда.

Member-only проверен отдельными реальными процессами при loss=0, RequireAuth=true и валидном ключе. Медиана сохраненного setup-времени относительно member с password-fallback:

| RTT | obfs | WSS |
| --- | ---: | ---: |
| 20 мс | 20,159 мс | 20,206 мс |
| 50 мс | 50,098 мс | 50,054 мс |
| 100 мс | 100,128 мс | 100,198 мс |

[Результаты](../benchmarks/performance-implementation-2026-09-21/member-rtt.json). Это один обмен на новом туннеле; у прежней конфигурации без PROXY_USER greeting уже был pipelined и такого дополнительного выигрыша нет.

UDP-over-TCP проверен штатным `udpprobe` с отдельным UDP echo, 400 датаграмм через каждый транспорт и вариант при RTT 50 мс, loss 0/1%. Во всех восьми сериях доставлены 400/400. При loss=0 p99 около 50,5 мс; при 1% около 121 мс у обеих версий. [Все результаты](../benchmarks/performance-implementation-2026-09-21/udp-results.txt). Потеря TCP-сегмента продолжает задерживать следующие датаграммы; оптимизация чтения этого свойства не устраняет.

### PGO: измерено, в релиз не включено

Профили CPU собраны отдельно в реальных процессах конечной версии: obfs/WSS, member auth, small/bulk/upload/mixed, new/reuse. Профили obfs и WSS объединены суммой CPU samples для каждого бинаря отдельно. Это веса лабораторной нагрузки; частоты рабочего маршрута неизвестны. Профили origin/генератора не использованы. [Профиль клиента](../benchmarks/performance-implementation-2026-09-21/pgo-client-top.txt), [сервера](../benchmarks/performance-implementation-2026-09-21/pgo-server-top.txt).

Независимая A/B/B/A-приемка PGO: 6 прогонов на вариант, 10200 малых наблюдений на сценарий, 150 больших. Обычные release-сборки без profiling сопоставлены с такими же PGO-сборками. [Сводка](../benchmarks/performance-implementation-2026-09-21/pgo-abba.md), [benchstat по независимым прогонам](../benchmarks/performance-implementation-2026-09-21/pgo-benchstat.txt).

Ускорение pooled-p50 bulk от -0,1% до +2,7%. Значимого изменения времени по медианам отдельных прогонов нет. CPU на reused WSS upload снизился на 3,12% (`p=0.024`), но на WSS download/reuse агрегированный CPU вырос примерно на 5%; остальные сравнения CPU незначимы. Один удачный сценарий без известного веса в рабочей нагрузке не оправдывает включение PGO для всех установок. Latency-порог не нарушен. Решение: **оставить PGO выключенным**, лабораторные профили не добавлять как `default.pgo`.

Размер клиента 12077413 -> 12202202 B (+1,03%), сервера 20086571 -> 20200604 B (+0,57%). Время сборки 0,28 -> 5,76 с и 0,43 -> 6,98 с. Это замер с уже прогретым кешем обычной сборки и первым использованием нового профиля, а не сравнение холодных build. [Исходные значения](../benchmarks/performance-implementation-2026-09-21/pgo-builds.json).

## Выпуск

Кодовые изменения PERF-01/02/03/05 реализованы, PERF-04/06 проверены и оставлены без спекулятивного DNS-кеша или PGO. Настоящий ARM проверен в loopback, UDP при loss проверен в netem; рабочий WAN/VPS и canary пока не выполнены. Доступность узла по SSH сама по себе не определяет выбранный рабочий маршрут и окно обновления.

Сводка изменений для пользователей включена в [README](../../README.md#https-implementation-results-22092026) и [Unreleased changelog](../../CHANGELOG.md#unreleased). Исправления H01-H05/R01, оптимизации, тесты и текстовые доказательства публикуются вместе. Предыдущие аудиты и отчеты сохраняют состояние на дату их составления; их формулировки о незакоммиченных изменениях описывают историю проверки, а не текущий статус публикации. Фактический commit/push определяется историей Git; номер новой версии и развертывание этим не объявляются.

Выпускные условия: независимый WAN baseline и candidate с контролем wire/useful bytes, retransmits, CPU системы/softirq и DNS; не менее 10000 малых наблюдений на вариант в целевых WSS/mixed-сценариях; пик нагрузки и бюджет полного набора туннелей; затем ограниченный canary обеих сторон с сохраненными бинарями/конфигурацией и независимым откатом. Повторные flush/scrape, quota/revoke и целостность должны проверяться и на этом маршруте. До его приемки стендовые результаты не считаются выпуском.

Команды повторения и ограничения стенда: [руководство](../performance-validation.md). Новые бинарники и профили не добавлены в Git.
