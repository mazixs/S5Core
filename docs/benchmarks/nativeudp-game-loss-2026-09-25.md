больше 0,18 мс при лимите 1; замирания не превышают прямой путь больше чем
на 10%. У `0x83` потери скрыты повторной передачей TCP, но задержка на
потерях выросла, а замираний стало больше.

Отчет пайплайна пометил 64 проблемы при 56 статусах `ok`: 48 предупреждений
о запуске тестового сервера без аутентификации и 16 сообщений `idle tcp echo:

используют стандартный UDP ASSOCIATE `0x03` в обоих вариантах и служат
контролем, а не проверкой native UDP. У obfs и wss ошибок игрового сценария
нет.

Полный прогон собран до добавления счетчиков UDP и сценария принудительного
отказа UDP в тот же день. Эти добавления не меняют формат или выбор пути, но
после них проведены отдельные короткие сценарии отказа UDP на 64 и 128 Гц.
Финальный часовой WAN-прогон проводится отдельно.

## Принудительный отказ UDP

Две дополнительные минутные ячейки после добавления счетчиков и фильтра
`tc` ([JSON](nativeudp-blackout-2026-09-25.json), локальный netns, RTT 50 мс):

- UDP заблокирован с начала на 55 с: 0% потерь, 0 замираний, 0 обрывов.
  Клиент проверил native UDP только после снятия блока; весь основной поток
  до этого шел по `0x83`.
- UDP исчез на десятой секунде на 12 с: клиент зафиксировал тайм-аут native
  UDP и перешел на `0x83` в той же ассоциации. Один перерыв между ответами
  1,063 с, 1,74% потерянных тиков, 0 обрывов. После восстановления пути
  клиент снова проверил native UDP. Порог замирания 1,5 с выполнен.

Три предупреждения в отчете: два ожидаемых запуска стендового сервера без
аутентификации и одно сообщение клиента о переходе на `0x83`.

Повтор на итоговой сборке после изменений окна и проб (тот же [JSON](nativeudp-blackout-2026-09-25.json)):
обе ячейки `ok`, 0 обрывов. При блоке с начала потерь и замираний нет;
при блоке посреди сессии одно замирание 1,062 с и восстановление native UDP
после снятия фильтра. Три сообщения отчета имеют тот же ожидаемый состав.

## MIPS-совместимость

Клиент под `mipsle` и `mips` с `GOMIPS=softfloat` проверен под QEMU против
сервера amd64 с включенным native UDP
([JSON](nativeudp-mips-2026-09-25.json)). Каждая пара передала 128 игровых
тиков при 64 Гц без ошибок. В логах обоих клиентов подтверждены проверка
UDP-пути и отправка игровых датаграмм через него. Это проверка совместимости
формата между архитектурами; скорость и нагрузка на реальном MIPS не
измерялись.

## Отказ UDP при 128 Гц

Отдельная двухминутная сессия, 200 байт в каждом направлении, RTT 50 мс,
UDP заблокирован с 10-й по 22-ю секунду; TCP оставался доступным
([три прогона](nativeudp-highrate-blackout-2026-09-25.json)). Начальное окно
на 128 тегов оставляло игру на `0x83` без обрыва, но native UDP не
восстановился за оставшуюся минуту. Окно 512 вернуло native UDP через 25,2 с
после разблокирования; немедленная повторная проба при переходе на `0x83`
сократила ожидание до 4,1 с. На финальном локальном прогоне 0 обрывов,
1 замирание длиной 1,055 с, p99 50,39 мс, тихий TCP-канал не падал.
Это проверка 128 Гц на локальном стенде, а не на WAN или в реальной игре.

## Повтор после правок ревью 3

После правок ревью 3 изменилось вот что. Путь ответов сервер выбирает по
словам клиента, а не по пути последней датаграммы. Счетчики сторон
ресинхронизируются кадром нулевой длины. Ответы на пробы идут не из читателя
общей точки. Те же отказы повторены на той же машине и в том же стенде
([64 Гц](nativeudp-blackout-2026-09-25.json), ключ `review3_check`;
[128 Гц](nativeudp-highrate-blackout-2026-09-25.json), последние три записи):

| Ячейка | Потери | p99 | Замирания / самый длинный перерыв | Обрывы |
|---|---:|---:|---:|---:|
| 64 Гц, UDP закрыт с начала на 55 с | 0% | 50,52 мс | 0 / 18,8 мс | 0 |
| 64 Гц, UDP пропал на 10-й секунде на 12 с | 1,74% | 51,23 мс | 1 / 1,063 с | 0 |
| 128 Гц, тот же отказ, три прогона | 0,87% | 53,21 / 50,48 / 50,49 мс | 1 / 1,054-1,055 с | 0 |

Замирание при отказе посреди сессии осталось прежним (1,062-1,063 с на 64 Гц,
1,054-1,055 с на 128 Гц). Native возвращается сам через 4,4-4,7 с после
снятия фильтра. Этот срок задает расписание повторов (1-2-4-8 с), а не
правки. Отсчет приблизительный: от начала замера плюс 22 с до строки клиента
"path restored". Первая ячейка "закрыт с начала" прошла на машине с
посторонней нагрузкой 4,35 ядра (p99 55,91 мс, стенд пометил ее шумной), в
таблице - ее повтор на спокойной машине. Первый прогон на 128 Гц дал p99
53,21 мс сразу после плана на 64 Гц, два повтора - 50,48 и 50,49 мс, как до
правок (50,39-50,64 мс). Счетчики отказов общей точки (tag, replay, auth,
read_error) во всех ячейках нулевые.

Эти ячейки не проходят через ресинхронизацию: за секунду до признания
потери клиент на 128 Гц успевает отправить около 128 датаграмм, окно
приемника - 512. Выход за окно проверяют тесты: сквозной
`TestTheCountersResyncWhenThePathHeals` (1200 датаграмм в оборванный путь, без
ресинхронизации native не возвращается за 15 с) и серверный
`TestTheCountersResyncAfterMoreLostThanTheWindow`.

## Час на WAN и ARM64

Первый часовой прогон на изолированном серверном стенде и ARM64-маршрутизаторе
([JSON](nativeudp-wan-hour-2026-09-25.json)) был собран до увеличения окна и
ускорения повторных проб. При 64 Гц: 230 391 тик, 0 обрывов, 89 успешных
проверок тихого TCP-канала, native UDP принял 230 630 пакетов без отказов
аутентификации. Потери 0,004% против 0,059% у прямого контроля; замираний
8 против 8. p99 56,405 мс против 54,052 мс, то есть +2,353 мс при пороге
+1 мс. В каждой из 60 минут медиана native-пути была выше прямого контроля
на 1,488-1,838 мс. Час подтверждает стабильность, но **не выполняет полевой
порог задержки У-5**.

Повтор полного часа на коммите `42d0f48` завершился без проблем стенда;
тестовые процессы на обеих машинах очищены. У всех 60 минут есть игровой и
прямой поток:

| Сборка | Потери native / прямо | p99 native / прямо | Добавка p99 | Замирания native / прямо | Обрывы |
|---|---:|---:|---:|---:|---:|
| До правки окна и проб | 0,004% / 0,059% | 56,405 / 54,052 мс | +2,353 мс | 8 / 8 | 0 |
| `42d0f48` | 0,006% / 0,054% | 55,489 / 54,404 мс | +1,085 мс | 10 / 10 | 0 |

На итоговой сборке 230 386 игровых тиков, 89 успешных проверок тихого
TCP-канала, 230 632 принятых native UDP пакета, 0 отказов по тегу,
аутентификации и повтору. Медианная добавка за минуту лежит в пределах
0,177-0,302 мс; добавка p99 по минутам - 0,282-1,820 мс.
Три порога У-5 из четырех пройдены, но p99 выше лимита +1 мс на 0,085 мс.
Это пограничное превышение, а не прохождение порога. Два часа были в разное
время и на разных сборках, поэтому разницу между ними нельзя приписать
только изменениям кода.

Отдельный [бенчмарк кодека на том же ARM64](nativeudp-arm-codec-2026-09-25.json)
дал 28,6 мкс на шифрование и прием 200-байтной датаграммы, 0 аллокаций.
Это стоимость кодека без сети и без полного пути приложения; она не
объясняет сама по себе добавку p99 ни первого, ни итогового часа.
"0 аллокаций" относилось только к кодеку: путь через хаб аллоцировал буфер
на каждую отправку и каждый прием.

После ревью окно приема ведется по счетчику, а буферы хаба берутся из пула.
Парный [прогон на том же роутере](nativeudp-arm-codec-window-2026-09-25.json):
кодек 5,55 мкс против 28,6 мкс, в 5,2 раза быстрее; на x86 (16 потоков) -
0,88 мкс против 4,1 мкс. Путь датаграммы через хаб туда и обратно не
аллоцирует ничего (`TestADatagramThroughTheHubCostsNoAllocations`). Часовые
прогоны выше сняты до этой правки.

Локальная проверка [памяти таблицы сессий](nativeudp-session-memory-2026-09-25.json)
дала около 44 КБ кучи на ассоциацию при 1000 зарегистрированных сессиях и
окне 512. Это оценка процесса amd64 после сборки мусора, а не замер емкости
боевого узла; перед большим числом одновременных игроков нужен отдельный
нагрузочный тест. После ограничения очистки тегами закрываемой ассоциации
удаление 1000 сессий заняло 39,4 мс на локальном стенде.

через туннель добавляется плечо от сервера S5Core до него. На это плечо
туннель не влияет, его определяет размещение узла относительно игровых
серверов.

### Замирания на прямом пути

Замирание - промежуток между соседними ответами длиннее 100 мс (`freezes` в
[`scripts/matrix/README.md`](../../scripts/matrix/README.md)). При 64 Гц ответ
приходит раз в 15,6 мс, то есть замирание - около шести тиков без ответа
подряд.

Прямой поток на WAN дает 8-10 таких событий в час, и все они короткие: самая
длинная пауза итогового часа - 108,5 мс, на 8,5 мс выше порога. Генератор
стоит на маршрутизаторе, беспроводного участка в пути нет, а на локальном
стенде без потерь замираний 0. Значит, паузы дает сам маршрут до сервера:
несколько пакетов подряд теряются или задерживаются. Native повторяет эти
паузы и не добавляет своих. Заметит ли их игрок, зависит от буфера
интерполяции конкретной игры; на реальных играх это не проверялось.

Метрики рядом: рывок - ответ медленнее медианы больше чем на 50 мс при
живом потоке; обрыв - 3 с без ответа, после чего стенд открывает ассоциацию
заново. Обрывов не было ни на одном пути этого отчета.

### Почему `0x83` растет ступенями

В первой таблице отчета p99 `0x83` на obfs растет с 50,2 мс без потерь до
101,8-134,3 мс на 0,5-2% и до 219,0 мс на 5%, а у прямого пути и native
остается на 50,1-50,2 мс. Туннелю не нужно знать уровень потерь: TCP узнает
о каждой потере сам, по подтверждениям, и пересылает сегмент. Доставка по
порядку держит за потерянным сегментом все тики, отправленные после него,
поэтому одна потеря задерживает несколько тиков. Уже при 0,5% на проход
больше процента тиков ждет пересылки, и p99 оказывается среди них. Механизм и
замер без настройки сокета - [`game-loss.md`](game-loss.md).

Рост идет ступенями, а не по прямой. На 0,5-2% добавка p99 к RTT - 52-84 мс,
порядка одной пересылки. На 5% - 169 мс, больше двух. Стенд шел с
`UDP_TUNNEL_TCP_TUNING` по умолчанию, на Linux 7.0 это нижняя граница таймера
пересылки 20 мс вместо 200 мс ([`game-tuning.md`](game-tuning.md)). Поэтому
ступень на 5% объясняется не минимальным таймером Linux, а, вероятно,
повторными потерями: пересылка теряется снова, и таймер удваивается. По
отдельным тикам это не разбиралось.

### Границы native в игровой сессии

- **По умолчанию выключен.** Без `UDP_PORT` у сервера и `UDP_NATIVE=true` у
  клиента UDP идет по `0x83`, как в 2.2.
- **Начало ассоциации идет по `0x83`.** Датаграммы переходят на native после
  ответа на первую пробу, то есть примерно через один RTT.
- **Пропажа UDP посреди сессии стоит около секунды.** Клиент перестает слать
  native, когда сервер молчит секунду, и тогда же говорит серверу по
  управляющему соединению отвечать по TCP; обратно на native ответы
  возвращает первая проба после восстановления пути. Блок UDP на 12 с дал одну паузу 1,06 с и
  1,74% потерянных тиков, после снятия блока native вернулся сам (раздел
  "Принудительный отказ UDP").
- **Потеря пути объявляется по пробам.** Три пробы подряд без ответа, первая
  отправлена не меньше секунды назад; дальше клиент повторяет серверу сигнал
  с каждой retry-пробой ([раздел 10.6 спецификации](../veil-spec.md)).
- **Крупные датаграммы идут по `0x83`.** Предел native - 1374 байта вместе с
  заголовком SOCKS5 UDP: `MaxWire` 1400 минус 8 байт тега, байты вида и
  длины добивки и 16 байт тега AEAD. Для цели IPv4 это 1364 байта данных
  игры.
- **Для наблюдателя это отдельный поток UDP на порт сервера, а не TLS.** В
  сети, которая режет незнакомый UDP, native не подтверждается, ассоциация
  остается на `0x83`, а клиент пишет одну Info-строку с адресом проб.
- **Больше 512 потерянных подряд пакетов одного направления** требуют новой
  ассоциации (раздел 10.6 спецификации).
