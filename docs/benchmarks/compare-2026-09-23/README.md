# raw, 2.1.0 и current: сравнение на одном стенде

Дата: 2026-09-23. Три варианта:

- `raw` - генератор ходит в источник сам, контроль без прокси;
- `v210` - тег `v2.1.0` (`44382b6`);
- `cur` - рабочее дерево 2.2 (незакоммиченные правки поверх `cd79abe`):
  уступка планировщику раз в 100 мкс, буфер записи WebSocket по
  `WS_MAX_FRAME`, пул буферов релея клиента, дозвон без горутины, строгий
  разбор ответа на `0x83`, удаление legacy и сырого пролога.

Вопрос серии: что current сделал лучше и хуже, чем 2.1, на каждом протоколе
приложения, и сколько каждый из них стоит против прямого пути. Разбор для
чтения - [отчет](../../reports/raw-v21-current-2026-09-23.html), здесь метод,
перепроверки и как повторить.

## Стенд

Тот же `bench/matrix`, что в [matrix-2026-09-22](../matrix-2026-09-22/README.md):
настоящие процессы `s5core` и `s5client`, источники HTTP/1.1, HTTPS (TLS 1.3),
HTTP/2, HTTP/3 поверх QUIC, TCP echo и UDP echo в процессе генератора. Отличия
этой серии:

- аутентификация member-only (`AUTH=member`): настоящий аккаунт в
  `USERS_FILE` с `tunnel_key`, `RequireAuth=true`, у клиента
  `OBFS_MEMBER_KEY` без `PROXY_USER`;
- бинари обоих вариантов собраны одинаково: `CGO_ENABLED=0 go build -trimpath
  -pgo=off`, `s5core-cur` побайтно совпадает со свежей сборкой дерева;
- `FLUSH=60s`, `WARMUP=1` (один прогрев на сценарий до замера);
- `OBFS_MTU=1400`, `OBFS_MAX_PADDING=256`, `WS_MIN_FRAME=256`,
  `WS_MAX_FRAME=4096`, keepalive 10-20 с.

Режимы:

- **loopback** - цена кода без сети, `taskset -c 0-5,8-13`, один набор
  процессов за раз, порядок вариантов чередуется между раундами.
  `GOMAXPROCS=4` у сервера и клиента (5 раундов) и `GOMAXPROCS=1`
  (5 раундов в suite8 и suite8b, затем 10 в suite11 и 12 в suite14);
- **netem** - RTT 40 мс, 200 Мбит/с, потери 0% и 0,5%, `-scale 0.3`. У
  туннеля формируется только участок клиент-сервер, у raw - весь путь. Тройки
  raw, 2.1 и current идут одновременно, каждая в своем netns на своих ядрах
  (`D`, `A`, `B`), ядра 2.1 и current меняются местами на четных раундах, а
  тройки obfs и wss идут параллельно на непересекающихся наборах.

## Правило вердикта

"Лучше" или "хуже" - только при разнице медиан не меньше 5% (для потерь -
0,5 п.п.) и одном знаке во всех парных раундах. При 3 раундах метрика без
эффекта получает такой вердикт примерно в 25% случаев, при 5 - в 6%, а метрик
в первой серии больше сотни. Поэтому каждый флаг "хуже" перепроверен отдельной
серией на 6-12 раундов, и для нее считается знаковый тест: в скольких парных
раундах current хуже и p двустороннего теста без ничьих.

Две оговорки к метрикам:

- **p99 под потерями 0,5%** при n около 600 - это вопрос, попал ли в верхний
  процент RTO (уровни 43, 93, 283 и 370 мс), а не свойство кода. Для этих
  сценариев добавлен `slow_pct`: доля выборок выше `p50 + SLOW_MS`
  (150 мс), то есть сколько запросов заплатили RTO;
- **сценарии под закачкой** (`*-under-bulk`) не фиксируют объем: закачка
  идет, пока идут малые запросы. Сырой CPU на прогон там сравнивать нельзя,
  только CPU на ГБ (`background_MBps` × длительность сценария из
  `matrix.log`, `cpu11.py`).

## Серии

| Скрипт | Что | Раунды |
|---|---|---|
| `suite8.sh`, `suite8c.sh` | loopback (4 и 1 ядро), netem без потерь и с 0,5%, аутентификация, soak | 5 / 5 / 2 / 3 / 1 |
| `suite8b.sh` | перезапуск ячеек, упавших до замера (порт занят на старте), и раунды 4-5 loopback с одним ядром | - |
| `suite9.sh` | A/B: буфер приема 4 МиБ на обоих UDP-сокетах `0x83` | 3 + 3 |
| `suite10.sh` | UDP-всплеск 40 Мбит/с на новой ассоциации; HTTP/3 под потерями 0,5% | 10; 6 |
| `suite11.sh` | loopback, одно ядро, малые запросы по открытому соединению | 10 |
| `suite12.sh` | второй проход soak в обратном порядке | 1 |
| `suite14.sh` | HTTP/3 под закачкой, wss, одно ядро: 2.1, current и `cury0` | 12 |
| `suite13.sh` | под потерями 0,5% со `slow_pct`; малые запросы под закачкой без потерь; захват участка туннеля | 6; 6; 1 |

`cury0` - дерево с `var yieldInterval time.Duration` (уступка после каждой
пачки, как в 2.1): `conn-cury0.patch.txt` - это вся разница с деревом,
собирается через `go build -overlay` с `overlay-cury0.json.txt` (`<repo>` -
корень репозитория). Если `cury0` ведет себя как 2.1, а current - нет, разницу
дает интервал уступки.

Сводки: `compare8.py` (полные таблицы), `compare9.py`-`compare14.py` (по
сериям), `cpu11.py` (CPU на ГБ), `loss13.py` (доля запросов с RTO суммарно
по раундам и биномиальный тест). Захват - `cap.sh`: `tcpdump -Z root` внутри
netns туннеля (без `-Z root` tcpdump в user namespace не может сменить uid и
падает), затем `pcap_timeline.py` строит медианный таймлайн соединения.

## Итоги

Все числа - в [отчете](../../reports/raw-v21-current-2026-09-23.html), здесь
только вердикты перепроверок.

- **Ошибок у current 0**: 2 259 748 запросов матрицы (тела сверяются
  побайтно) и четыре прогона soak. У 2.1 в soak 21 ошибка, почти все -
  UDP-всплески: ответы ассоциации уходили за датаграммой без заголовка.
- **Установка соединения** на RTT 40 мс у 2.1 и current совпадает до
  миллисекунды на всех протоколах и обоих транспортах. Цена кода на loopback
  у current ниже (CPU -15% у obfs и -8% у wss), отсюда полоса +8..+13% на
  HTTP/HTTPS и +33% на HTTP/3 через obfs.
- **Флаги "хуже" первой серии не подтвердились**: UDP-всплеск (разброс внутри
  версии больше разницы), HTTP/3 под потерями (current не хуже), loopback с
  одним ядром (лучший кандидат - HTTP/3 под закачкой через wss, хуже в 14
  раундах из 22, p=0,29; `cury0` дает те же числа, что current, то есть
  интервал уступки ни при чем).
- **Доля запросов с RTO под потерями 0,5%** (`loss13.py`): из 24 сравнений
  ни одно не значимо. Новое TCP-соединение - единственная строка, где current
  хуже на обоих транспортах (obfs 20 против 14 из 540, wss 28 против 17),
  вместе p=0,07 после отбора. Не доказано и не опровергнуто; механизма в коде
  не найдено. Проверяется 20-30 раундами одного сценария.
- **Малые запросы под закачкой без потерь** (RTT 40 мс, 6 раундов): у wss
  медиана бимодальна у обеих версий (45 или 130 мс), вердикта нет.
- **member-only** равен NoAuth до 0,5 мс, пароль стоит +1 RTT на новом
  соединении и у `password-fallback`. Остаток сверх круга (+52 мс вместо +40
  на двух сценариях) у 2.1 такой же.
- **Захват участка туннеля** (`cap.sh`) снят только для obfs с member-only:
  tcpdump внутри netns не принял сигнал остановки (профиль AppArmor tcpdump
  не принимает сигналы от процессов, запущенных из VS Code, который стоит
  из snap), и серия была остановлена. Захватывать лучше с `-c N` или
  `timeout` внутри netns, а не внешним `kill`.

## Как повторить

Тот же набор серий теперь - план пайплайна
[`scripts/matrix`](../../../scripts/matrix/README.md):

```bash
python3 scripts/matrix/matrix.py run scripts/matrix/plans/compare.toml --out bench/runs/cmp
python3 scripts/matrix/matrix.py resume bench/runs/cmp      # после обрыва
python3 scripts/matrix/matrix.py recheck bench/runs/cmp     # план перепроверки флагов "хуже"
```

План берет фильтры сценариев, масштабы, раунды и наборы ядер из скриптов
этой серии; отличия (один raw на раунд netem вместо одного на транспорт, 3
раунда серии auth вместо одного) записаны в шапке плана. Числа этой записи
сняты разовыми скриптами `bench/matrix/suite8c.sh` ... `suite14.sh` (не
коммитятся), поэтому новые числа сравнивать с новыми же, а не с таблицами
выше.

## Ограничения

- Одна машина: loopback меряет код, netem - модель сети, а не путь. WAN и
  ARM-роутер в этой серии не запускались; для них есть
  [nodes.md](../../field/nodes.md), [arm-router.md](../arm-router.md) и
  [yield.md](../yield.md).
- Полоса под netem при `-scale 0.3` - разгон slow start, а не канал.
- Soak на этой машине не сравнивает версии: число операций за 30 с
  проваливается в 2-4 раза в случайные моменты у любой версии.
