# Raw, опубликованная 2.0.0 и current: повтор WAN после оптимизации

Дата: 2026-09-22. Current в этом сравнении - **`9e0eb3937b45c7637d1536b252f5b9f852df7455`**, а не произвольный последующий HEAD. Маршрут: ARM-роутер (aarch64, 3 CPU, AES/PMULL) -> тот же Linux amd64 VPS (1 vCPU), RTT около 43 мс. Рабочие службы не обновлялись.

## Что сравнивается

- **Raw**: прямой HTTP от роутера к временному origin на VPS.
- **v2**: опубликованные клиент и сервер 2.0.0. Хеши обоих файлов совпали с [предыдущим WAN-снимком](../wan-2026-09-21/manifest.json). Клиент содержит `vcs.revision=112c4ffdd2ee941b6987f122fde6aa5235861c88`; у опубликованного Docker-сервера revision не записан, поэтому его идентичность проверяется SHA-256.
- **Current**: ARM64-клиент и AMD64-сервер, собранные Go 1.26.6 из чистого коммита `9e0eb39`, `CGO_ENABLED=0`, PGO выключен. Build info содержит `vcs.modified=false`.

Obfs и WSS измеряются **двумя отдельными сериями**. В каждой свой raw-контроль; объединять его медианы между сериями нельзя. У WSS внешний TLS проверяется временным CA и именем localhost, не отключением проверки сертификата. Используется стандартный Go TLS, без browser fingerprint. Origin внутри обоих транспортов - HTTP/1.1, без дополнительного HTTPS. Это замер полосы и стоимости транспорта, а не повтор desktop HTTPS-стенда.

В обеих версиях: формат v1, printable prologue, obfs MTU=1400, padding=256; для WSS shaping=256-4096. Включена password-auth с одним временным пользователем; холодный Argon2id прогревается до замеров. Member-only намеренно не включается только у current: сравнивается одинаковая конфигурация. Системные настройки TCP, маршруты и firewall не менялись. Raw и туннель выходят с роутера напрямую к тому же VPS; проверены маршрут через eth3 и отсутствие OUTPUT-перенаправления для тестовых TCP-портов.

## Методика

На VPS мало свободной RAM, поэтому одновременно работает **только одна тестовая версия сервера и клиента**. Обе используют один и тот же порт; после блока процессы останавливаются. Тестовые каталоги находятся на диске, не в RAM-backed `/tmp`. Origin ограничивает доступ IP источника и loopback; настоящие учетные записи не используются.

Шесть раундов охватывают все перестановки raw/v2/current. Порядок download/upload меняется через раунд. Перед каждой передачей прогрев 4 МиБ, затем **256 МиБ одним новым соединением**. Скорость включает setup и разгон TCP. На вариант и направление шесть измеренных передач. Используется один текущий `wirebench`, с исправленными единицами МиБ/с и Мбит/с; 1 МиБ = 2^20 байт. Payload - случайный блок 256 КиБ, повторяемый до заданного объема.

Для bulk проверяются HTTP status, полный объем скачивания, объем отправки и подтверждение upload; SHA-256 каждого bulk-тела этот инструмент не считает. Дополнительно после каждого блока выполняются 50 новых запросов к фиксированному ответу **24 байта**: итого 300 на вариант и транспорт, проверка status/размера/SHA-256. Это временный вариант `httpsprobe`, допускающий HTTP в проверке URL; измерение HTTP TTFB и полного тела остается тем же. P99 на 300 наблюдениях приведен для диагностики, а не как приемка порога на 10000 запросах.

CPU и RSS клиента/сервера снимаются из `/proc` отдельно. CPU/GiB - сумма CPU двух прокси; origin и генератор туда не входят. Системная загрузка и softirq учитываются отдельно в JSON. Метрики сервера включены; интенсивного отдельного scrape, массовых аккаунтов, квот и mixed traffic в этой серии нет. TCP monitor работает с интервалом 200 мс на обоих хостах; максимальный фактический разрыв 209,3 мс. Часы сверены через существующий SSH-канал; системное время не менялось.

## Результаты

Медианы шести передач по 256 МиБ, **МиБ/с**. В скобках диапазон отдельных прогонов. Изменение в последнем столбце - отношение медиан скоростей, не процент сокращения времени.

| Транспорт | Направление | Raw | 2.0.0 | Current | Отношение медиан current/v2 |
| --- | --- | ---: | ---: | ---: | ---: |
| obfs | down | 38.52 (33.91-48.14) | 44.84 (41.06-48.75) | 51.54 (49.02-53.05) | +15.0% |
| obfs | up | 56.59 (40.05-57.66) | 35.26 (17.51-48.27) | 36.07 (30.05-54.81) | +2.3% |
| wss | down | 34.50 (16.51-47.02) | 39.53 (38.83-40.98) | 47.76 (33.48-48.85) | +20.8% |
| wss | up | 48.62 (40.84-57.15) | 36.11 (30.20-44.98) | 41.27 (28.77-51.22) | +14.3% |

**Устойчивый результат этой серии - obfs download.** Current быстрее 2.0.0 во всех шести парных раундах. Для остальных строк положительное отношение медиан еще не доказывает повторяемое ускорение:

| Транспорт | Направление | Медиана парных изменений | Bootstrap 95% CI |
| --- | --- | ---: | ---: |
| obfs | down | +15.1% | [+4.9%; +24.3%] |
| obfs | up | +9.5% | [-14.8%; +125.5%] |
| wss | down | +19.4% | [-12.1%; +23.3%] |
| wss | up | +1.9% | [-6.6%; +28.8%] |

Bootstrap пересэмплирует шесть целых парных раундов, не пакеты или соседние запросы. При n=6 интервал сам по себе приблизителен. WSS download ускорился в четырех раундах и замедлился в двух; все они сохранены. Для upload ни надежное ускорение, ни повторяемая регрессия не установлены.

Raw не является постоянным физическим потолком канала: скорость меняется между передачами, а отдельный TCP-поток имеет собственные окна и потери. В этой серии медиана туннельного download выше raw. Это не означает эффективность выше 100% и не используется для такого заявления. TCP-снимки подтверждают изменения cwnd, окон и retransmits; они не доказывают единственную причину каждого провала.

Системные счетчики не позволяют приписать эти события конкретному процессу. Хост не полностью изолирован от своей рабочей нагрузки; это дополнительная граница интерпретации.

## Доказательства и ограничения

Исходники временных измерителей и оркестраторов сохранены в [fixtures](fixtures/). Они требуют приватного `addresses.json`, соответствующих бинарников и SSH-алиасов; значения адресов и credentials в репозиторий не входят.

Для каждого транспорта сохранены `samples.jsonl`, `summary.json`, `manifest.json`, `build-info.txt`, окружение и журнал. В копиях build-info удалены только концевые пробелы. Сводка пересоздается командой:

```bash
python3 docs/benchmarks/wan-2026-09-22/obfs/analyze.py
python3 docs/benchmarks/wan-2026-09-22/wss/analyze.py
```

`*-monitor.log.gz` содержат все сохраненные снимки выбранных 36 измеренных bulk-потоков каждой серии. Warmup и короткие потоки исключены только из этого извлечения, не из request-лога. IP заменены метками, hex-адреса `/proc/net/tcp` скрыты, порты/счетчики/время сохранены. `analyze-tcp.py` повторяет сопоставление потока и сводку. Выборочные TCP-счетчики не являются окончательными счетчиками закрытого сокета. При upload VPS - получатель; его retransmit нельзя выдавать за retransmit отправителя на роутере, где NETLINK_SOCK_DIAG недоступен.

Полные TCP-логи, бинарники и приватные служебные данные остаются в `/tmp/s5core-wan-20260922/` и `/tmp/s5core-wss-wan-20260922/`. В Git не добавляются IP узлов, ключи и пароли. Первый незавершенный запуск obfs остановлен проверкой фикстуры: ожидалось 23 байта вместо фактических 24. SHA-256 совпадал, продуктового дефекта не было; эта попытка сохранена отдельно и не включена в статистику.

Этот повтор сравнивает опубликованную 2.0.0 с конечной реализацией, тогда как [desktop A/B](../../reports/performance-implementation-2026-09-22.md) сравнивал рабочий baseline с H01-H05/R01 и конечный код. Проценты разных баз и нагрузок не складываются. Новый результат не меняет исторические измерения [21 сентября](../wan-2026-09-21/README.md).

Это временный WAN-стенд, не canary рабочих служб. Еще не закрыта полная выпускная приемка: длительный mixed/p99 на целевом маршруте, пик нагрузки, полный бюджет туннелей и обновление с независимым откатом.
