# TCP и UDP в S5Core 2.3.0-rc5: резерв оптимизации

Аудит от 30.09.2026. Ветка `mzx/native-udp-game-2.3`, HEAD
`83420220d5c3d95dbab5a8968951985461c5117d`, совпадение с удаленной веткой
проверено через GitHub API. Тег `v2.3.0-rc5` указывает на
`b4bd6397c916c5cd13e99f89a3ce6a59a686816a`; отличие HEAD от тега только в
`docs/plan/v2.3-rc5.md`. Производственный код, настройки и развертывания в
этом аудите не менялись. Эксперименты запускались через `go test -overlay`.

**Резерв есть.** Самый конкретный результат - уменьшение времени чистого
native-кодека на 13,5-24,1% в двух совместимых по формату прототипах. Для
UDP-всплесков следующий кандидат - пакетное чтение ответов целей с
пакетной отправкой native. Для UDP через TCP - объединение уже готовых
кадров очереди. Ускорение обычного TCP-релея и улучшение игрового пинга
этими замерами не установлены.

## Что уже исправлено к rc5

Повторное чтение кода показывает, что находки rc1 нельзя переносить в rc5
как открытые дефекты:

- `internal/socks5/associate.go:593` создает отдельный `TunnelWriter`, а
  читатель ответов в строке 728 только ставит fallback-кадр в очередь.
  Синхронная запись TCP больше не удерживает этот читатель на native-пути.
- `cmd/s5client/native_udp.go:275` фиксирует счетчик в момент решения о
  потере пути. `internal/socks5/native_path.go` упорядочивает слова клиента
  по этому счетчику, включая поздние TCP-сигналы.
- `nativeClient.hears` учитывает просроченные пробы; одна лишь давность
  последнего пакета уже не является достаточным условием отката.
- В горячих путях используются `netip`, пулы и пакетный учет трафика.
  Нулевые аллокации native-датаграммы закреплены полным тестом
  `cmd/s5client/native_cost_test.go`. Сетевой вариант этого теста в текущем
  окружении выполнить не удалось.
- TCP-обфускация уже режет запись по MTU, шифрует в заранее выделенной
  памяти, пишет пачками и выдает накопленные полные кадры при чтении.
  Настройка `yieldInterval=100us` выбрана прежним отдельным процессным
  сравнением: [замеры планировщика](../benchmarks/yield.md).
- rc5 добавил историю времени TCP dial и замену UDP-сокета, от которого не
  получено ни одного ответа. Это уже реализованные меры против дыр пути:
  [план rc5](../plan/v2.3-rc5.md).

## 1. Native UDP: два измеренных кандидата

### Содержимое паддинга

В `pkg/nativeudp/nativeudp.go:211` случайность запрашивается для длины,
а в строке 218 еще раз для содержимого паддинга. Содержимое находится
внутри AEAD; приемник использует только длину. Прототип убирает второй
запрос и оставляет нулевые байты при прежнем случайном распределении длины.

Раздел 10 спецификации задает случайную длину, но не требует случайного
содержимого. Для TCP нулевое содержимое уже прямо требуется разделом 6:
[спецификация](../veil-spec.md). Сходный прием описан для шифрованного
паддинга в [RFC 8446, раздел 5.4](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.4).
Это обоснование прототипа, а не отдельный криптографический аудит.
Счетчики, nonce, AEAD, размеры пакетов и частота проб остаются прежними.

Самостоятельный эффект в окончательных парных замерах: время `Seal + Open`
ниже на 4,2-7,8%. Патч: [zero-padding.patch](v2.3-rc5-performance-2026-09-30/zero-padding.patch).
На этом ядре Go использует `vgetrandom`; утверждать, что убрали ровно один
системный вызов на пакет, по этому замеру нельзя.

### Повторное хеширование постоянной части HMAC

`tagger.tag` в `pkg/nativeudp/nativeudp.go:147` каждый раз заново хеширует
64-байтные постоянные префиксы внутреннего и внешнего SHA-256. Тег нужен
и при отправке, и при заполнении приемного окна. В профиле штатного
`BenchmarkCodecRoundTrip` его накопленная доля составляет 46,71% CPU:
[профиль](v2.3-rc5-performance-2026-09-30/native-cpu-top.txt). Это доля чистого
кодека без сокетов, правил, учета и очередей.

Второй прототип сохраняет состояния SHA-256 после этих префиксов и
восстанавливает их перед новым счетчиком. Используется документированный
интерфейс [crypto/sha256.New](https://pkg.go.dev/crypto/sha256#New), без
`unsafe` и замены HMAC другим алгоритмом. Патч уже включает нулевой
паддинг: [cached-hmac.patch](v2.3-rc5-performance-2026-09-30/cached-hmac.patch).

Цена одного тега снизилась с 205,6 до 128,4 нс, на 37,5%. Теги для 128
ключей и 256 счетчиков каждого ключа, всего 32 768 значений, совпали с
`crypto/hmac` + SHA-256. Проверены также потери, перестановка, replay,
подделки, resync, размерные пробы и одновременная работа двух направлений.

У прототипа появился компромисс: создание `Session` выделяет 28 536 байт
вместо 27 320, то есть на 1216 байт больше, и делает 20 аллокаций вместо 8.
При этом создание стало быстрее: медиана 75,8 вместо 112,5 мкс.
Это память и аллокации при создании; на пакет по-прежнему 0 B/op и
0 allocs/op. Источники: [до](v2.3-rc5-performance-2026-09-30/setup-base.txt),
[прототип](v2.3-rc5-performance-2026-09-30/setup-cached.txt).

Состояние нового `tagger` изменяемое. При внедрении оно должно оставаться
под существующими `sendMu` и `recvMu`; копирование такого объекта не должно
создавать совместно используемые хешеры между независимыми сессиями.

### Итоговые парные замеры

Linux amd64, Intel i7-11700K, Go 1.26.6, ядро 7.0.0-34-generic,
`GOMAXPROCS=1`, без привязки к конкретному ядру. Пять последовательных
раундов с чередованием порядка `base, zero, cached` и
`cached, zero, base`, по 300 мс на случай. Все сборки завершены до этой
серии. Числа ниже - медианы, доверительные интервалы не рассчитывались.
Размер - полезная нагрузка кодека; один шаг - одностороннее
`Seal + Open` с движением приемного окна, без сети.

| Шифр / байты | rc5, нс | Нулевой паддинг, нс | Паддинг + HMAC, нс | Изменение двух правок |
|---|---:|---:|---:|---:|
| AES / 200 | 881,0 | 812,2 | 668,4 | -24,1% |
| AES / 928 | 1125,0 | 1050,0 | 909,5 | -19,2% |
| ChaCha / 200 | 1027,0 | 966,2 | 823,0 | -19,9% |
| ChaCha / 928 | 1604,0 | 1537,0 | 1388,0 | -13,5% |

Это уменьшение времени кодека, а не проценты ускорения всего сервера или
снижения RTT. На спокойном игровом потоке экономия долей микросекунды не
должна трактоваться как уменьшение пинга на миллисекунды. Практическая
цель - больше запаса CPU при загрузках и всплесках. ARM и WAN не измерены.

Первичные данные: [rc5](v2.3-rc5-performance-2026-09-30/paired-base.txt),
[паддинг](v2.3-rc5-performance-2026-09-30/paired-zero.txt),
[две правки](v2.3-rc5-performance-2026-09-30/paired-cached.txt),

Файлы `pilot-*` - предварительные серии; итоговая таблица использует только

## 2. UDP-всплески: пакетное чтение и отправка

`internal/socks5/associate.go:676` берет один ответ цели,
строит SOCKS-заголовок, копирует payload, шифрует и отправляет его в
`nativeSession.Send`, затем берет следующий. `Hub.read` тоже читает
датаграммы по одной. Аллокации устранены, но каждый пакет все еще проходит
через отдельную операцию приема и отправки.

В сохраненных полевых данных rc4 и предрелизной сборки rc5 были потери на
сокетах ответов целей, в том числе при приемном буфере 4 МиБ; общий
native-сокет в том наблюдении не терял. Это исторические данные, не новый
опрос узлов: [Ч-25](../plan/draft.md),
[воспроизведение всплесков](../benchmarks/udp-burst-2026-09-28.md).
Они указывают, какой участок профилировать первым, но не доказывают, что
CPU был единственной причиной каждого отброса.

Предлагаемый следующий эксперимент: Linux-путь, который забирает до
16-32 уже доступных ответов, сохраняет границы датаграмм, шифрует каждый
отдельно и отправляет готовую пачку через `sendmmsg`. На прочих платформах
остается одиночный путь. Для игры нельзя вводить ожидание заполнения пачки:
первый доступный пакет должен обрабатываться сразу, размер пачки ограничен.

У `x/net/ipv4` и `ipv6` есть
[ReadBatch / WriteBatch](https://pkg.go.dev/golang.org/x/net/ipv4#PacketConn.ReadBatch),
с оптимизацией на Linux. Однако прямой переход на них не гарантирует
сохранения нулевых аллокаций: в используемом `x/net v0.55.0`
`internal/socket/sys_posix.go:66` разбирает адрес в `net.IP` и
`*net.UDPAddr`. Нужен замер цены всего пути, а не только количества syscall.

Критерии: меньше CPU на миллион датаграмм и меньше `RcvbufErrors` при
одинаковой форме всплеска; p99 не хуже на редком потоке и при параллельной
загрузке; сохранены IPv4/IPv6, wildcard-source/PKTINFO, PMTU, ошибки ICMP,
ротация сокета и корректное закрытие. Выигрыш пока не измерен.

## 3. TCP: объединять уже накопленные fallback-кадры

`TunnelWriter.Run`, `internal/socks5/tunnel_writer.go:164`, вызывает
`Write` отдельно для каждого кадра. Пачки внутри `obfs.Write` объединяют
части одной записи; они не объединяют разные вызовы `Write` этой очереди.
Проба с заранее готовыми 900 кадрами дала 900 вызовов `Write`,
846 000 байт, 0 отбросов:
[измерение](v2.3-rc5-performance-2026-09-30/queued-wave.txt).
Это подсчет вызовов потоку с приемником в памяти, не измерение syscall
или TCP-пропускной способности.

Кандидат - после первого кадра неблокирующе забрать уже готовые кадры до
ограничения по числу и байтам и записать несколько length-prefixed кадров
одним вызовом. Одиночный кадр уходит сразу. Ограниченная пачка должна
сохранять приоритет control, возраст каждого кадра, stop и правильный учет
записанных байтов при ошибке. Особенно важно не расширить допустимый
перерасход квоты: нынешний `written` проверяет его после каждого кадра,
пачка не может бесконтрольно обойти эту границу.

Это относится к fallback native-ассоциаций, где есть `TunnelWriter`.
Обычный `0x83` пишет прямо из читателя; обобщение на него требует отдельного
эксперимента. К обычному TCP CONNECT вывод тоже напрямую не относится.
Критерии: меньше записей/CPU на всплеск, тот же порядок кадров и предел
квоты, отсутствие дополнительной задержки редких пакетов. 
## 4. Общий хаб и наблюдаемость

У `Hub.read` один читатель, два участка с `h.mu` на принятый пакет, а
`settle` под общей блокировкой обновляет индексы и вычисляет новые теги
(`pkg/nativeudp/nativeudp.go:632,651`). HMAC-прототип уменьшает и работу
внутри этой секции. После пакетного I/O стоит снять CPU- и mutex-профили
под несколькими ассоциациями и во время resync. Признаков фактической
проблемы конкуренции из текущего чистого микробенчмарка нет; удалять
блокировки или уменьшать replay-окно на его основании нельзя.

В `Session.packets` 64 места. Переполнение этой очереди и глобальной
очереди probe-ответов молча попадает в `default` (строки 680 и 694).
`accepted` увеличивается раньше постановки данных в очередь. В `Stats`
нет отдельных счетчиков этих двух отбросов.

Нужны пассивные счетчики `data_queue_drop` и `probe_queue_drop`, без
адресов и неограниченных меток. По разности `accepted` и `ClientNative`
их вычислить нельзя: `accepted` включает пробы и пакеты, которые позже
могут быть отклонены разбором/правилами. Это задача наблюдаемости перед
изменением размера очередей, не установленная причина игровых потерь.

## 5. Обычный TCP CONNECT

Сегментация, пулы и чтение полных накопленных кадров уже работают.
В свежем `BenchmarkFramingOnly` запись 32 КиБ с `Padding256` занимает
медиану 9,935 мкс, без аллокаций:
[данные](v2.3-rc5-performance-2026-09-30/tcp-framing.txt).
Здесь конечный сокет ничего не делает; число не задает реальную скорость
TCP. В `BenchmarkFrameObserver` медиана с SDK-телеметрией 20,413 мкс,
без hook - 20,050 мкс. Резерв этого конкретного hook небольшой:
[данные](v2.3-rc5-performance-2026-09-30/tcp-frame-observer.txt).
Это не оценка всей телеметрии и всех timeout-оберток сервера.

Открытый дефект Ч-22 остается в `cmd/s5client/main.go:477`: CONNECT-ответ
читается одним `Read`, и `n > 0, io.EOF` отбрасывается как ошибка setup.
Ранее воспроизведенные случаи приведены в
[Ч-22](../plan/draft.md).
В rc5 этот обработчик по коду не изменился. Закрытие этого дефекта повышает
надежность коротких соединений; это отдельная работа, не ускорение релея.
Критерий: полный успешный SOCKS-ответ и последующие данные доставляются
даже вместе с EOF, а поврежденный/неполный ответ не становится успехом.

Для дальнейшего ускорения обычного TCP нужен процессный профиль именно
релея: syscall, crypto, deadlines, метрики, CPU/GiB, throughput и p99
коротких запросов рядом с загрузкой. Увеличение MTU или удаление `Gosched`
по чистому framing-бенчмарку недостаточно обосновано; прежний процессный
стенд уже показал цену удаления scheduling point для p99.

## Порядок работ и проверка

1. **Нулевой паддинг native**: небольшая правка с отдельно измеренным
   эффектом; описать содержимое в спецификации и проверить старые клиенты.
2. **Предвычисление HMAC**: подтвержденный выигрыш кодека, с отдельной
   оценкой памяти на много сессий и сохранением сериализации хешеров.
3. **Счетчики очередей и профиль узла под волной**, затем **пакетное
   UDP I/O** на участке ответов целей, если профиль подтверждает цену I/O.
4. **Объединение готовой TCP-очереди**, с проверкой control, возраста,
   квоты, частичной ошибки записи и редких пакетов.
5. **Ч-22** вести как отдельный дефект TCP-клиента. Пересмотр общей
   блокировки хаба и timeout-оберток делать по профилю после первых шагов.

Перед внедрением: обязательный `./scripts/pre-commit.sh`, совместимость
клиент/сервер rc3-rc5, процессный A/B на одном CPU, затем ARM и один и тот
же WAN-путь. Для UDP использовать форму 450 датаграмм за 5 мс с хвостом и
`wave900`, отдельно 64 Гц, 1 Гц и асимметричный трафик, blackout и PMTU.
Считать CPU, p95/p99, потери на сокете/очередях, долю fallback и восстановление.
Улучшение CPU не должно увеличивать долю TCP у здорового native-пути.

В текущем аудите прошли 16 выбранных тестов кодека для каждого варианта,
включая race-прогон двух совместных прототипов, проба 900 кадров и тест
нулевых аллокаций frame observer. Полный `go test -count=1 ./...` был
запущен, но сетевые тесты упали из-за запрета создания системных сокетов
в песочнице; Docker API тоже недоступен. Полный набор и сетевые проверки
не считаются пройденными. Журнал:
[tests.txt](v2.3-rc5-performance-2026-09-30/tests.txt).
ARM, WAN, свежий игровой тест, CI, выпуск и развертывание здесь не выполнялись.

Параметры: [baseline.json](v2.3-rc5-performance-2026-09-30/baseline.json).

