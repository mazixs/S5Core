# Пайплайн бенчмарка: raw, версии, рабочее дерево

Один вход для сравнения "без прокси" против нескольких сборок s5core/s5client
на одной машине: loopback и netem, TCP, HTTP/1.1, HTTPS, HTTP/2, HTTP/3 (QUIC),
UDP через `0x83`, soak, игровая сессия. План описан в TOML, прогон переживает обрыв и
продолжается с места остановки, каждое ожидание ограничено по времени, а
отчет собирается сам.

Root не нужен: каждая ячейка работает в своем `unshare --user --net`, поэтому
порты, TIME_WAIT и qdisc у ячеек не пересекаются и ничего не остается на хосте.
Настоящий путь между двумя машинами - режим `network = "wan"`, раздел
[WAN](#wan-сервер-и-клиент-на-удаленных-машинах).

## Быстрый старт

```bash
cd scripts/matrix
./matrix.py run plans/quick.toml --dry-run      # проверка плана, ячейки, худшая оценка времени
./matrix.py run plans/quick.toml                # 5-10 минут, HEAD против рабочего дерева
./matrix.py status ../../bench/runs/quick-<время>
xdg-open ../../bench/runs/quick-<время>/report.html
```

Матрица серии 2026-09-23 (`docs/benchmarks/compare-2026-09-23/`) -
`plans/compare.toml`: те же фильтры сценариев, масштабы, раунды и наборы
ядер, что у разовых `suite8c.sh` ... `suite14.sh`, отличия перечислены в шапке
плана. Это ночь работы; серии можно гонять по одной и дописывать в тот же
каталог:

```bash
./matrix.py run plans/compare.toml --out ../../bench/runs/cmp --series lo4
./matrix.py run plans/compare.toml --out ../../bench/runs/cmp --series loss,h3loss
```

Нужны `go`, `git`, `unshare`, `ip`, `tc`, `taskset`, `openssl`, Python 3.11+
(только стандартная библиотека). Проверка окружения идет до сборки.

## Команды

| Команда | Что делает |
|---|---|
| `run PLAN [--out DIR] [--series a,b] [--dry-run]` | собирает варианты, гонит пачки, пишет отчет |
| `resume DIR [--retry-failed]` | доделывает прерванный прогон тем же планом |
| `status DIR` | сколько пачек готово, какие ячейки не `ok`, какие пачки шумные |
| `report DIR [--include-noisy]` | пересобирает `report.html`, `summary.md`, `analysis.json` |
| `recheck DIR [--rounds 10]` | пишет `recheck.toml`: только флаги "хуже", на большем числе раундов |
| `stale DIR [--kill]` | процессы из `DIR/bin`, оставшиеся после жесткого убийства |
| `wan-clean DIR` | останавливает юниты и процессы WAN-прогона на его хостах и удаляет их каталоги |

Ctrl+C один раз - ячейкам говорят остановиться и записать, что есть (до 15 с),
второй раз - убить сразу. Прерванные пачки повторяются на `resume` целиком.

## План

```toml
name = "quick"
base = "head"            # с чем сравнивать
candidate = "wt"         # что сравнивать

[defaults]               # любой ключ можно переопределить в серии
scale = 0.1              # множитель числа запросов
scenario_timeout = "2m"  # бюджет одного сценария
auth = "member"          # member | password | fallback | none, можно списком

[env.server]             # переменные поверх базового окружения стенда
OBFS_MTU = "1400"

[variants.raw]
direct = true            # без прокси, контроль
[variants.head]
ref = "HEAD"             # любой git ref, собирается из git archive
[variants.wt]
ref = "worktree"         # текущее дерево с незакоммиченными правками
[variants.wty0]
ref = "worktree"
patch = "../patches/yield-every-batch.patch"   # путь от файла плана

[cpus]                   # наборы ядер для taskset
loopback = "0-5,8-13"    # loopback-ячейки идут по одной, на одном наборе
raw = "0,8"              # netem: ячейки раунда идут одновременно,
obfs = ["1-2,9-10", "3-4,11-12"]   # у каждой свой набор, наборы вращаются по раундам
wss = ["6,14", "7,15"]

[[series]]
name = "loss"
network = { rtt_ms = 40, loss_pct = 0.5, rate_mbit = 200 }   # или "loopback"
variants = ["raw", "head", "wt"]
transports = ["obfs", "wss"]    # plain только с auth = "none"
rounds = 6
slow_ms = 150                   # доля запросов медленнее p50 + 150 мс (RTO)
only = ["h3/", "=udp/rtt-64"]   # подстрока или =точное имя
compare = [["head", "wt"]]      # по умолчанию [[base, candidate]]
kind = "probe"                  # или "soak"
```

Неизвестный ключ, пересечение ядер у одновременных ячеек, `patch`, которого
нет, или `only`, не выбравший ни одного сценария, - ошибка до запуска.
Сценарии: `bin/matrix -list` или `go run . -list` в этом каталоге.

Ячейки loopback идут по одной, порядок вариантов в каждом втором раунде
обратный, чтобы дрейф машины не ложился на один вариант. Раунд netem идет
одной пачкой: ячейки делят время, но не ядра, а наборы ядер меняются местами
от раунда к раунду. Если ячеек в раунде больше, чем наборов (серия auth),
раунд делится по режиму аутентификации: сравниваемые варианты всегда идут
одновременно.

`run` печатает худшую оценку времени (каждый сценарий упирается в бюджет), а
в ходе прогона - ETA по уже пройденным пачкам той же серии.

## WAN: сервер и клиент на удаленных машинах

Сервер и origin работают на одной удаленной машине, клиент и генератор - на
другой (роутер), оркестратор ходит на обе по ssh. Шаблон -
`plans/wan.example.toml`; копию с настоящими адресами держите в `bench/plans/`
(в `.gitignore`): адресам узлов в репозитории не место.

```toml
[wan]
server = "root@SERVER_IP"       # ssh target: systemd-run, curl, ss
client = "router"               # ssh target: хватает BusyBox (awk, nc, nohup, sha256sum)
client_arch = "arm64"           # amd64 | arm64 | arm | 386 | mipsle | mips
server_dir = "/root/s5bench"    # абсолютный путь, последняя часть содержит s5bench
client_dir = "/opt/tmp/s5bench"
# server_ip (по умолчанию из server), server_arch = "amd64",
# server_memory_max = "300M", origin_memory_max = "256M", max_foreign_cores = 0

[[series]]
name = "wan"
network = "wan"                 # plain только с auth = "none", см. ниже
```

Что происходит:

- Генератор и все варианты собираются под обе архитектуры, заливаются в
  `server_dir` и `client_dir` и сверяются по sha256.
- Адрес клиента, каким его видит сервер, определяется по новому пиру на
  `:22`, пока клиент держит соединение (NAT и несколько маршрутов у роутера
  делают его угадывание ненадежным).
- Origin на сервере - transient unit systemd (`s5bench-origin`) с
  `IPAddressDeny=any` и `IPAddressAllow` только для клиента, самого сервера и
  loopback, плюс собственный список источников в генераторе. Сервер ячейки -
  unit `s5bench-srv` с `MemoryMax`, `RuntimeMaxSec` и тем же фильтром.
- `plain` в WAN - порт SOCKS5 без пароля, но открытым прокси он не становится:
  фильтр юнита пускает к нему только клиента, а сам сервер доходит только до
  origin. `s5client` в такой ячейке не запускается, генератор идет в сервер
  напрямую, и UDP ASSOCIATE (`0x03`) остается настоящим UDP, а не `0x83`.
- На клиенте процессы живут по pid-файлам, за ячейкой следит watchdog
  (бюджет ячейки + 90 с). Убиваются только pid, в чьей командной строке есть
  каталог стенда: pid переиспользуются, а рядом работают боевые процессы.
- Ячейки идут по одной, порядок вариантов в четных раундах обратный.
- Посторонняя нагрузка хостов (`remote_foreign_cores`) - занятость хоста
  минус CPU наших процессов. Она пишется в `run.json`; пачка помечается
  шумной только при ненулевом `max_foreign_cores`.
- В конце прогона юниты останавливаются, каталоги удаляются, в журнале
  "wan: hosts cleaned". Если оркестратор убит жестко - `matrix.py wan-clean DIR`.

Грабли, на которых это проверено:

- `systemd-run` не разбирает `IPAddressAllow=localhost`, нужен
  `127.0.0.0/8 ::1`.
- Клиент 2.1 с `PROXY_AUTH_MODE=member-only` не стартует без
  `OBFS_FORMAT=v1` (в шаблоне это `[env.client]`; 2.2 читает то же значение
  как единственный формат).
- BusyBox `sleep` принимает только целые секунды, `timeout` и `ss` на роутере
  нет: паузы идут через `usleep`, готовность порта - через `/proc/net/tcp`.
- UDP-сокет генератора в raw не привязывается к 127.0.0.1: с него датаграммы
  на удаленный origin не уходят, и raw показывал 100% потерь UDP и отказ H3
  при живом пути.

## Что где лежит

```
bench/runs/<план>-<время>/
  plan.json manifest.json events.log     план, состояние пачек, журнал
  report.html summary.md analysis.json   отчет
  bin/<вариант>/{s5core,s5client} bin/matrix bin/build.json   сборки с commit, dirty и sha256
  code/                                  копия пайплайна, которой гоняются ячейки
  cells/<серия>/<ячейка>/                spec.json run.json result.json и логи
  attempts/<ячейка>.<n>/                 прошлые попытки пачки
```

Секреты стенда (PSK, пароли, ключи участников) генерируются на ячейку и живут
в `tmp/` ячейки с правами 700, каталог удаляется после ячейки. В `spec.json`
их нет.

## Ошибки, зависания и таймауты

Три уровня, каждый ловит то, что пропустил предыдущий.

1. **Операция** (генератор). Каждый dial, запрос и датаграмма под своим
   дедлайном (60 с, но не дальше бюджета сценария; 10 с на echo; 1 с на
   ожидание датаграммы). SOCKS-рукопожатие прерывается контекстом. UDP-поток
   после последней отправки ждет опоздавшие датаграммы 2 с, поэтому может
   вернуться на 2 с позже бюджета.
2. **Сценарий** (генератор). `scenario_timeout` останавливает сценарий с
   `aborted: timeout`, `max_errors_in_row` подряд - с `aborted: errors`.
   Ошибка после истечения бюджета идет в `cut`, а не в ошибки. Если сценарий
   не вернулся за `hang_grace` после бюджета, генератор пишет частичный
   `result.json` с `"hung"` и выходит с кодом 3.
3. **Ячейка** (обертка в netns). Генератор молчит дольше бюджета + grace +
   30 с - `stalled`; сервер или клиент умер во время замера - `crashed`;
   дедлайн ячейки (сумма бюджетов всех сценариев + 120 с) - `timeout`. Поверх
   этого оркестратор держит внешний таймаут на 60 с больше и убивает группу
   процессов. Смерть оркестратора убивает ячейку через `PR_SET_PDEATHSIG`, а
   netns исчезает вместе с ней.

| Статус | Значит | Повтор |
|---|---|---|
| `ok` | замер полный | - |
| `hung` | сценарий завис, остальные записаны | нет |
| `stalled`, `timeout` | ячейка остановлена по времени | нет |
| `crashed` | сервер или клиент умер во время замера | нет |
| `gen_failed` | генератор упал или не дописал результат | нет |
| `setup_failed` | не поднялись порты, netem или прогрев | да, `retries` раз |
| `cell_error` | исключение в самой обертке | да |
| `interrupted` | остановлено пользователем | на `resume` |

Повтор перезапускает пачку целиком, прошлая попытка уходит в `attempts/`.
Статусы без повтора остаются в отчете как находки: зависание или падение -
это результат, а не шум. `resume --retry-failed` перегоняет и их. Прогрев
(`tcp/connect` на 2% объема) идет со своим бюджетом, а не с бюджетом серии.

Сбои, на которых это проверено: неверный env сервера (`setup_failed` с
последней строкой лога сервера, повтор, отказ), бюджет сценария 1 мс
(`hung`), генератор под SIGSTOP (`stalled` через бюджет + grace + 30 с),
сервер под SIGSTOP (ячейка `ok`, прерванные операции в разделе "Проблемы"),
SIGKILL сервера во время замера (`crashed`), дедлайн ячейки 40 с (`timeout`,
частичный `result.json` сохранен), Ctrl+C посреди ячейки (`interrupted`, код
130, процессов не осталось, `resume` доделал).

## Шум

Перед пачкой оркестратор ждет, пока посторонняя нагрузка на ее ядрах не
опустится ниже `guard.max_foreign_cores` (до `load_wait`). После пачки
посторонняя нагрузка считается как занятость ядер пачки минус CPU всех
процессов ячеек; пачка выше порога помечается `noisy` и из сравнений
выпадает (`report --include-noisy` возвращает ее). На рабочей машине с
браузером фон 1-1,5 ядра с всплесками до 2,6, поэтому порог ниже 1,5 здесь
бесполезен, а в `quick.toml` стоит 3,0: на трех раундах одна шумная пачка
оставляет транспорт без вердикта ("мало пар").

## Игровая сессия

`game/64hz-200b` - долгая сессия быстрой сетевой игры: 64 тика в секунду,
датаграмма 200 байт в обе стороны через UDP ASSOCIATE (s5client переводит его
в `0x83`), час при `scale = 1`. Рядом идет тихий TCP-канал: эхо 64 байт раз в
40 с, дольше `READ_TIMEOUT` сервера, то есть он жив, только пока его держит
keepalive туннеля. За прокси тот же поток одновременно идет напрямую: контроль
снят в те же минуты на том же пути, отдельный вариант без прокси не нужен.

Сценарий запускается только по имени в `only` (`"=game/64hz-200b"`): час не
должен попадать в план, который его не просил.

- `loss_pct`, `p999_ms`, `jitter_ms` (среднее |ΔRTT| соседних ответов);
- `spike_pct`, `spikes_per_hour` - ответ медленнее медианы на `slow_ms` (без
  него на 50 мс), всплеск - серия таких ответов подряд; `freezes` - промежуток
  между ответами длиннее 100 мс, `longest_gap_ms`;
- `breaks` - ответа нет 3 с или закрылось управляющее соединение, ассоциация
  открывается заново, как переподключилась бы игра; `breaks_closed`,
  `downtime_s`. Тики, выпавшие на переподключение, считаются потерянными, а не
  досылаются пачкой;
- `idle_tcp_ok`, `idle_tcp_failed`;
- `ctl_*` - то же у прямого контроля.

`series` в `result.json` - окна по минуте (p50, p99, max, потери, у контроля с
префиксом `ctl_`): по ним видно, копится ли что-то за час. Трафик - около 90 МБ
в час на поток без накладных расходов туннеля, контроль - столько же.

## Как читать вердикт

Сравнение парное, по раундам. "Хуже" или "лучше" - только если медианы
разошлись не меньше чем на 5% (для процентов - на 0,5 п.п., для мс еще и не
меньше чем на 0,02 мс) и знак одинаков во всех парах. На 3 раундах метрика
без эффекта получает такой вердикт примерно в 25% случаев, на 5 - в 6%,
поэтому "хуже" - это флаг, а не вывод: `recheck` пишет план перепроверки
только флагов на большем числе раундов. Доля медленных запросов сравнивается
точным биномиальным тестом по суммам всех раундов, CPU на ГБ - по ячейке.
Колонка raw - медиана контроля без прокси.

## Как добавить сценарий

Сценарий - строка в `suite()` в `main.go`: имя и функция, возвращающая
`stats`. Цикл операций идет через `p.sample()` и `p.next(s)`, дедлайн операции -
`p.opCtx()`, пауза - `p.sleep(d)`: тогда бюджет, лимит ошибок подряд и
остановка работают без отдельного кода. `Bytes` заполняйте, иначе у ячейки не
будет CPU на ГБ. Новая метрика в `extra` попадает в отчет после строки в
`METRICS` (`pipeline/analysis.py`). Сценарий с префиксом `game/` без `-only`
не запускается (`optIn` в `main.go`).
