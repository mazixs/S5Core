# Приманка: что видит тот, кто пришел не за туннелем

Документ описывает решение задачи Ф5-6: чем отвечает сервер на все, что не
является туннелем, и почему статической страницы для этого недостаточно.
Формат самого туннеля - в [veil-spec.md](../veil-spec.md).

## Что было не так со страницей

Встроенная страница-приманка отвечала на `/`, отдавала 404 на все остальное
и 204 на `/favicon.ico`. Три ответа на весь сайт. Зонду, который умеет
задавать больше одного вопроса, этого хватает:

- один и тот же HTML на любой запрос к `/` при любом заголовке - так не
  ведет себя ни один настоящий сайт;
- путь туннеля (`WS_PATH`) отвечал **400 Bad Request** на обычный GET,
  потому что запрос доходил до обработчика апгрейда. То есть эндпоинт
  находился перебором путей: 404 везде и 400 в одном месте;
- ни cookies, ни редиректов, ни заголовков кеширования - ничего из того, что
  есть у любого живого хоста.

## Что теперь

`WS_DECOY_UPSTREAM` превращает приманку в настоящий обратный прокси на
указанный оператором сайт. Все, что не является WebSocket-апгрейдом на
`WS_PATH`, уходит наверх и возвращается как есть: статус, заголовки, тело,
включая собственный 404 этого сайта.

Отдельно: обычный GET пути туннеля больше не попадает к апгрейдеру. Решение
принимается по заголовкам (`websocket.IsWebSocketUpgrade`), и запрос без них
обслуживается приманкой наравне с любым другим путем. Проверяется тестом
`TestTheTunnelsPathLooksLikeAnyOtherPath`.

Что переписывается по дороге:

| Что | Почему |
|---|---|
| `Host` запроса наверх - имя апстрима | Иначе сайт получает имя, о котором не слышал, и виртуальный хостинг ломается |
| `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `Forwarded` - удаляются | Чужому сайту незачем знать адреса тех, кто сюда ходит, - ни зондов, ни пользователей |
| `Location` на апстрим - в путь без хоста | Иначе следующий запрос браузера уйдет на зеркалируемый домен, и это видно всем |
| `Domain=` в `Set-Cookie`, если он называет апстрим - удаляется | То же самое, только для следующего запроса с cookie |

Апстрим недоступен - 502 с нейтральной страницей, без имени веб-сервера:
страница, которая называет nginx, при заголовках от другого сервера - это
различие, которое зонд увидит. В лог при этом уходит предупреждение.

## Чего эта приманка не дает

- **Это не зеркало.** Сертификат, адрес и, скорее всего, поведение TCP -
  наши. Тот, кто сравнивает наши ответы с ответами оригинала байт в байт,
  найдет разницу; задача была в другом - убрать различия, видимые **без**
  оригинала для сравнения, то есть то, чем располагает автоматический
  сканер.
- **Ссылки внутри HTML не переписываются.** Зеркалируемый сайт будет тянуть
  часть ресурсов со своего домена. Переписывание тел - игра без выигрыша
  (CSS, JS, JSON, вебсокеты приложения), поэтому оно не делается. Выбирайте
  апстримом что-нибудь самодостаточное.
- **Апстрим видит трафик.** Он не узнает, кто именно ходит (заголовки сняты),
  но видит, что с этого адреса идут запросы. Лучший апстрим - тот, что
  принадлежит вам.

## Отказ, который ничего не сообщает

Вторая половина задачи - поведение при неудачной аутентификации. У зонда,
записавшего настоящего клиента, есть два хода:

1. отправить запись целиком - кадр соберется и будет отвергнут по истории
   повторов или по тегу;
2. отправить случайные байты - двухбайтовая длина расшифруется во что
   попало, и сервер будет ждать кадр, который не придет.

Раньше первый ход закрывал соединение мгновенно, а второй подвешивал его до
таймаута. Разница между этими двумя временами и есть ответ на вопрос "эти
байты здесь что-то значат?" - то единственное, что транспорт обязан скрыть.

Теперь сервер не закрывает соединение сам ни в одном из случаев. Он
дочитывает и выбрасывает данные, ничего не отвечает, и соединение закрывает
бюджет рукопожатия (`HANDSHAKE_TIMEOUT`) - тот же самый бюджет, который
закрывает клиента, молча подключившегося и ничего не отправившего.

Проверки: `TestAReplayedFirstFlightIsAnsweredLikeGarbage` (обфусцированный
порт, задача Ф4-4) и `TestInsideTheTunnelAReplayIsAnsweredLikeGarbage`
(WebSocket, задача Ф5-6). Обе меряют время до закрытия и объем ответа и
падают, если соединение закрылось заметно раньше бюджета.

**Цена.** Соединение, которое раньше умирало за миллисекунду, теперь живет
`HANDSHAKE_TIMEOUT` (по умолчанию 15 с) и занимает слот из `MAX_CONNECTIONS`
и свои буферы. Сканер, бьющий в порт, удерживает слоты дольше. Ручка для
этого - `HANDSHAKE_TIMEOUT`: уменьшая ее, оператор уменьшает и стоимость, и
сам бюджет рукопожатия. Отдельной ручки нет намеренно: два разных таймаута
вернули бы ту самую разницу во времени, ради устранения которой все это и
сделано.

## Настройка

```bash
WS_ENABLED=true
WS_ADDR=0.0.0.0:443
WS_CERT_FILE=/etc/letsencrypt/live/example.com/fullchain.pem
WS_KEY_FILE=/etc/letsencrypt/live/example.com/privkey.pem
WS_PATH=/ws
WS_DECOY_UPSTREAM=http://127.0.0.1:8080   # сайт, который тут и живет
```

Пустой `WS_DECOY_UPSTREAM` оставляет встроенную страницу - это по-прежнему
допустимо, но слабее по причинам из первого раздела. URL проверяется при
старте: схема только `http`/`https`, обязательный хост, без query и
фрагмента.
