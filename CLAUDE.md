# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Команды

```bash
go build ./cmd/s5core        # сервер
go build ./cmd/s5client      # клиент
go test -race ./...          # все тесты (CI гоняет с -coverprofile)
go test -race -run TestName ./pkg/obfs/          # один тест
go test -bench=. ./pkg/transport/ws/             # бенчмарки транспорта
gofmt -s -l .                # CI падает, если вывод непустой
go vet ./...
./scripts/pre-commit.sh      # полный pipeline; его же запускает CI
```

CI (`.github/workflows/ci.yml`) не содержит собственных проверок: он запускает `./scripts/pre-commit.sh` в контейнере `golang:1.26.6`, то есть локальный прогон и CI дают один вердикт по построению. Сам скрипт проверяет: `go mod verify`, `gofmt -s`, отсутствие длинного тире в `.go`, актуальность `go.mod` (`go mod tidy -diff`, по коду возврата - прежний вариант зеленел, когда tidy не отрабатывал вовсе), `go vet`, `golangci-lint` (конфиг `.golangci.yml`), `govulncheck`, race-тесты с покрытием и сборку обоих бинарей. Недостающие инструменты он ставит сам, версии обоих закреплены в шапке скрипта: с `@latest` один и тот же коммит проверялся бы разными сканерами локально и в CI. Для оффлайна есть `SKIP_LINT=1`, `SKIP_VULN=1`, `SKIP_SLOW=1`.

Воспроизвести окружение CI: `docker run --rm -v "$PWD":/src -w /src golang:1.26.6 ./scripts/pre-commit.sh`.

Вспомогательные скрипты: `scripts/check_proxy.sh`, `scripts/vpn_test.sh` (проверка прокси/туннеля), `scripts/s5vpn-win.ps1` (full-tunnel на Windows).

## Архитектура

Два бинаря вокруг общего ядра:

- `cmd/s5core` - сервер. Читает конфиг только из переменных окружения (`caarlos0/env`), см. `.env.example` и таблицы в `docs/guides/configuration.md`.
- `cmd/s5client` - локальный SOCKS5-прокси на машине пользователя, заворачивающий трафик в обфусцированный туннель к серверу.
- `pkg/s5server` - публичный SDK. `NewServer(cfg)` / `Start(ctx)` / `UpdateWhitelist`. Именно сюда встраиваются внешние Go-приложения; `cmd/s5core` - тонкая обертка над ним. `server.go` - жизненный цикл и сборка слушателей, `telemetry.go` - OpenTelemetry-инструменты и наблюдатели, `config.go` - `Config`, дефолты и валидация, `conn.go` - обертки соединения (`timeoutConn`, `metricsConn`, лимит) и buffer pool, `listener.go` - `listenerPipeline` и Accept, `advice.go` - `TRANSPORT_ADVICE`.

### Слои соединения

Сервер поднимает несколько независимых слушателей одновременно: plain SOCKS5 (`PROXY_PORT`, по умолчанию 1080), обфусцированный (`OBFS_PORT`, 1443) и WebSocket/TLS (`WS_ENABLED`). Каждый слушатель оборачивает соединение своим транспортом и отдает результат в один и тот же `internal/socks5.Server`.

- `pkg/obfs` - AES-256-GCM обертка над `net.Conn`. Формат провода целиком описан в `docs/veil-spec.md` (задача Ф5-1) - это единственный источник истины, правки формата идут сначала туда, а `pkg/obfs/spec_test.go` и `internal/socks5/spec_test.go` падают, если документ и код разошлись. Кадр: `[MaskedLen 2B][GCM(kind|payloadLen|payload|padLen|padding)]`, перед первым кадром клиент шлет 32 байта пролога, по умолчанию закодированного (`prologue.go`, раздел 3.5 спецификации): на провод уходит base64 пролога (43 символа) плюс добивка 0-20 символов того же алфавита, длина которой выводится из секрета сессии (`veil.OpeningPad`) - открытие печатаемое, поэтому первый пакет попадает под исключение правила блокировки шифрованного трафика, а граница открытия не стоит на постоянном смещении. Сервер узнает кодировку по алфавиту первых 32 байт и принимает обе, настройка (`OBFS_PROLOGUE`) только у отправителя. `kind` (1 байт внутри AEAD): 0 - данные, 1 - keepalive, 2 - FIN, 3 - hello, 4 - advice (Ф5-7, `control.go`). Управляющие кадры - TLV внутри AEAD, едут в первой записи своей стороны (hello - от клиента вместе с прологом, advice - от сервера вместе с ответом на приветствие SOCKS5), поэтому кругов не добавляют; доставляются один раз, кадр не той роли молча отбрасывается, битый - отказ `bad_control_frame`. Прежний формат (4-байтная длина, случайный nonce, AES-GCM прямо на PSK) живет в `pkg/obfs/legacy` и только у клиента: сервер его не принимает, это окно миграции с графиком удаления в `docs/field/migration.md`. Ключи сессионные: HKDF-SHA256 от PSK и секрета пролога дает по паре ключей (данные и маска длины) на каждое направление, nonce - счетчик кадров, роль (`RoleClient`/`RoleServer`) обязательна при создании соединения. Сам вывод ключей живет в `pkg/veil`, не в `pkg/obfs`: пролог и то, как из него получается секрет, - подменяемая схема (`veil.Scheme`, задача Ф5-2), остальной формат от нее не зависит. `keepalive.go` - кадр с нулевым payload и паддингом под размер недавнего кадра данных, интервал рисуется заново из `[KEEPALIVE_MIN, KEEPALIVE_MAX]` и подавляется реальным трафиком; `Read` пропускает такие кадры, поэтому пустая запись больше не доходит до читателя. `CloseWrite` шлет кадр `kindFIN` и не трогает транспорт под собой - это и есть полузакрытие, одинаковое на TCP и на WebSocket (Ф4-9): у WebSocket своего полузакрытия нет, а расходиться поведение транспортов не должно. После FIN `Read` у пира отдает `io.EOF`, обратное направление продолжает работать, а `Write` на закрытой половине возвращает ошибку. Keepalive живет здесь, а не в `pkg/transport/ws`: WebSocket-ping отличим по opcode и размеру, а обычному обфусцированному слушателю он вообще недоступен. `replay.go` - `SaltHistory`: серверная кольцевая история прологов (`OBFS_REPLAY_WINDOW`, одна на все обфусцированные слушатели), ловит повтор записанного соединения на новом сокете. Отказ выдается не в момент разбора пролога, а после расшифровки первого кадра - иначе реплей отвечал бы быстрее, чем неверный PSK, и зонд это измерил бы. Запись режется на кадры по `OBFS_MTU` и уходит пачками (`framesPerBatch`), чтение буферизует пачку кадров; буферы записи, чтения и рандома преаллоцированы и рассчитаны от MTU - менять их значит трогать hot path, изменения проверять бенчмарками и профилем релея (`docs/benchmarks/relay-profile.md`).
- `pkg/veil` - схема аутентификации первого кадра и вывод ключей (Ф5-2, Ф5-3). `Scheme` - интерфейс из четырех методов (`Name`/`Size`/`Offer`/`Accept`); `Symmetric` - голая случайная соль, `Clocked` - она же плюс 8 байт HMAC над часовой эпохой, и это схема по умолчанию. Сервер перебирает эпохи `E-2..E+2`, то есть терпит около двух часов расхождения часов; не найдя эпохи, он **не** возвращает ошибку, а отдает заведомо неверный секрет, чтобы отказ пришел там же, где отказ по неверному PSK. Диагностика рассинхрона (`OnClockSkew` -> лог и `s5core_obfs_clock_skew_total`) ничего не меняет в поведении на проводе и ограничена по частоте. `Context` (версия формата, идентификатор узла, Ф5-4) уходит в MAC пролога и в метки HKDF, а не на провод: сервер узнает контекст клиента за один HMAC до вывода ключей, поэтому поддержка двух контекстов (окно миграции, `OBFS_ACCEPT_NODE_IDS`) стоит один HMAC, а не вторую попытку расшифровки. Пустой `NodeID` - тоже идентичность, а не отсутствие проверки. Шифр тоже часть контекста (Ф5-5): клиент берет AES-256-GCM там, где у процессора есть аппаратный AES, и ChaCha20-Poly1305 там, где его нет (разница на проводе без аппаратного AES - 12 раз на x86-подстановке и 5,9 раза на настоящем ARM, а с аппаратным AES выигрыш AES на ARM - 3,4 раза против 1,7 у подстановки; замеры в `docs/benchmarks/ciphers.md` и `docs/benchmarks/arm-router.md`), сервер принимает оба и узнает выбор из MAC пролога. Размеры ключа, nonce и тега у шифров совпадают, поэтому форма кадра не меняется - это и делает выбор бесплатным. Маска длины - интерфейс `veil.LengthMask`, у ChaCha она берет 32 маски из одного блока keystream, иначе стоила бы дороже самого шифра. Вторая половина Ф5-5 - `roster.go`: `Roster` - та же `Clocked`, но 8 из 24 случайных байтов пролога отданы под идентичность участника (`Tag(ключ участника, эпоха) XOR Mask(PSK, Random, эпоха)`), а ключ участника входит в секрет сессии, поэтому два участника с одним PSK не читают трафик друг друга. `Directory` держит таблицу `тег -> участник` на все эпохи окна и перестраивает ее в фоне (`Run`, раз в четверть эпохи), поэтому поиск - одно чтение map: 1240 нс на 8 участниках и 1231 нс на 262 144 (`docs/benchmarks/roster.md`). Не нашли участника - `Anonymous` (общий аккаунт, окно миграции) или вывод ключей от **случайного** ключа-заглушки: подставить пустой нельзя, секрет тогда совпадет с секретом общего аккаунта и сервер примет любого.
- `pkg/transport/ws` - WebSocket-транспорт с шейпингом кадров (`shaped.go`, `WS_MIN_FRAME`/`WS_MAX_FRAME`/`WS_MAX_JITTER_MS`). Каждая запись режется минимум на два кадра переменным числом разрезов - иначе длина обфусцированного кадра выходит на провод как длина TLS-записи. Кадры пишутся по одному намеренно: склейка в один syscall собрала бы их в одну запись и обнулила смысл. Дефолты полосы живут в `shaped.go` (`DefaultMinFrame`/`DefaultMaxFrame`), `pkg/s5server` ссылается на них.
- `pkg/transport/tlsdecoy` - TLS-слушатель, разделяющий сокет между туннелем (WebSocket-upgrade на `WS_PATH`) и приманкой на всех прочих путях. Приманка по умолчанию - встроенная статическая страница (`staticDecoy`: корень / favicon 204 / 404), но при заданном `WS_DECOY_UPSTREAM` вместо нее поднимается обратный прокси на этот сайт (`proxy.go`, `httputil.ReverseProxy`): неаутентифицированный запрос, включая обычный GET самого `WS_PATH`, получает статус, заголовки и тело апстрима, вплоть до его 404 (Ф5-6). Апстрим не узнает посетителя (снимаются `X-Forwarded-*` и `Forwarded` в `Rewrite`) и не называет себя в ответе (`hideUpstream` переписывает `Location` и `Domain=` в `Set-Cookie`, указывающие на апстрим). `ValidateUpstream` проверяет URL на старте, иначе сервер не запускается. HTML-ссылки внутри тела не переписываются - это задокументированное ограничение в `docs/design/decoy.md`.
- `internal/utls` - подмена TLS-fingerprint через `refraction-networking/utls` (`TLS_FINGERPRINT`) и проверка пина сертификата (`WS_PIN_SHA256` у клиента). Пин ставится на `VerifyConnection`, а не на `VerifyPeerCertificate` (L01 плана правок): второй не вызывается на возобновленной TLS-сессии, потому что сертификат на ней не передается, и встраивающее приложение, которое отдаст дилеру `tls.Config` с `ClientSessionCache`, получило бы пин, проверенный один раз за все соединения. Гарантию держит `pkg/transport/ws/pin_resumption_test.go`: стенд считает выдачи сертификата сервером и потому отличает возобновление от полного рукопожатия. Чужие `VerifyConnection` и `VerifyPeerCertificate` в переданном конфиге не затираются, а выполняются перед пином и сохраняют право отказать - это там же, `TestTheCallersOwnConnectionCheckSurvivesPinning`.

### SOCKS5-ядро

`internal/socks5` - форк `armon/go-socks5` (свой LICENSE и README внутри), сильно расширенный. Не трактуй его как vendored-зависимость, правки идут прямо в нем. Ключевое отклонение от RFC 1928: **кастомная команда `0x83` (`UDPTunnelCommand`)** - UDP-over-TCP мультиплекс. Клиент переписывает байт команды в `cmd/s5client/main.go` при получении обычного Associate (`0x03`), сервер обрабатывает в `associate.go:handleUDPTcpmux`. Это защита от UDP-утечек (WebRTC/QUIC/DNS); любое изменение формата надо вносить синхронно на обеих сторонах. Обычный Associate (`0x03`) держит на ассоциацию **два** UDP-сокета (Ф6-5): анонсированный клиенту говорит только с клиентом, к целям ходит второй со своим портом и тем же `BIND_IP`. Один сокет заставлял различать команду и ответ по адресу отправителя, и посторонний, нашедший анонсированный порт, доставлял датаграммы клиенту.

Ненулевой `FRAG` теперь отказ, а не единичный пакет (F18, `udp.go:ParseUDPHeader`, раздел 10.3 `docs/veil-spec.md`): сборки фрагментов нет, и пересылка куска датаграммы отдает цели часть сообщения под видом целого. Решение меняет совместимость с клиентами, которые кладут туда мусор: их датаграммы теперь молча отбрасываются, то есть отказ виден как таймаут у приложения, а не как испорченный ответ цели. Проверка стоит в парсере, поэтому одинакова на обоих UDP-путях (`internal/socks5/udp_frag_test.go` проверяет оба).

Оба UDP-пути берут сокет клиента один раз, через `socketOf` (`request.go`), и отвечают `serverFailure`, если его нет: интерфейс `conn` обещает только `Write` и `RemoteAddr`, а ассоциация живет дольше запроса и берет у соединения локальный адрес и дедлайны. Прежде это были три приведения к `net.Conn` без проверки (L02 плана правок), то есть паника в середине ассоциации вместо отказа в ее начале (`internal/socks5/udp_socket_contract_test.go`).

Ответ сервера на `0x83` клиент читает строго по формату, а не одним `Read` (F14, `cmd/s5client/udp_client.go:readSOCKSReply`): фиксированная часть через `io.ReadFull`, проверка VER/RSV/ATYP, затем адрес и порт. Раньше ответ из одного байта проходил как успех (условие смотрело `connectResp[1]`, которого еще не было), а остаток ответа доставался кадровому циклу и читался как длины кадров. Правка заодно фиксирует границу: все, что пришло после ответа, остается в потоке и принадлежит кадрам.

DNS на UDP-путях идет под бюджетом одной датаграммы (F12, `resolver.go:resolveWithin` c `session.SLA().Dial`): резолв выполняется на той же горутине, которая читает клиентский сокет, поэтому имя без ответа останавливало не датаграмму, а всю ассоциацию. На CONNECT-пути резолв и dial делят один дедлайн (`request.go:attemptDeadline`), а контекст от резолвера дает значения, но не дедлайн (`keepValues`).

### Состояния соединения

`internal/session` - явная модель соединения (Ф6-1). Три ортогональных региона на одной `Session`, каждый - свой атомик и своя таблица переходов: `protocol` (accepted/handshake/dialing/relay/half_closed/closed, ведет `internal/socks5`), `frames` (await_header/await_body/deliver/frame_error, ведет `pkg/obfs` через `Config.OnFrameState`) и `account` (within_quota/grace/quota_exceeded/expired, ведет релей по `userstore.SessionStatus`). Плоского автомата нет намеренно: состояния меняются независимо, и плоский список пришлось бы перемножать. `Unframed` - не состояние, а отсутствие региона, поэтому plain-слушатель не публикует ячейки `frames` вообще. Тип релея (`Stream`/`Tunnel`) - атрибут `Relay`, а не отдельное состояние: он решает только какие дедлайны применимы.

Дедлайны спрашиваются у сессии, а не задаются режимом: `timeoutConn` на каждом чтении и записи зовет `Session.ReadDeadline`/`WriteDeadline`, а та отвечает по своим состояниям из `session.SLA` (`Handshake`/`Dial`/`ReadIdle`/`WriteIdle`/`FrameBody`/`Grace` из `HANDSHAKE_TIMEOUT`/`DIAL_TIMEOUT`/`READ_TIMEOUT`/`WRITE_TIMEOUT`/`FRAME_TIMEOUT`/`QUOTA_GRACE`). Строкового `SetDeadlinePolicy` больше нет. `Tunnel` в релее не получает idle-дедлайна вовсе, но недочитанный кадр получает `FrameBody` - одним таймаутом это не выражалось.

Единственная связь между регионами - `Exhaust`: событие аккаунта уводит `protocol` в `half_closed`, то есть квота срабатывает в процессе, а не к следующему соединению (`internal/socks5/grace_test.go`). Время жизни сессии принадлежит **внешней** обертке соединения (`metricsConn` в проде, `sessionConn` в тестах): `ServeConnContext` делает `defer conn.Close()`, и именно этот Close закрывает сессию. Добавляешь обертку поверх - закрывай сессию в ней, иначе терминальный переход не случится.

Каждый переход уходит в `session.Observer`, включая отвергнутые (`illegal=true`) - отказ считается, а не теряется. `pkg/s5server` превращает это в `s5core_session_transitions_total`, а реестр открытых сессий - в gauge `s5core_sessions`, который считается в момент scrape (`registerSessionGauge`), поэтому hot path платит один атомик на переход и ничего на метрику. Лейблы обеих метрик - из закрытых множеств в коде, трафик их не выбирает; `pkg/s5server/sessions_test.go` это проверяет.

### Границы пакетов

Разделение зафиксировано тестом, а не договоренностью: `internal/arch/arch_test.go` спрашивает `go list -deps` и падает, называя нарушителя (Ф6-2). Правила там же, каждое с обоснованием в одну строку. Добавляешь импорт и тест краснеет - это не формальность, а ровно то разделение, которое считается выполненным.

- `internal/relay` - копирование и учет байтов: `Half.Run` (одно направление, счетчик, опрос аккаунта на границе флаша `FlushThreshold` = 64 КиБ), `HalfClose`, `Status`. Про SOCKS5 не знает ничего. Все хуки `Half` необязательны, включая `CloseDst` и `Exhaust` (R12): `Half{Dst, Src}` - это то, что описывает документация пакета, и оно обязано работать, а не падать на первом EOF. Без `Exhaust` статус, отличный от `Allowed`, заканчивает половину: качать дальше за аккаунт, которому только что отказали, - это грация, которую вызывающий дает явно. `internal/socks5/relay.go` остался файлом из алиасов: `socks5.SessionStatus`, `socks5.ErrSessionNotAllowed` и `socks5.HalfCloseObserver` - имена публичного API SDK, и встраивающему не нужно импортировать второй пакет ради двух идентификаторов.
- `internal/identity` - решение о допуске: `identity.Guard` (бывший `fail2banStore`) с жестким лимитом на источник и мягким на аккаунт. Телеметрию не знает - `Options.OnAuthFailure`/`OnAccountAlert`, хуки собирает `authHooks` в `pkg/s5server/telemetry.go`. Хранилище под ним `Guard` не мутирует: `AddUser`/`RemoveUser` идут прямо в `userstore.Store`, который сам потокобезопасен. Бывший `Guard.ModifyStore` брал замок, которого путь аутентификации не берет, то есть не защищал ничего, и удален вместе с ним.
- `internal/socks5` - кодек сообщений: не импортирует ни телеметрию, ни obfs, ни транспорты, ни userstore.
- `pkg/transport/*` - доставка байтов. TLS внутри `ws` - собственный формат провода этого транспорта (WSS без него не существует), поэтому `internal/utls` разрешен явным исключением в правиле; криптография полезной нагрузки (`pkg/obfs`, `pkg/veil`) - нет.
- `internal/session` не зависит ни от чего нашего: это словарь, в котором отчитываются остальные.

### Пользователи и аутентификация

`internal/userstore` - lock-free JSON-хранилище аккаунтов (`USERS_FILE`) с квотами трафика и сроками действия. Счетчики трафика на hot path идут через `TrafficCounterFor` (atomic), а не через callback. `SIGHUP` перезагружает файл, сливая накопленный трафик. Пароли - Argon2id (`internal/passwordhash`); plaintext поддерживается только для миграции при первом успешном логине.

Механизм ровно один (Ф6-3). `PROXY_USER`/`PROXY_PASSWORD` раньше жили в отдельной карте паролей рядом с хранилищем, из-за чего Argon2id, квоты, сроки и роли были у развертывания с файлом и отсутствовали у развертывания без него, а `AddUser` делал разное в зависимости от того, какое из двух перед ним. Теперь `uStore` создается всегда при `RequireAuth`, просто без файла: пустой на старте, `AddUser` его наполняет. Файл добавляет к этому сохранность и каталог участников - ключи нельзя разрешить из аккаунтов, которых нигде нет, поэтому `veil.NewDirectory` по-прежнему строится только при `USERS_FILE` (иначе Roster-пролог уехал бы на провод у тех, кто его не просил).

Разделение учетной записи на две вещи (Ф6-3, `internal/identity`): `Identity` - имя, ключ, роль и политика, то, что туннель разрешает до SOCKS5 за константное время и без пароля; `Credential` - Argon2id-хеш, который проверяет панель и API. Именно поэтому оба утверждения верны одновременно: туннель не брутфорсится (он не принимает паролей), а панель принимает пароли (она не туннель). Проекции аккаунта - `UserAccount.Identity(key)`, `.Policy()`, `.Credential()`.

Роли - `user`/`operator`/`admin`, поле `role` в `users.json` (пустое = `user`). Таблица прав закрытая, в `identity.Role.Can`: connect - все известные роли, view accounts и manage server - operator и admin, manage accounts - только admin. Неизвестная роль не получает ничего, включая connect, и отвергается при чтении файла (`validateUsers` -> `ParseRole`). Роль не влияет на то, идет ли трафик, - это дело политики (`enabled`, `valid_until`, `traffic_limit_bytes`).

В SDK права проверяются на `Server.As(username)` -> `*Admin`, а не на самом `Server`: держатель `*Server` может вызвать `Stop`, ему проверять нечего, а панель действует от имени аккаунта. `Server.AddUser`/`RemoveUser`/`UpdateWhitelist` остаются путем владельца процесса и документированы как непроверяемые.

Миграция старого `users.json` (Ф6-3, `internal/userstore/migrate.go`): при загрузке каждому аккаунту без `tunnel_key` выдается ключ (32 байта `crypto/rand`), файл переписывается, в лог идет предупреждение со списком аккаунтов - **без самих ключей**: лог отгружают, ротируют и читают не владельцы аккаунтов. `Reload` мигрирует только в памяти и файл не трогает - оператор его только что редактировал, и обработчик сигнала не вправе писать поверх.

Хеш проверяется там, где читается файл, а не там, где логинятся (F15):
`passwordhash.Validate` вызывается из `validateUsers`, и файл с хешем, который
нельзя проверить, отвергается целиком - на старте или на том `SIGHUP`, который
его принес. Причина в том, что Argon2id на части параметров отвечает паникой,
а не ошибкой (`t=0`, `p=0`, пустой тег), а отрицательное `m` в прежнем разборе
через `fmt.Sscanf` превращалось в запрос на терабайты и убивало процесс по OOM.
Разбор PHC строгий: хвост после параметров, нестрогая версия и знак у числа -
все это отказ, диапазоны проверяются с обеих сторон.

Ленивая миграция plaintext-пароля хеширует с отпущенным замком (110 мс под
замком остановили бы все остальные соединения), поэтому запись результата
проверяет состояние заново: `commitMigratedHash` отказывается писать, если
аккаунт исчез, сменил `*userEntry`, уже получил хеш или сменил plaintext
(R05). Правка оператора выигрывает у миграции, которая шла в это время, а файл
при отказе не переписывается - `SIGHUP` его намеренно не трогал.

Fail2ban-обертка над `CredentialStore` живет в `internal/identity` (`identity.Guard`), не в `internal/socks5`.

### Наблюдаемость

Метрики - через OpenTelemetry (`InitTelemetry` в `pkg/s5server/telemetry.go`), экспортер Prometheus на `METRICS_BIND_ADDR:METRICS_PORT`. По умолчанию биндится на localhost - не менять дефолт.

## Договоренности

- Ключ участника (`tunnel_key` в `USERS_FILE`, он же `OBFS_MEMBER_KEY` у клиента) - не пароль и из пароля не выводится: 32 случайных байта. Аккаунт с ним опознается туннелем до рукопожатия SOCKS5, и `internal/socks5` отвечает `NoAuth`, называя сессии это имя (`Config.TunnelIdentity` -> `obfs.IdentityOf`). `IdentityOf` разворачивает обертки соединения (`NetConn`/`Unwrap`), потому что до SOCKS5 туннель доходит завернутым в `metricsConn` - добавляешь свою обертку, дай ей `NetConn()`, иначе участники молча потеряют имена. Аккаунты без ключа продолжают ходить по паролю, пока сервер не выставит `OBFS_REQUIRE_MEMBER_KEY=true`.
- Вид пролога (`OBFS_PROLOGUE`) тоже настройка **отправителя**: `printable` (по умолчанию) кодирует пролог, `raw` - прежний провод, сервер принимает обе кодировки без настройки. Поэтому порядок обновления парка здесь обратный порядку `OBFS_FORMAT`: сервер первым, клиенты следом (`docs/field/migration.md`, 4.6). Полевой замер, ради которого это сделано, - в `docs/field/stealth.md`: на фильтрующем пути кодированное открытие дает 0 отказов на 78 соединений, сырой пролог - 45 на 48. Меняешь длину или алфавит открытия - обновляй записанные числа в `pkg/obfs/demo_test.go` (`openingLenLow`/`openingLenHigh`/`openingLenDistinct`) и раздел 3.5 `docs/veil-spec.md`, иначе падает `pkg/obfs/spec_test.go`.
- `OBFS_SPLIT_OPENING` (клиент, по умолчанию выключено) кладет открытие в отдельную запись, кадры - в следующую. Формат от этого не меняется: получатель читает поток и границ записей не видит, серверу настраивать нечего. Это второе, независимое от печатаемости исключение того же фильтра: он классифицирует первые пакеты от 100 байт, а открытие - 43-72 (замер и живой прогон туннеля в `docs/field/stealth.md`, раздел 4.7 `docs/field/migration.md`, раздел 3.5 `docs/veil-spec.md`). Выключено по умолчанию, потому что короткий пакет на фиксированном месте - постоянная форма, а на измеренном пути печатаемое открытие проходит и без нее. Кругов не добавляет: запись не ждет ответа.
- Шифр (`OBFS_CIPHER`) совпадать **не** обязан: его выбирает клиент по своему процессору, сервер принимает оба. Добавляешь третий шифр - он должен попасть в `veil.Ciphers()`, в раздел 5.0 `docs/veil-spec.md` и в `docs/benchmarks/ciphers.md`, иначе падает `pkg/obfs/spec_test.go`, а сервер его не примет.
- Совпадать у клиента и сервера обязаны `OBFS_PSK` (ровно 32 байта) и `OBFS_NODE_ID`, а часы двух машин - расходиться меньше чем на два часа (Ф5-3). `OBFS_MAX_PADDING` - настройка отправителя (приемник берет длину полезной нагрузки из расшифрованного заголовка и это поле не читает), `OBFS_MTU` ограничивает размер кадра этой стороны на проводе и задает размеры ее буферов (приемник читает любую заявленную длину кадра, до 65535 байт - больше 16-битное поле не выражает). При правке обфускации все равно проверяй обе стороны: формат кадра общий.
- Правила уровня 1 в `internal/stealth/level1.go` - это дословный перенос политики из статьи USENIX Sec 2023, и расхождение с ней считается дефектом чек-листа, а не его настройкой. Проверено 19.09.2026: TLS-исключение Ex5 задано тремя байтами с диапазонами (`[\x16-\x17]\x03[\x00-\x09]`, раздел 4.3 статьи), у нас стояли два - `tlsRecordPrefix` теперь проверяет все три. Двухбайтовая версия освобождала `16 03 FF`, которое цензор блокирует, то есть чек-лист зеленел бы на форме, которую в поле режут; это важно ровно для контрмеры с TLS-префиксом из `docs/field/stealth.md`. Там же приведен к статье Ex1: сравнения нестрогие (`<= 3.4`, `>= 4.6`), граница полосы освобождается, - это `inRandomBand`. Меняешь таблицу исключений - сверяйся со статьей, а не с прошлой версией таблицы.
- Регрессионная проверка стелса - чек-лист `internal/stealth` и `pkg/obfs/demo_test.go` (`TestTheStealthChecklist`), а не энтропия: энтропийный порог проходит любой шифрованный поток и остается зеленым ровно тогда, когда продукт детектируем. В тесте записано текущее состояние формата (доля первых пакетов без исключений Ex1-Ex5, постоянные байты заголовка, длины открытия). Позиционная проверка уровня 2 идет по потоку **за** открытием (`internal/stealth/opening.go`, `alignPastOpening`): сравнивать абсолютные смещения в корпусе с открытием переменной длины значит мерить алфавит открытия, а не тело за ним. Меняешь формат кадра - обновляй записанные числа и указывай задачу. Корпус для стороннего анализа: `S5CORE_STEALTH_CORPUS=<dir> go test ./pkg/obfs/ -run TestTheStealthChecklist`, затем `go run ./cmd/stealthcheck <dir>`.
- `scripts/keepalive_matrix.sh` + `cmd/idleprobe` - стенд для измерения времени жизни простаивающего туннеля (прямо и за nginx в docker). Самый короткий таймаут на пути - собственный `READ_TIMEOUT` сервера (30 с), поэтому интервал keepalive обязан быть меньше него; CDN и мобильный CGNAT локально не воспроизводятся.
- Любой отказ в `readOpening` идет через `c.fail`, а не возвратом ошибки (R08): схема (`veil.Scheme`) подменяема, и та, которая вернет ошибку по данным клиента, немедленно откроет разницу во времени между отказом на прологе и отказом на кадре. Сегодняшние схемы такой путь не берут - неизвестному клиенту они отдают неверный секрет, - поэтому `bad_opening` в метрике стоит на нуле; инвариант держится тестом со схемой-заглушкой (`pkg/obfs/linger_synctest_test.go`, обе кодировки открытия).
- Отказ обфусцированному соединению не рвет сокет, а сливает его в никуда до конца бюджета рукопожатия (Ф5-6): `obfs.Config.RefuseLinger` кормится из `HANDSHAKE_TIMEOUT` (`server.go`), сервер читает и выбрасывает байты, пока дедлайн не истечет. Так время до закрытия при неверном PSK, при реплее и при мусоре, который так и не стал кадром, совпадает - иначе зонд отличал бы отказ от шума. Отдельной ручки на linger нет намеренно: второй таймаут вернул бы разницу во времени. `c.authenticated` выставляется **после** проверки реплея в `readFrame`, иначе реплей был бы освобожден от слива и закрывался быстрее (`pkg/obfs/conn.go`). Гарантию держат `pkg/s5server/replay_probe_test.go` и `pkg/s5server/decoy_probe_test.go`, обоснование - в `docs/design/decoy.md`.
- Открытие несет **первый кадр любого вида**, а не первый кадр данных (R04): половина, закрытая до первой записи, шлет FIN с тем же кодированным открытием (`writeControlLocked` в `pkg/obfs/keepalive.go`). Прежде эта ветка писала сырой пролог, то есть тихо закрытое соединение открывалось формой, ради ухода от которой и сделана кодировка, и теряло исключение фильтра из `docs/field/stealth.md`. Гарантию держит корпус из 300 таких соединений через `stealth.Analyze` (`pkg/obfs/halfclose_opening_test.go`), а не глазами: числа сверяются с теми же константами, что и обычное открытие в `demo_test.go`.
- Верхняя граница шейпера соблюдается и **не становится сама модой** (R09): кусок выше `maxFrame` садится не на `maxFrame`, а в случайную точку верхней шестнадцатой полосы (`plan` в `pkg/transport/ws/shaped.go`). Жесткий кламп поднимал долю самой частой длины в корпусе с 1,7% до 4,3% при пороге теста 5% и до 17% на батче туннеля - то есть чинил выход за границу, заводя взамен одну заметную длину. Остаток моды принадлежит правилу floor и неустраним без роста числа кадров на 25% (арифметика и замеры - `docs/benchmarks/frame-shaping.md`, раздел "The upper bound"); порог держит `TestTheBoundDoesNotMakeOneLengthTheShape`. Пустая запись кадра не производит вовсе (R10): кадр нулевой длины - форма, которой на этом соединении больше нет ни у чего.
- `docs/benchmarks/frame-shaping.md` - замеры и обоснование шейпинга (Ф4-7): почему полоса начинается с 256, почему цена в syscall неустранима и как она соотносится с бюджетом 10%, плюс цена верхней границы (R09/R10). Читай перед правкой `shaped.go`.
- `docs/design/writer-serialisation.md` - решение Ф4-6 (мьютекс на направление вместо горутины-писателя) с замером, на который оно опирается; трогая запись в `pkg/obfs` или `pkg/transport/ws`, читай его первым.
- `docs/design/half-close.md` - решение Ф4-9 (FIN-кадр в формате обфускации вместо `CloseWrite` транспорта), цена по benchstat и найденная попутно гонка дедлайна записи в `ws.Conn`. Читай перед правкой полузакрытия или формата кадра.
- `scripts/udp_loss_matrix.sh` + `cmd/udpprobe` - стенд для измерения цены UDP-over-TCP (`0x83`) на канале с потерями: три контейнера и `tc netem` внутри них (root на хосте не нужен). Итог Ф4-10 в `docs/benchmarks/udp-over-tcp.md`: через туннель теряется меньше датаграмм (TCP чинит участок до сервера), медиана не меняется, платит хвост - плотный поток один RTT, редкий поток один RTO (в Linux минимум 200 мс). Отдельного режима в обход туннеля не будет: это и есть утечка UDP. Там же цена датаграммы внутри клиента: цикл мультиплексирования в `cmd/s5client/udp_client.go` - единственный код, выполняемый на каждый пакет, и он не аллоцирует ничего (`BenchmarkUDPDatagramRoundTrip`, `TestADatagramCostsNoAllocations`). Держится это тем, что адрес приложения берется один раз на ассоциацию, а чтение и запись идут через `netip` (`ReadFromUDPAddrPort`/`WriteToUDPAddrPort`): `*net.UDPAddr` на каждое чтение плюс копия под атомик стоили трех аллокаций из семи, сравнение адресов строками - остальных четырех (R11). Трогаешь цикл - гоняй бенчмарк.
- Порядок в `Server.Stop` значим: сначала отмена контекста, закрытие слушателей и `wg.Wait()`, и только потом финальный сброс трафика (`StopPeriodicFlush`). `internal/relay` отдает счетчику последнюю пачку (до `relay.FlushThreshold`, 64 КиБ на направление) в момент завершения половины, то есть при закрытии соединения; сброс до ожидания писал файл без этих байтов у каждой живой сессии. Гарантию держит `pkg/s5server/shutdown_flush_test.go`.
- `docs/gates/README.md` - оглавление вердиктов по всем пяти шлюзам плана; все пять вынесены. G1 (полоса: канал или код) закрыт 19.09.2026 замером на боевом VPS: канал 333-599 Мбит/с, туннель 80,3% вниз и 73,3% вверх, процессор не загружен (5-6,5% ядра у сервера) - упор в канал и окно TCP на RTT 43 мс, а не в код. Порог SLO в `docs/benchmarks/results.md` (85% канала) обфусцированный слушатель не берет, plain берет (89,9%); разница - цена кадрирования и шифрования, она измерена и стабильна.
- Уровень 4 чек-листа стелса - не что сеть делает с потоком, а что о клиенте записывает принимающая сторона: `internal/stealth/fingerprint.go` разбирает `ClientHello` и считает JA3 и JA4, `internal/stealth/fingerprint_test.go` держит записанные отпечатки пяти профилей uTLS, а `pkg/transport/ws/fingerprint_test.go` проверяет, что дилер кладет на провод именно их - это два разных утверждения, и совпадение таблиц между файлами намеренно продублировано, чтобы расхождение падало тестом. JA3 у Chrome разный на каждом соединении (шаффл расширений с версии 110), JA4 - один и тот же, поэтому совпадать надо по JA4 (`TestChromeShufflesItsJA3ButNotItsJA4`). Числа привязаны к версии uTLS: при апгрейде зависимости запись обновляется **после** сверки нового JA4 с настоящим браузером, а не подгонкой теста под вывод. Без `TLS_FINGERPRINT` клиент на проводе - это Go без GREASE и без ALPN (`TestWithoutAFingerprintTheClientIsRecognisablyNotABrowser`). Приемник в поле - `cmd/fpcollect` (свой TLS-слушатель, отдает JSON с JA3, JA4, предложенным и выбранным ALPN, SNI, GREASE и RTT рукопожатия): чужие сервисы доступны не с каждого пути и меняют выдачу без предупреждения. Наш сервер ALPN не выбирает - расхождение известное, пункт Б-3 в `docs/backlog.md`.
- `cmd/fpprobe` + `docs/field/stealth.md` - уровень 3 чек-листа стелса, то есть проверка не корпуса, а живого пути. Проба шлет один пакет заданной формы и смотрит `bytes_acked` из `TCP_INFO`: подтверждение дает стек другой стороны, поэтому ответ не зависит от приложения - важно, потому что наш сервер отказ оформляет как молчание (`RefuseLinger`), и по поведению сервера доставку не отличить. Замер 19.09.2026 на фильтрующем пути: случайный первый пакет доставлен в 20% случаев поодиночке и в 6% при всплеске из 16 соединений, те же байты под пятибайтовым заголовком TLS-записи - 93 из 93. У формы есть два модификатора: `:splitN` пишет тот же залп N отдельными сегментами TCP, `@N` задает размер только этой форме (`random:split3@512`). `splitN` меряет самую дешевую из возможных контрмер - правило смотрит на первую полезную нагрузку соединения, и если ее разрезать, смотреть становится не на что; обмана это не требует, потому что оба конца наши и принимающий стек собирает поток сам. В одно число там сложены два эффекта (рассинхрон разбора и укорочение первого сегмента, которое меняет Ex1), разделяются они сравнением `random:splitN` с `random@размер_сегмента`. Между сегментами стоит пауза (`-split-gap`, 3 мс): Nagle Go выключает сам, но остается autocorking Linux, который склеивает мелкие записи - у реализации в клиенте будет ровно та же задача. Отсюда: обфусцированный туннель с этого пути не поднимался вообще, хотя plain SOCKS5 и прямой HTTP на тот же адрес работали. Это полевое подтверждение вердикта G3 и цены контрмеры (пять байт на соединение).
- `scripts/wire_local.sh` - локальный стенд полосы, откалиброванный по боевому каналу (RTT 43 мс, 390 Мбит/с, потери 0,02%, задержка ставится только на клиенте, чтобы путь сервер-цель остался быстрым, как в поле). Нужен, чтобы оценивать прогресс и регрессию полосы без VPS. Прямой замер сходится с боевым (41,0 против 41,4 МБ/с), туннель локально дает фору около 8 процентных пунктов (88,9% против боевых 80,3%) - числа сравнивать с локальными же, а не с боевыми. Числа и способ проверки в `docs/benchmarks/local-bandwidth.md`.
- `docs/backlog.md` - работа, по которой решение принято и обосновано, но она не начата: Б-1 мимикрия под конкретный сервис (половина механизма уже есть - `WS_DECOY_UPSTREAM` и `TLS_FINGERPRINT`, нет профиля клиента; ограничение в том, что домен наш, и в том, что профиль обязан быть согласован с приманкой, иначе мимикрия снижает стелс) и Б-2 WSS за чужим фронтом без своих ключей (`WS_ENABLED` сейчас требует `WS_CERT_FILE`/`WS_KEY_FILE`, а терминация TLS на фронте ничего не раскрывает - полезную нагрузку шифрует `pkg/obfs`). Заводишь новый пункт - там же пиши, что считается его выполнением.
- `docs/field/nodes.md` - боевые узлы и цена туннеля на настоящем пути, с контролем без туннеля: у каждого числа есть тот же путь и та же точка, но мимо туннеля, иначе полоса в МБ/с не значит ничего. Замер 20.09.2026 на двух узлах в разных ЦОД: длинное плечо (RTT 43 мс) отдает 84,0% канала, короткое (RTT 25 мс) - 88,1%, то есть порог SLO из README берет тот узел, у которого короче плечо, и разница объясняется RTT, а не настройкой. UDP через туннель не двигает медиану ни на одном пути (+0,6 мс и -0,1 мс), а хвост растет только там, где на пути есть потери (p95 +6,4 мс против 0) - это полевое подтверждение `docs/benchmarks/udp-over-tcp.md`. Оттуда же числа по устойчивости установки и решение, что `OBFS_SPLIT_OPENING` на боевых путях не нужен. Там же раздел "что уходит мимо туннеля": трафик шел мимо по двум причинам, и ни одна не в коде - перехват висел на списке портов, а правило "страна клиента - напрямую" отдавало прямой путь STUN-серверу с адресом этой страны. Проба - `scripts/leak_matrix.py`, запускать с проверяемой машины: она сверяет адреса по четырем осям - порт, протокол (UDP и TCP), география сервера и версия IP, - подбирая цели парами так, чтобы разница в ответах называла причину (один сервер на 3478 и на 10000: разный только порт, поэтому разница говорит именно о перехвате). С `--node` она выносит вердикт сама и возвращает код 1 на ответ с чужого адреса. Вердикт выносится по адресу, а не по конфигурации: правило прокси-ядра, отбрасывающее весь udp/443, может быть живым и при этом не видеть трафика пробы вообще, если перехват его не забирает. Вывод для развертывания: перехватывать весь диапазон портов, а решать "что идет напрямую" по домену, ASN или стране на стороне прокси-ядра - номер порта про трафик не говорит ничего, и WebTransport (HTTP/3 на произвольном UDP-порту) раскрывает адрес там, где обычный WebRTC-тест на 3478 и 19302 показывает путь чистым. Настройка перехвата на роутере - `docs/field/mihomo.md`. Охват перехвата - свойство развертывания, проверять на каждом новом отдельно; снимаешь новые числа - дописывай туда.
- `docs/benchmarks/arm-router.md` - замер на целевом железе клиента: ARM-роутер (aarch64, 3 ядра, аппаратный AES) с клиентом, собранным кросс-компиляцией. Отсюда берутся ответы на вопросы "потянет ли роутер" и "будет ли OOM": гигабит через туннель стоит одного ядра из трех **процессу** и около 1,8 ядра роутеру целиком (такты процесса не считают softirq, поэтому там же снята вторая колонка из `/proc/stat`), 200 одновременных соединений - 25 МБ RSS (73-92 кБ на соединение: 37 кБ буферов `pkg/obfs` от `OBFS_MTU` плюс два буфера `io.Copy` по 32 КиБ в релее клиента, потому что у `obfs.conn` нет `ReadFrom`/`WriteTo`), под `GOMEMLIMIT=32MiB` клиент не падает и не платит за лимит ничем измеримым. Там же - plain-контроль на том же пути (98,3% канала против 87,1% у туннеля), который и разделяет остаток полосы на цену кадрирования и цену RTT; до него это разделение было догадкой. Там же сняты настоящие ARM-числа шифров, заменившие подстановку `GODEBUG=cpu.aes=off` на x86. Тестовый бинарник кросс-компилируется целиком (`go test -c`), Go на роутере не нужен.

- `scripts/conn_latency.sh` + `cmd/connlat` - стенд для разложения установки соединения на круги (symmetric netem, RTT 50 мс). Измерено: прямо в цель 2,01 RTT, голый SOCKS5 5,02, obfs 4,03, WSS 6,06. Обфускация не тратит на рукопожатие ни одного круга - соль, приветствие и CONNECT идут одним кадром. Отсюда решение шлюза G4 в `docs/gates/g4-first-frame.md`: схема первого кадра берется симметричная (вариант Б), потому что 0-RTT экономить нечего; задача фазы 5 - не потерять это свойство (ответ сервера до полезной нагрузки стоит +1 RTT, то есть +25% установки).

- Смена транспорта в поле (Ф5-7) идет без замены бинарника, `docs/field/migration.md`. Сервер: `TRANSPORT_ADVICE` (разбор в `pkg/s5server/advice.go`, рекомендованный транспорт обязан быть включенным слушателем, иначе старт отклоняется) - клиент получает кадр `advice` внутри туннеля и применяет к следующему соединению. Рычаг на живом сервере - не переменная, а `TRANSPORT_ADVICE_FILE` (`cmd/s5core/advice_file.go`): окружение запущенного процесса снаружи не меняется, поэтому `SIGHUP` перечитывал переменную и получал ровно то же значение (F19). Файл побеждает переменную, перечитывается по сигналу, проходит те же проверки; отсутствующий или пустой файл снимает рекомендацию, битый - оставляет прежнюю в силе и уходит в лог. Это тот же порядок, что у `LOG_LEVEL_FILE`, и по той же причине: у переменной роль дефолта развертывания, у файла роль рычага. Клиент: `TRANSPORT=auto|obfs|ws` (`ws` требует `WS_URL`, рекомендация адрес не несет), `TRANSPORT_COOLDOWN` - отдых транспорта после отказа на фазах dial/greeting/auth (connect не считается), `OBFS_FORMAT=auto|v1|legacy` с чередованием форматов по `OBFS_FORMAT_REPROBE`. Политика целиком в `cmd/s5client/transport.go`; `dialTunnel` без `policy` ведет себя как раньше, поэтому вручную собранные конфиги в тестах ничего не знают о ней. Фаза `auth_rejected` отделена от `auth` намеренно: отказ сервера в аутентификации - это ответ, а ответ доказывает, что транспорт и формат дошли до конца SOCKS5-диалога. Политику он не двигает и подсказку про PSK, `OBFS_NODE_ID` и часы не печатает (иначе одна опечатка в пароле уводила весь клиент на прежний формат провода на все окно `OBFS_FORMAT_REPROBE`, а сервер этот формат не принимает). Молчание на той же фазе по-прежнему считается отказом пути. Гарантию держат `TestARejectedPasswordDoesNotMoveTheTransportOrTheFormat` и `TestTheSilentServerHintIsNotPrintedForARejection`. Хочешь новую ручку формы - только через конфигурацию, `TestClientDefaultsMatchTheLibraries` ловит расхождение дефолтов клиента с библиотеками.
- `s5core_client_connections_total{client_version, transport}` - единственная метрика с лейблом, значение которого приходит из трафика. Исключение записано в `docs/design/observability-policy.md` и держится оградой `versionLabels` (`pkg/s5server/advice.go`): символы идентификатора сборки, 32 символа, не больше 32 именованных сборок на сервер, дальше `other`. `transport` берется у слушателя, а не из hello. Ограду проверяют `TestClientBuildsAreCountedByTransport` и `TestTheVersionLabelIsFenced`.
