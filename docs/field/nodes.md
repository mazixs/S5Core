# Боевые узлы: сколько стоит туннель на настоящем пути

Замеры в [`benchmarks/local-bandwidth.md`](../benchmarks/local-bandwidth.md) и
[`benchmarks/arm-router.md`](../benchmarks/arm-router.md) отвечают, сколько
берет код. Здесь другой вопрос: сколько из канала доходит через туннель и что
происходит с задержкой. Поэтому у каждого числа есть контроль - тот же путь,
та же точка, то же время, но мимо туннеля.

Без контроля полоса не значит ничего: 33 МБ/с это провал, если канал дает 90,
и почти потолок, если канал дает 39.

Снято 20.09.2026, версия на всех точках `v1.5.0-rc1`, транспорт `obfs`,
формат провода `v1`, пролог `printable`, шифр AES-256-GCM (выбран клиентом по
аппаратному AES). Раздел "Контроль после обновления" повторяет те же замеры
21.09.2026 на `v2.0.0`.

## Стенд

Два узла в разных ЦОД, оба с одним кодом и одной настройкой; отличаются длина
плеча и железо. Клиент - один и тот же ARM-роутер, два экземпляра `s5client`.

| | узел A | узел B |
|---|---|---|
| сервер | 1 vCPU, 967 МБ | 4 ядра, 5,9 ГБ |
| RTT ICMP с клиента | 42,8 мс (42,6-43,0) | 25,1 мс (24,4-25,7) |

Длина плеча - единственное, что различает узлы в выводах ниже. Адреса, порты и
имена машин к результату отношения не имеют и здесь не приводятся.

## Полоса: прямо и через туннель

Один файл в 50 МБ с того же сервера, прогоны чередуются (прямо, туннель,
прямо, туннель), чтобы состояние канала было общим.

| | прямо, МБ/с | туннель, МБ/с | доля канала |
|---|---|---|---|
| узел A, прогон 1 | 40,3 | 33,5 | |
| узел A, прогон 2 | 38,5 | 32,6 | |
| **узел A, среднее** | **39,4** | **33,1** | **84,0%** |
| узел B, прогон 1 | 47,4 | 43,6 | |
| узел B, прогон 2 | 50,3 | 42,6 | |
| **узел B, среднее** | **48,9** | **43,1** | **88,1%** |

Порог SLO из README - 85% канала. Короткое плечо его берет, длинное не берет
четырех десятых процента. Разница объясняется не кодом: код на обеих сторонах
один, а RTT отличается почти вдвое. Остаток полосы съедает окно TCP на длинном
плече - тот же вывод, что у шлюза G1 в
[`gates/README.md`](../gates/README.md): упор в канал и RTT, а не в процессор.

Прошлый замер на том же узле давал 80,3%, нынешний 84,0% - это не улучшение
кода, а другой измеритель: там полоса снималась через второй туннель, здесь с
клиента, который и есть боевой.

## Задержка установки

Медиана десяти запросов к `http://cp.cloudflare.com/generate_204`: сначала
прямо, потом через узел.

| | прямо | через узел | разница |
|---|---|---|---|
| узел A | 0,056 с | 0,185 с | +0,129 с |
| узел B | 0,052 с | 0,133 с | +0,081 с |

Это цена маршрута, а не туннеля: прямой запрос уходит в ближайшую точку
Cloudflare, через узел он сначала доезжает до узла. Разница между узлами
повторяет разницу их RTT. Цена самой обфускации измерена отдельно и в кругах:
4,03 RTT против 5,02 у голого SOCKS5, то есть кадрирование не добавляет ни
одного круга ([`gates/g4-first-frame.md`](../gates/g4-first-frame.md)).

## UDP через туннель

200 датаграмм по 60 байт с интервалом 20 мс, `cmd/udpprobe`, эхо на сервере.
Контроль - тот же UDP по тому же пути, но мимо туннеля.

| | p50 | p95 | p99 | джиттер | потери |
|---|---|---|---|---|---|
| узел A, прямо | 43,3 мс | 43,7 мс | 44,0 мс | 0,3 мс | 0/200 |
| узел A, туннель | 43,9 мс | 50,1 мс | 51,8 мс | 1,3 мс | 0/200 |
| узел B, прямо | 26,9 мс | 30,0 мс | 30,9 мс | 1,2 мс | 0/200 |
| узел B, туннель | 26,8 мс | 29,8 мс | 32,1 мс | 1,2 мс | 0/200 |

Медиана не меняется ни на одном пути (+0,6 мс и -0,1 мс), платит хвост: там,
где на пути есть потери, p95 растет на 6,4 мс, где потерь нет - не растет
вовсе. Это ровно предсказание
[`benchmarks/udp-over-tcp.md`](../benchmarks/udp-over-tcp.md): мультиплекс
`0x83` чинит потери участка до сервера, а цену выставляет редким датаграммам,
попавшим на ретрансмиссию.

Потерь ноль во всех четырех прогонах, то есть худший случай из
`udp-over-tcp.md` (один RTO, в Linux минимум 200 мс) здесь не наступает.

## Устойчивость установки соединения

25-30 подключений подряд на каждый узел, чередуя две формы открытия (в одной
записи с кадрами и отдельным пакетом, `OBFS_SPLIT_OPENING`):

| | открытие с кадрами | открытие отдельным пакетом |
|---|---|---|
| узел A | 30/30, 0,190 с | 30/30, 0,186 с |
| узел B | 25/25, 0,165 с | 25/25, 0,175 с |

Ни один из путей не режет первый пакет, поэтому `OBFS_SPLIT_OPENING` выключен
на обоих: выигрыша нет, а короткий пакет на фиксированном месте - это своя
постоянная форма. Путь, на котором она нужна, и измеренный там порог в 100
байт - в [`stealth.md`](stealth.md).

## Контроль после обновления до 2.0.0

Повтор 21.09.2026, когда парк перешел на `v2.0.0` (сначала клиенты, следом
серверы). Вопрос здесь один: не стало ли хуже. Контроль тот же - прямая
закачка по тому же пути в том же окне.

| | RTT ICMP | установка через узел | туннель, МБ/с | прямо, МБ/с |
|---|---|---|---|---|
| узел A, 20.09 (rc1) | 42,8 мс | 0,185 с | 33,1 | 39,4 |
| **узел A, 21.09 (2.0.0)** | **43,3 мс** | **0,188 с** | **31,9-33,2** | **29,0-32,8** |
| узел B, 20.09 (rc1) | 25,1 мс | 0,133 с | 43,1 | 48,9 |
| **узел B, 21.09 (2.0.0)** | **26,7 мс** | **0,136 с** | **40,8-44,8** | **48,3-52,0** |

Полоса туннеля воспроизвелась на обоих узлах, задержка установки совпала до
трех миллисекунд, RTT - в пределах суточного разброса пути. Доля канала на
узле B - 78-89% против записанных 88,1%.

Прямой контроль на узле A в этот раз просел до 29-32,8 МБ/с, и туннель вышел
быстрее него (97-114%). Это не заслуга туннеля: через узел A в момент замера
шел боевой трафик (46 живых сессий на сервере), и проседал именно тот прогон,
который шел без туннеля. Число полосы на узле A за этот день считать нельзя -
контроль недостоверен; сам туннель дал свои прежние 32-33 МБ/с.

Версия клиента проверена отдельно, потому что заменялись обе стороны сразу.
Старый бинарник rc1 поднимался рядом с новым на своем порту петли и качал с
того же сервера, чередуя с ним: 33,0 / 35,8 / 28,7 МБ/с у rc1 против
27,8 / 29,0 / 30,8 у 2.0.0, то есть разницы между версиями нет - обе версии
лежат внутри разброса пути. Клиент при 50 МБ/с занимает 55% одного ядра из
трех, то есть упора в процессор роутера нет.

### Чем мерить, чтобы число значило скорость, а не разгон

Одиночная закачка в 50 МБ на коротком плече длится около секунды, и в эту
секунду попадает разгон окна TCP, а не установившийся поток. Такой замер дал
28-35 МБ/с там, где установившаяся скорость - 41-45. Поэтому скорость берется
серией из четырех закачек подряд, первая отбрасывается, а считает ее сам
`curl` (`%{speed_download}`), а не секундомер оболочки: `date +%s` на четырех
секундах округляет до 25%.

Так же снимается и фон. Замер на роутере считает все, что на нем в это время
работает: на первом прогоне 21.09 треть ядра занимал забытый `awk` по
14-мегабайтному логу, и полоса туннеля падала до 28-30 МБ/с при свободном
канале. Перед замером стоит посмотреть `top` и убедиться, что idle близок к
95%, иначе меряется загрузка роутера, а не путь.

## Что уходит мимо туннеля

Полоса и задержка меряют трафик, который до туннеля дошел. Этот раздел про
трафик, который до него не дошел: два сервиса проверки WebRTC показали
настоящий адрес клиента при том, что обычный HTTP-запрос с той же машины
показывал адрес узла.

Проверяется без браузера: WebRTC узнает внешний адрес не у сайта, а у
STUN-сервера, поэтому достаточно послать тот же Binding Request самому
(`scripts/leak_matrix.py`, запускать с проверяемой машины). Замер 20.09.2026:

| STUN сервер | порт | нас видят как | почему так |
|---|---|---|---|
| stun.l.google.com | 19302 | адрес узла | порт в списке перехвата |
| stun.cloudflare.com | 3478 | адрес узла | порт в списке перехвата |
| stun.sipgate.net | 3478 | адрес узла | порт в списке перехвата |
| **stun.sipgate.net** | **10000** | **настоящий адрес** | **порт вне списка** |
| **stun.sipnet.ru** | 3478 | **настоящий адрес** | **правило по стране отдает прямой путь** |
| stun.linphone.org | 3478 | адрес узла | контроль |

Две строки выделены, потому что это две **разные** причины, и лечатся они в
разных местах. Пара sipgate 3478/10000 доказывает первую без рассуждений: один
и тот же сервер, один и тот же протокол, отличается только номер порта.

1. **Перехват висел на списке портов, а не на всем диапазоне.** Все, чего в
   списке нет, идет мимо туннеля, и это касается не только UDP: SSH на порт 22
   приходил на сервер с настоящего адреса.
2. **Правило "страна клиента - напрямую" в конце набора** отдает прямой путь
   любому серверу с адресом этой страны, в том числе STUN-серверу. Локальный
   сервис проверки этим и пользуется. Лечится правилом для STUN/TURN **до**
   правила по стране.

Ни одна из причин не в s5core: на всех путях, где трафик до туннеля дошел,
наружу виден адрес узла. Это охват перехвата, то есть свойство развертывания,
и проверять его надо на каждом новом отдельно - для этого проба и лежит в
репозитории. `scripts/leak_matrix.py` сверяет адреса по четырем осям: порт,
протокол (UDP и TCP), география сервера и версия IP. С ключом `--node` она
выносит вердикт сама и возвращает код 1, если ответ пришел с адреса, которого
в списке узлов нет.

Номер порта для такого решения плохой признак, и дело не только в дырках
списка: на одном номере живут разные вещи - на UDP 10000 и STUN, раскрывающий
адрес, и медиа Jitsi. Утечка STUN-ом не ограничивается: WebTransport ходит
поверх HTTP/3, то есть по UDP на произвольном порту, и сервис проверки,
собранный на нем, читает настоящий адрес, пока перехвачен не весь диапазон -
при этом обычный WebRTC-тест на стандартных 3478 и 19302 показывает путь
чистым. Отсюда правило: **перехватывать весь диапазон портов, а решать "что
идет напрямую" по домену, ASN или стране на стороне прокси-ядра.**

Настройка перехвата на стороне роутера - в [`mihomo.md`](mihomo.md).

### Чем закрыто

Диапазон перехвата раскрыт на все порты, STUN/TURN (3478-3481, 5349-5352,
19302-19309, tcp и udp) вынесены в правила прокси-ядра до правила по стране.
Контрольный прогон 20.09.2026 после правок: все шесть серверов пробы видят
один адрес - адрес узла. SSH на внешний сервер приходит с адреса узла.

Там же выяснилось, почему вердикт выносится по адресу, а не по конфигурации:
правило прокси-ядра, отбрасывающее весь UDP на порт 443, живо и срабатывает
(1201 раз), но датаграммы пробы на тот же порт до ядра не доходят вообще - их
не забирает перехват, и ни один счетчик ядра они не двигают. Правило в конфиге
не говорит о том, что трафик через него идет; говорит только адрес, который
видит сервер ([`stealth.md`](stealth.md), уровень 4).

## Как повторить

На сервере (порт открыт только на время замера, отдается случайный blob):

```bash
head -c 50000000 /dev/urandom > /tmp/blob.bin
python3 -m http.server 38080 --bind 0.0.0.0 &
/tmp/udpprobe -echo 0.0.0.0:39999 &
```

С клиента:

```bash
ping -c 10 <сервер>
curl -s -o /dev/null -w '%{speed_download}\n' http://<сервер>:38080/blob.bin
curl -s -o /dev/null -w '%{speed_download}\n' \
     --socks5-hostname 127.0.0.1:<порт клиента> http://<сервер>:38080/blob.bin
udpprobe -target <сервер>:39999 -n 200 -interval 20ms -label direct
udpprobe -target <сервер>:39999 -socks 127.0.0.1:<порт> -n 200 -label tunnel
```

Прогоны обязательно чередовать: канал клиента общий с остальным трафиком, и
два подряд замера одной стороны меряют не туннель, а соседа по каналу. Стенд
после замера убирать - открытый HTTP на публичном интерфейсе это лишняя
поверхность, а `blob.bin` занимает 50 МБ на диске сервера.
