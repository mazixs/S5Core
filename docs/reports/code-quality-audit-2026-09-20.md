# S5Core: код-ревью и аудит качества

Дата: 20.09.2026. Проверена текущая рабочая копия на ветке `main`, базовый коммит `71971ed8f82dd52ce7214598932bdf454d8fc894`. В анализ включены измененные и неотслеживаемые файлы. Это аудит рабочего дерева, а не только указанного коммита или опубликованного релиза.

## 1. Вывод

Код проходит штатный Linux-анализ и race-тесты, но содержит существенные ошибки управления доступом, UDP и жизненного цикла. Зеленый линтер здесь не означает готовность к релизу. Найдено **19 дефектов: 10 уровня P1 и 9 уровня P2**. P0 не подтвержден. Приоритет P1 означает необходимость исправления до релиза соответствующей функции; условия применимости указаны у каждой находки.

Основные проблемы:

- Удаленный через SDK пользователь продолжает устанавливать новые соединения со старым ключом туннеля.
- Оба UDP-режима обходят проверку адреса отдельной датаграммы и контроль состояния аккаунта; учет трафика неполон.
- Отмена контекста при активном UDP-over-TCP может навсегда заблокировать остановку сервера.
- WebSocket читает сообщение целиком без ограничения размера до проверки ключа; холодная проверка паролей не ограничивает число параллельных Argon2id.
- Объект административного SDK сохраняет отозванные права; оператор получает ключи других аккаунтов.
- Windows-сборка обоих основных бинарей сломана, хотя release workflow обещает их публиковать.

При этом признаков массового мертвого кода нет: подтверждены **две полностью недостижимые внутренние функции**. Большая часть остальных результатов `deadcode` относится к публичному SDK и тестовым помощникам. Неиспользуемых переменных и бесполезных присваиваний настроенные анализаторы не обнаружили.

Исходники, зависимости и существующие документы в ходе аудита не изменялись. Добавлен только этот отчет. Исправления, коммит, публикация и проверка production не выполнялись.

## 3. Подтвержденные дефекты

### F01. P1: удаление аккаунта не отзывает ключ туннеля

**Код:** [server.go:288](../../pkg/s5server/server.go#L288), [request.go:285](../../internal/socks5/request.go#L285), [relay.go:136](../../internal/relay/relay.go#L136).

`Server.RemoveUser` удаляет запись из `userStore`, но не обновляет `s.members`. В отличие от `ReloadUsers`, он оставляет старый ключ в `veil.Directory`. Обновление эпох самой директории не перечитывает store. Новое соединение получает старую identity и `NoAuth`. Затем `TrafficCounterFor` возвращает `nil`, потому что пользователя уже нет, а `relay.Half.Run` при `Counter == nil` вообще не вызывает `Status`.

**Воспроизведение:** `TestAuditRemovedMemberStillTransfers`: поднять сервер с `USERS_FILE` и обязательным ключом участника, вызвать `RemoveUser("alice")`, открыть новый туннель старым ключом. CONNECT и обмен данными с echo проходят. Это не только отсрочка отзыва уже открытой сессии.

**Исправление:** синхронно обновлять директорию при изменениях аккаунтов; проверять существование и текущую политику identity до разрешения CONNECT; не связывать обязательность авторизации с наличием указателя счетчика. Добавить регрессию на новые и существующие сессии после удаления.

### F02. P1: разрешенный адрес в UDP-запросе открывает доступ к запрещенным назначениям

**Код:** [request.go:128](../../internal/socks5/request.go#L128), [associate.go:148](../../internal/socks5/associate.go#L148), [associate.go:454](../../internal/socks5/associate.go#L454).

`Rules.Allow` вызывается для первоначального SOCKS-запроса. В `0x03` и `0x83` адрес каждой последующей датаграммы независимо извлекается из UDP-заголовка и сразу разрешается через DNS/отправляется. Проверка `Rules` на этот адрес отсутствует. Адрес setup-запроса UDP ASSOCIATE к тому же описывает клиентскую сторону ассоциации, а не все будущие назначения.

**Воспроизведение:** `TestAuditUDPPolicyBypass/0x3` и `/0x83`: правило разрешает только `127.0.0.2`; setup указывает его, датаграмма указывает запрещенный `127.0.0.1`. Echo получает пакет. Счетчик вызовов `Rules.Allow` остается равным 1.

**Исправление:** проверять назначение каждой датаграммы до DNS и отправки; отдельно определить допустимость самой команды UDP ASSOCIATE. Общий валидатор назначения должен использоваться обоими UDP-обработчиками. Для запрещенного имени тест должен доказывать отсутствие DNS-запроса и исходящего пакета.

### F03. P1: UDP не обеспечивает квоты, срок действия и полный учет трафика

**Код:** [associate.go:267](../../internal/socks5/associate.go#L267), [associate.go:324](../../internal/socks5/associate.go#L324), [server.go:129](../../pkg/s5server/server.go#L129).

В обоих UDP-циклах отсутствует вызов `SessionStatus`: уже открытая ассоциация продолжает работать после исчерпания квоты, истечения срока или удаления аккаунта. В `0x83` отсутствует и вызов пользовательского счетчика трафика. В стандартном UDP `udpMeter.addIn/addOut` сразу возвращается при `BytesAddIn/BytesAddOut == nil`, поэтому обязательный для учета `TrafficCallback` оказывается зависим от необязательной телеметрии SDK.

**Воспроизведение:** оба подслучая `TestAuditUDPPolicyBypass` пересылают пакет при настроенном статусе `SessionQuotaExceeded`, не вызывая проверку. `TestAuditUDPMeterDependsOnTelemetry`: передано 300 байт, пользовательскому callback передано 0. Для `0x83` отсутствие metering также видно непосредственно в обоих циклах обработчика.

**Исправление:** отделить биллинговый учет от метрик; учитывать payload обоих направлений и проверять политику на ограниченной границе пакетов/байтов. Зафиксировать, входят ли заголовки в квоту. Проверить одинаковое поведение с `Telemetry=nil` и с Prometheus, а также финальный сброс остатка при закрытии.

### F04. P1: активный `0x83` может заблокировать завершение сервера

**Код:** [associate.go:430](../../internal/socks5/associate.go#L430), [associate.go:445](../../internal/socks5/associate.go#L445), [associate.go:485](../../internal/socks5/associate.go#L485), [socks5.go:211](../../internal/socks5/socks5.go#L211), [server.go:653](../../pkg/s5server/server.go#L653).

При отмене контекста TCP-reader выходит через `return`, не вызывая `stopTunnel`. Обработчик при этом ждет только `<-errCh`, а не `ctx.Done()`. UDP-reader может остаться в `ReadFromUDP` без дедлайна. Закрытие UDP-сокета находится в `defer` обработчика и до него выполнение не доходит. `ServeContext` ждет этот обработчик, вслед за ним зависает `Server.Stop`.

**Воспроизведение:** `TestAuditUDPTunnelCancellationHangs`: создать простаивающий `0x83`, отменить контекст, закрыть TCP-соединение и listener. `ServeContext` не возвращается за контрольные 200 мс. Неограниченность ожидания подтверждается циклом зависимостей в коде, а не только длительностью теста. Проба намеренно оставляет заблокированный обработчик во временном тестовом процессе; завершение процесса освобождает его ресурсы.

**Исправление:** единая идемпотентная остановка обеих половин, выбор между результатом и отменой контекста, принудительное закрытие сокетов и ожидание обеих горутин. Регрессионный тест должен проверять завершение `Server.Stop`, включая сброс учета.

### F05. P1: неаутентифицированное WebSocket-сообщение не ограничено по памяти

**Код:** [conn.go:24](../../pkg/transport/ws/conn.go#L24), [conn.go:44](../../pkg/transport/ws/conn.go#L44), [upgrader.go:24](../../pkg/transport/ws/upgrader.go#L24).

Адаптер вызывает Gorilla `ReadMessage`, который собирает полное сообщение, и копирует непрочитанный остаток в `readBuf`. `SetReadLimit` нигде не установлен. Проверка ключа обфускации находится выше этого слоя, поэтому знание PSK для выделения памяти не требуется. Таймаут ограничивает время, но не количество полученных за него байт.

**Воспроизведение:** `TestAuditWSBuffersWholeMessage`: после WebSocket upgrade отправлено сообщение размером 2 МиБ; вызов `Read` с буфером на 1 байт оставляет в `readBuf` 2 097 151 байт. Большой объем и параллельные сообщения не проверялись ради экономии ресурсов.

**Исправление:** читать сообщение потоково через `NextReader` и/или задать обоснованный предел сообщения на обоих концах. Предел должен учитывать разрешенный batching и публичный контракт `Write`, а не произвольный маленький размер. Проверить oversized и fragmented messages. Возможности ограничения описаны в [документации Gorilla](https://pkg.go.dev/github.com/gorilla/websocket#Conn.SetReadLimit).

### F06. P1: холодный Argon2id допускает неограниченное число разных проверок

**Код:** [verifier.go:143](../../internal/userstore/verifier.go#L143), [guard.go:202](../../internal/identity/guard.go#L202), [passwordhash.go:15](../../internal/passwordhash/passwordhash.go#L15).

Объединение конкурентных запросов работает для одинаковых `username/password`. Разные неверные пароли холодного аккаунта создают разные `flight` и одновременно запускают Argon2id. Общего семафора/бюджета памяти KDF нет; лимит соединений не заменяет такой бюджет; ban регистрируется после дорогой проверки и не останавливает уже начатую пачку. Один стандартный KDF запрашивает 64 МиБ. Кеш успешной проверки помогает в установившемся режиме, но не защищает до первого успеха и после истечения TTL.

**Воспроизведение:** `TestAuditColdVerifierConcurrency` под `synctest` подтверждает одновременный вход 32 разных паролей в функцию дорогой проверки. KDF в этой пробе заменен блокирующим callback; это проверка планирования, не реальный замер 2 ГиБ памяти. При стандартном KDF эти 32 операции требуют примерно 2 ГиБ только под его рабочую память.

**Исправление:** ограничить глобальную параллельность KDF с учетом памяти, добавить отменяемую ограниченную очередь и проверять дешевые условия аккаунта до KDF. Проверить холодный старт, разные неправильные пароли и TTL. Простое уменьшение стоимости Argon2 не исправляет отсутствие ограничения.

### F07. P1: административный объект сохраняет права после понижения роли или удаления

**Код:** [admin.go:32](../../pkg/s5server/admin.go#L32), [admin.go:55](../../pkg/s5server/admin.go#L55), [admin.go:75](../../pkg/s5server/admin.go#L75).

`Server.As` сохраняет копию `identity.Identity`. Все последующие действия авторизуются по сохраненной `a.actor.Role`, а не по актуальной записи store. Уже выданный handle остается административным после `SetRole`, `ReloadUsers` или удаления аккаунта.

**Воспроизведение:** `TestAuditStaleAdmin`: root получает handle, понижает себя до `user`, тем же handle назначает другого admin; после удаления root handle по-прежнему меняет роли.

**Исправление:** хранить идентификатор действующего аккаунта и перечитывать его при каждой операции; исчезновение аккаунта должно приводить к отказу. Определить отзыв доступа при отключении аккаунта. Проверить отзыв у уже созданных handle.

**Граница риска:** это дефект account-bound SDK. В проекте нет HTTP admin API, поэтому удаленная эксплуатация через готовый административный endpoint не утверждается. `As(username)` также не является процедурой входа: вызывающее приложение обязано само аутентифицировать пользователя.

### F08. P1: роль operator получает ключи всех аккаунтов

**Код:** [admin.go:87](../../pkg/s5server/admin.go#L87), [migrate.go:128](../../internal/userstore/migrate.go#L128), [model.go:43](../../internal/identity/model.go#L43).

`Admin.Accounts` требует только `ViewAccountsAction`, доступное operator, и возвращает `Identities()` с полем `Key`. В модели permission описан как просмотр имен, ролей и квот без ключей. На практике вместе со списком аккаунтов передаются их 32-байтовые секреты, включая admin. Это позволяет обладателю общего PSK представляться другими участниками туннеля. Выдача ключей вместе с листингом закреплена текущими тестами: замечание касается небезопасного разделения полномочий, а не случайной сериализации.

**Воспроизведение:** `TestAuditOperatorReceivesKeys`: `As("noc").Accounts()` возвращает ключ root длиной 32 байта. Значения ключей в отчет и вывод не включались.

**Исправление:** отдельный DTO списка без секретов; выдача/перевыпуск ключа отдельной операцией с отдельным разрешением. Тест на отсутствие ключей у operator и в обычном листинге. Как и F07, применимо к приложениям, использующим account-bound SDK; автоматическое получение прав HTTP-admin через этот ключ не доказано.

### F09. P1: release workflow не может собрать Windows-бинарники

**Код:** [s5core/main.go:315](../../cmd/s5core/main.go#L315), [s5client/main.go:315](../../cmd/s5client/main.go#L315), [release.yml:81](../../.github/workflows/release.yml#L81).

В общих файлах обеих команд используется `syscall.SIGUSR1`, которого нет для Windows. Linux CI этого не видит. При теге release job падает на Windows-сборке. Docker image к этому моменту уже мог быть опубликован: `create-github-release` зависит от `build-and-push-docker`.

**Воспроизведение:** `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./cmd/...` возвращает `undefined: syscall.SIGUSR1` для обоих файлов. Linux/arm64 и Darwin/arm64 собираются.

**Исправление:** вынести Unix-сигналы в файлы с build tags и предоставить Windows-вариант. В CI до публикации проверять всю заявленную матрицу основных бинарей. Публикация Docker и release assets должна зависеть от успешно завершенных проверок.

### F10. P1: ошибочный начальный `ALLOWED_IPS` снимает ограничение доступа

**Код:** [server.go:369](../../pkg/s5server/server.go#L369), [listener.go:254](../../pkg/s5server/listener.go#L254), [config.go:146](../../pkg/s5server/config.go#L146).

В `Start` нераспознанные IP молча пропускаются. Если список полностью ошибочный, результат пуст; пустой whitelist означает разрешение всем. При этом `UpdateWhitelist` те же значения отклоняет. CIDR-строка, которую пользователь ошибочно принял за поддерживаемую, попадает в ту же ветку.

**Воспроизведение:** `TestAuditInvalidInitialWhitelistIsOpen`: настройка `192.0.2.OOPS` не мешает старту и SOCKS5-handshake клиента с loopback; тот же список вызывает ошибку `UpdateWhitelist`.

**Исправление:** единый строгий парсер для старта и обновления; любая неправильная запись должна отклонять конфигурацию. Не превращать ошибку конфигурации в пустой разрешающий список. Поддержку IP и CIDR следует определить явно.

### F11. P2: объединение проверок пароля пересекает смену хеша

**Код:** [verifier.go:152](../../internal/userstore/verifier.go#L152).

Ключ `flights` содержит username и тег пароля, но не хеш/версию учетной записи. Пока проверяется старый пароль против старого хеша, reload может заменить хеш. Новая проверка старого пароля против нового хеша присоединится к старому flight и получит его `true`. У обычного кеша проверка `against` есть, у flight ее нет.

**Воспроизведение:** `TestAuditVerifierFlightCrossesHashChange`: две синхронизированные проверки с одинаковыми username/password и разными `hash`; новый KDF не вызывается, новая проверка возвращает `VerifyPathCoalesced` и `true`. Воспроизведено на механизме кеша, без вероятностной гонки сетевых запросов.

**Исправление:** включить хеш/версию записи в ключ flight, повторно проверить актуальность аккаунта перед разрешением входа. Регрессия должна моделировать reload во время KDF.

### F12. P2: DNS не входит в бюджет подключения

**Код:** [request.go:153](../../internal/socks5/request.go#L153), [request.go:213](../../internal/socks5/request.go#L213), [resolver.go:15](../../internal/socks5/resolver.go#L15).

DNS запускается на исходном контексте сервера, а `context.WithTimeout` создается только внутри `handleConnect`, после DNS. Дедлайн TCP-клиента не отменяет `LookupIP`. Медленный DNS способен занять обработчик дольше `DIAL_TIMEOUT` и handshake budget. UDP-resolve имеет такую же проблему ограничения одной операции.

**Воспроизведение:** `TestAuditDNSOutsideDialBudget`: при SLA dial/handshake по 1 секунде Resolver получает контекст без deadline. Реальный зависший DNS не требовался.

**Исправление:** создавать общий контекст попытки до DNS, передавать его resolver и dialer; для каждой UDP-операции установить отдельный ограниченный бюджет. Проверить медленный resolver, отмену клиента и остановку сервера.

### F13. P2: `^` внутри класса символов отключает автоматическое ограничение regex

**Код:** [ruleset.go:38](../../internal/s5core/ruleset.go#L38).

`anchorPattern` считает любой символ `^` или `$` признаком явно заданных границ выражения. Но `^` в `[^.]` является отрицанием класса, а экранированный `$` может быть обычным символом. Такие шаблоны остаются неограниченными и разрешают совпадение с частью имени вопреки обещанию автоматически проверять полное назначение.

**Воспроизведение:** `TestAuditCaretClassDisablesAnchoring`: шаблон `[^.]+\.example\.com` разрешает `ok.example.com.attacker.invalid`.

**Исправление:** использовать явную семантику полного совпадения либо корректный разбор `regexp/syntax` для обратной совместимости. Добавить классы символов, экранированные метасимволы и альтернативы в таблицу тестов. Отдельно определить нормализацию регистра DNS-имен.

### F14. P2: клиент принимает неполный ответ на создание UDP-туннеля

**Код:** [udp_client.go:37](../../cmd/s5client/udp_client.go#L37).

Ответ сервера читается одним `Read`. Если пришел только байт `VER=5`, условие `rn >= 2 && connectResp[1] != 0` не срабатывает, и клиент сообщает приложению об успехе. Оставшаяся часть SOCKS5-ответа затем разбирается как длины UDP-кадров, повреждая поток. `net.Conn` не гарантирует целый протокольный ответ за один `Read`.

**Воспроизведение:** `TestAuditUDPReplyAcceptedAfterOneByte`: upstream отправляет только один байт `5`, приложение уже получает полный ответ об успешном UDP ASSOCIATE.

**Исправление:** прочитать фиксированный заголовок через `io.ReadFull`, проверить VER/REP/RSV/ATYP, затем полностью прочитать переменный адрес и порт. Не терять данные после ответа. Для CONNECT-пути также полезен общий parser вместо проверки результата произвольного `Read`, хотя тот путь остаток ответа пересылает дальше.

### F15. P2: неполная валидация PHC приводит к panic и может оставить незавершенный flight

**Код:** [passwordhash.go:111](../../internal/passwordhash/passwordhash.go#L111), [passwordhash.go:139](../../internal/passwordhash/passwordhash.go#L139), [verifier.go:164](../../internal/userstore/verifier.go#L164).

Параметры Argon2 проверяются только на верхние границы. Нет положительных нижних границ, проверки длины декодированных salt/hash и строгого полного разбора параметров. Например, пустой hash доходит до `argon2.IDKey` и вызывает panic. При panic внутри `slow()` flight не удаляется и `done` не закрывается, поэтому следующие одинаковые попытки могут ждать бессрочно, даже если верхний обработчик поймал panic.

**Воспроизведение:** `TestAuditEmptyPHCHashPanics`: строка `$argon2id$v=19$m=8,t=1,p=1$c2FsdA$` вызывает panic вместо возврата ошибки. Прием любого пароля этой строкой не подтвержден: фактическое поведение именно panic.

**Исправление:** строгая валидация PHC при загрузке и перед KDF, безопасные диапазоны чисел до преобразования в unsigned, допустимые размеры salt/hash. Гарантировать завершение flight при ошибке. Условие дефекта - неправильный хеш в файле аккаунтов; удаленное изменение этого файла аудит не предполагает.

### F16. P2: допустимый для валидатора `WS_PATH` может обрушить запуск

**Код:** [listener.go:80](../../pkg/transport/tlsdecoy/listener.go#L80), [listener.go:145](../../pkg/transport/tlsdecoy/listener.go#L145).

`ValidatePath` проверяет лишь несколько строковых условий. Путь `/{` проходит, но регистрация в современном `http.ServeMux` вызывает panic. Паттерны вроде `/{name}` дополнительно расходятся с точным сравнением `r.URL.Path` в upgrader. Listener к моменту регистрации уже создан.

**Воспроизведение:** `TestAuditBadPathPassesValidation`: `ValidatePath("/{") == nil`, регистрация того же значения в ServeMux вызывает panic.

**Исправление:** принимать именно канонический литеральный путь; отвергать wildcard/pattern-синтаксис и неоднозначные представления до открытия сокета. Другой вариант - единый handler с точным сравнением пути. Контракт panic при недопустимом паттерне подтвержден [документацией ServeMux](https://pkg.go.dev/net/http#ServeMux).

### F17. P2: ошибка частичного запуска оставляет уже поднятые listeners

**Код:** [server.go:399](../../pkg/s5server/server.go#L399), [server.go:428](../../pkg/s5server/server.go#L428), [server.go:485](../../pkg/s5server/server.go#L485).

Plain listener запускается до obfs/WS. При ошибке bind следующего порта или загрузки сертификата `Start` возвращает ошибку без отката уже поднятой части. SDK-клиент, считающий неуспешный `Start` отсутствием работающего сервера, оставляет порт и горутины активными.

**Воспроизведение:** `TestAuditFailedStartLeavesPlainListener`: занять obfs-порт, вызвать `Start`, получить ошибку; plain SOCKS5 продолжает отвечать на handshake. Затем тест явно вызывает `Stop` для очистки.

**Исправление:** транзакционный запуск с cleanup всех приобретенных ресурсов при ошибке. CLI уже вызывает `Stop` после возврата `Start`, поэтому для штатного CLI эффект ограничен этим промежутком; основной дефект относится к контракту SDK.

### F18. P2: неподдерживаемые UDP-фрагменты пересылаются как целые датаграммы

**Код:** [udp.go:30](../../internal/socks5/udp.go#L30).

Парсер игнорирует ненулевой `FRAG`, хотя reassembly не реализован. В результате части фрагментированного SOCKS5-пакета уходят назначениям как отдельные полные payload. Это расхождение с [RFC 1928, раздел 7](https://www.rfc-editor.org/rfc/rfc1928.html#section-7): при отсутствии поддержки фрагментации такие пакеты требуется отбрасывать.

**Воспроизведение:** `TestAuditFragmentAccepted`: пакет с `FRAG=1` принимается `ParseUDPHeader` без ошибки.

**Исправление:** отвергать `FRAG != 0`, пока не реализована сборка фрагментов. Проверить оба UDP-режима и не заявлять полную поддержку RFC при сознательном отклонении.

### F19. P2: заявленное изменение transport advice по SIGHUP не читает изменяемый источник

**Код:** [main.go:264](../../cmd/s5core/main.go#L264), [main.go:291](../../cmd/s5core/main.go#L291), [migration.md](../field/migration.md).

Обработчик SIGHUP повторяет `env.Parse` над окружением уже запущенного процесса. Изменение `.env` или `export` в другом shell это окружение не меняет, а конфигурационный файл здесь не читается. Поэтому обещанный сценарий изменения `TRANSPORT_ADVICE` без рестарта штатного бинаря не обеспечен. Прямой SDK-вызов `UpdateTransportAdvice` работает как отдельный механизм.

**Подтверждение:** прослежен путь обработки сигнала; в нем нет чтения `.env` или иного файла advice. Для `LOG_LEVEL` в проекте уже предусмотрен отдельный `LOG_LEVEL_FILE`, а для advice аналог отсутствует. Живой production-процесс не изменялся.

**Исправление:** добавить явный файл конфигурации/advice с валидацией и атомарным применением либо честно описать доступность изменения только через SDK/перезапуск. Проверить интеграционным тестом: изменить файл, послать SIGHUP, открыть новое соединение и прочитать новую рекомендацию.

## 4. Маршрутизация и границы протоколов

| Путь | Реальное поведение | Оценка |
| --- | --- | --- |
| Plain / obfs / WS | Общий SOCKS5-core, общие pipeline whitelist и лимит соединений | Правильное направление архитектуры; F10 касается начального парсинга списка |
| TCP CONNECT | Destination rule проверяется до DNS, затем resolve и dial | Хорошо; исправить F12/F13 |
| UDP `0x03` | Первичная команда проверяется, назначения последующих датаграмм нет | F02/F03; не эквивалентен TCP по политике |
| UDP `0x83` | UDP внутри TCP, сокет выхода IPv4, собственное кадрирование | F02/F03/F04; поддержка IPv6-назначений требует отдельного теста |
| Client `ROUTE_DOMAINS` | Подходящие FQDN туннелируются, остальные отвергаются; literal IP при пустом `destFQDN` разрешен; UDP-проверка пропущена | Это фильтр доменов, а не полноценный split tunnel с прямым маршрутом; уточнить описание и политику IP/UDP |
| Client domain normalization | Lowercase и IDNA; завершающая точка не удаляется | `example.com.` и `example.com` могут дать разные решения; добавить тест |
| WS path | Upgrade на настроенном пути, прочие запросы в decoy | Концепция согласована; F16 касается разбора path |
| HTTP `/metrics`, `/health` | Собственный ServeMux, без неявного default mux | Хорошо; health всегда возвращает 200 и не является полной readiness-проверкой |
| SOCKS BIND | Явно возвращает command-not-supported | Живой отказной обработчик, не мертвый код |

Для DNS сейчас выбирается только `ips[0]`; fallback между адресами и Happy Eyeballs отсутствуют. Это подтвержденное свойство `internal/socks5/resolver.go`, но отказ на конкретном dual-stack production-маршруте не воспроизводился. Оптимизация должна сохранять правило проверки назначения до исходящего запроса.

Это не доказательство смысловой необходимости каждого экспортируемого поля конфигурации. Отдельных доказанных мертвых переменных для удаления нет.

### Файловая и документальная гигиена

- Локальные `bin/` занимают около 43 МиБ, `bench/` около 48 КиБ, присутствует `coverage.txt`. Все они игнорируются Git. `git ls-files -ci --exclude-standard` пуст: среди отслеживаемых файлов нет совпадающих с текущими ignore-правилами. Это локальные артефакты, не мусор коммита; удалять их без необходимости не требуется.
- `.dockerignore` отсутствует, а Dockerfile использует `COPY . .`. Локальные бинарники, профили, `.git` и будущие `.env` не исключаются из контекста Docker через `.gitignore`. Добавить отдельный `.dockerignore`; текущая утечка секретов в опубликованный образ не установлена.
- В `.gitignore` есть имена нескольких корневых диагностических бинарей, но нет `/fpcollect`. `go build ./cmd/fpcollect` оставит неигнорируемый файл. Либо единообразно собирать в `bin/`, либо дополнить правило.
- README занимает около 106 КБ, `CLAUDE.md` около 60 КБ. Много комментариев пересказывают прошлые задачи вместо текущего контракта. Выносить историю и результаты измерений в уже существующие `docs/design`/`docs/benchmarks`; в коде оставить инвариант и причину нетривиального решения.
- Есть устаревшие комментарии: `WSMinFrame` в `pkg/s5server/config.go` обещает default 512 при фактическом 256; `listenerPipeline.closeOnce` объясняется уже исправленным закрытием канала tlsdecoy; в `request.go` продублирован комментарий `readAddrSpec`.

- Рабочее дерево содержит много пользовательских незакоммиченных изменений, включая новые пакеты и перенесенные документы. Это состояние разработки, а не доказательство наличия мусора. Ничего из него аудит не удалял и не коммитил.

Приоритет оптимизации: сначала ограничить память F05/F06 и восстановить корректность учета F03. Затем профилировать конкретную нагрузку, а не заменять Gorilla, OTel или `encoding/json` по общему представлению о скорости. Связка OTel + Prometheus здесь имеет понятные роли: инструменты SDK, exporter и HTTP endpoint; сам факт наличия двух библиотек не доказывает дублирование.

`sync.Pool` не является ограничителем памяти: GC вправе очищать его. В проекте уже используются переиспользуемые буферы relay/UDP и тесты аллокаций obfs. Сохранять их полезнее, чем добавлять пулы во все функции. Для WS полная сборка сообщения и дополнительная копия являются конкретным источником мусора; для verifier подтверждены небольшие горячие аллокации, но их оптимизация вторична.

## 8. Покрытие и очередность исправлений

Общее покрытие 65,7% занижается диагностическими CLI с 0%, но это не причина игнорировать исполняемые входы: `cmd/s5core` имеет 21,0%, `cmd/s5client` 48,7%. У `pkg/s5server` 84,9%, `internal/socks5` 77,9%, `userstore` 84,4%, `session` 95,1%. При таком покрытии найденные ошибки находятся прежде всего на границах подсистем, а не в непокрытых простых ветках.

1. **Доступ и остановка:** F01-F04, F07/F08/F10. Проверки удаления/отзыва, каждого назначения UDP, квот без телеметрии и завершения сервера.
2. **Ресурсные ограничения:** F05/F06. Тесты больших сообщений и холодных проверок; контролируемая нагрузка с измерением heap/RSS.
3. **Релиз:** F09. Матрица до публикации; затем F16/F17 для корректного неуспешного запуска.
4. **Протокол и конфигурация:** F11-F15, F18/F19. Версионирование auth-flight, дедлайны DNS, строгие parser/regex, реальный источник reload.
5. **Очистка:** две мертвые функции, `.dockerignore`, единое место для бинарей, сокращение исторических комментариев. Обновления зависимостей делать отдельно от исправления поведения протокола.

Критерий приемки: штатные проверки плюс регрессии на каждую исправленную находку, включая запуск из отдельного SDK-потребителя и Windows build. Повышение процента покрытия само по себе не заменяет эти сценарии.

## 9. Воспроизводимость и материалы проверки

Основные команды для исходного дерева, с выводом артефактов вне репозитория:

```bash
go version
go mod verify
go mod tidy -diff
gofmt -s -l .
go vet ./...
go build ./...
golangci-lint run ./...
go test -race -count=1 -timeout=5m \
  -coverprofile=/tmp/s5core-audit-coverage.txt -covermode=atomic ./...
govulncheck -show verbose ./...
deadcode -test ./...
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./cmd/...
```

`golangci-lint` и `govulncheck` запущены из `$GOPATH/bin`, `deadcode` установлен отдельно во временный каталог. Исходные `go.mod` и `go.sum` не менялись.

Временный каталог проверки `/tmp/s5core-audit-20260920` содержит `tests.log`, `coverage.txt`, `lint.log`, `vuln-verbose.log`, `deadcode-all-tests.log`, `modules.json`, `cross-build.log`, `syntax.log`, `bench.log`, `bench-smoke.log`, `repro.log`, начальный Git status и SHA-256-манифест. Это локальные временные материалы, они не добавлены в Git и могут быть удалены системой. Сам отчет содержит результаты, условия воспроизведения и ссылки на исходные места независимо от сохранности `/tmp`.

Во временной копии добавлены только `audit_repro_test.go` в восьми пакетах. Полный повтор дополнительных проб:

```bash
cd /tmp/s5core-audit-20260920/repo
go test -race -count=1 -run '^TestAudit' -v -timeout=45s \
  ./cmd/s5client ./pkg/s5server ./internal/userstore ./internal/socks5 \
  ./internal/passwordhash ./internal/s5core \
  ./pkg/transport/tlsdecoy ./pkg/transport/ws
```

Эта команда применима именно к подготовленной временной копии: в исходном репозитории дополнительных проб нет. F19 подтвержден разбором пути конфигурации, F09 отдельной кросс-сборкой; остальные находки сопоставлены с перечисленными в тексте `TestAudit*`.

Перед добавлением отчета сравнены SHA-256 всех исходных файлов и Git status с начальным состоянием: изменений исходного дерева от аудита не обнаружено. Номера строк относятся к проверенной рабочей копии и могут сдвинуться после последующих правок.

Метод интерпретации `deadcode` сверялся с [официальным описанием Go](https://go.dev/blog/deadcode): недостижимость зависит от выбранных точек входа, поэтому запуск только для двух CLI не является основанием удалять API библиотеки. Контракты HTTP дополнительно сверены через `find-docs`/Context7 и официальную документацию, а детали Gorilla - с исходниками установленной версии 1.5.3.
