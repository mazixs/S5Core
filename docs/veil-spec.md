# Спецификация формата S5Veil

Задача плана Ф5-1. Этот документ - единственный источник истины по формату
провода. Реализация обеих сторон ведется по нему, а не по чтению чужого кода;
расхождение реализации и документа - это баг одного из двух, а не вопрос
вкуса.

**Статус:** описан формат версии **v1** - то, что работает сегодня, после
задач Ф4-2 - Ф4-5, Ф4-9, Ф5-2, Ф5-3 и Ф5-4. Точки, зарезервированные под
продолжение фазы 5, помечены явно: раздел 9 (правдоподобный префикс первого
кадра).

Формат несовместим со сборками до Ф5-3: пролог теперь содержит MAC над
часовой эпохой, а секрет сессии - саму эпоху. Обе стороны надо обновлять
вместе; порядок миграции - задача Ф5-7.

## 1. Соглашения

- Все многобайтовые целые - **big-endian** без знака.
- `A || B` - конкатенация. `A ^ B` - побайтовый XOR.
- Размеры в байтах. `X[i:j]` - полуинтервал, как в Go.
- Слово **ДОЛЖЕН** отмечает требование, нарушение которого делает реализацию
  несовместимой; **СЛЕДУЕТ** - рекомендацию, отступление от которой допустимо
  и должно быть обосновано.
- "Клиент" - сторона, инициировавшая TCP-соединение; "сервер" - принявшая.
  Роль ДОЛЖНА быть задана явно при создании соединения: стороны делят секрет
  и не должны делить пространство счетчиков.

## 2. Слои

```
приложение
  |  SOCKS5 (RFC 1928), включая команду 0x83 - раздел 10
обфускация S5Veil            <- этот документ, разделы 3-9
  |  кадры
транспорт                    <- TCP, либо WebSocket поверх TLS
```

Обфускация не знает, что лежит под ней: она работает поверх любого
`net.Conn`, доставляющего байты по порядку. Из этого следуют два правила:

- Сигналы уровня потока (конец полупотока, keepalive) ДОЛЖНЫ выражаться
  кадрами этого формата, а не средствами транспорта. У WebSocket нет
  полузакрытия, а его ping отличим по opcode и длине - см. `docs/design/half-close.md`.
- Транспорт не обязан сохранять границы записей. Приемник ДОЛЖЕН собирать
  кадр из произвольного числа чтений.

## 3. Сессия

### 3.1 Пролог

Клиент ДОЛЖЕН передать **32 байта** пролога **перед первым кадром**, в том же
сегменте, что и первый кадр. На проводе эти 32 байта представлены кодированным
открытием (раздел 3.5); все, что ниже в этом разделе, описывает их содержимое,
а не их представление.

Сервер пролога не шлет. Пролог один на соединение, и выбрал его клиент.

```
клиент -> сервер:  Prologue (32) || Frame_0 || Frame_1 || ...
сервер -> клиент:  Frame_0 || Frame_1 || ...
```

Что именно лежит в этих 32 байтах, определяет **схема аутентификации** (раздел
4.1). Формат знает о ней ровно две вещи: сколько байтов занимает пролог и как из
пролога получается секрет сессии. Все остальное - кадрирование, маска длины,
паддинг, управляющие кадры - от схемы не зависит и при ее замене не меняется.
Это требование задачи Ф5-2: выбор схемы сделан на измеренных основаниях
([gates/g4-first-frame.md](gates/g4-first-frame.md)), но он может оказаться
неверным, и цена ошибки не должна включать переделку формата.

Схема v1 - **симметричная с часовой привязкой** (раздел 3.2): 24 байта
случайных данных и 8 байт MAC над ними и текущим часом. Прямой секретности
она не дает (раздел 4.2). Ее вариант с реестром участников (раздел 3.4)
тратит 8 из этих 24 байтов на замаскированную идентичность и тем самым дает
серверу имя пользователя до первого кадра; для всего остального формата это
по-прежнему 32 байта пролога.

Требование "в том же сегменте" - не оптимизация, а свойство: у формата нет
отдельного рукопожатия, и клиент шлет полезную нагрузку в первом же сегменте
данных. Цена нарушения измерена: ответ сервера до полезной нагрузки добавляет
один круговой путь, 25% времени установки соединения
([gates/g4-first-frame.md](gates/g4-first-frame.md)).

### 3.2 Часовая эпоха

```
Epoch        = unix_time / 3600                          (целочисленно)
Random       = 24 случайных байта
Tag          = HMAC-SHA-256(PSK, "S5Core/veil v1 epoch" || Random ||
                                 uint64_BE(Epoch) || uint64_BE(len(Context)) || Context)
Prologue     = Random (24) || Tag[0:8]
Secret       = Prologue (32) || uint64_BE(Epoch)
```

`Context` - каноническая строка контекста из раздела 4.3, с явной длиной
перед ней, чтобы одну и ту же последовательность байтов нельзя было разбить
на части по-другому.

Клиент ДОЛЖЕН ставить свою текущую эпоху. Сервер ДОЛЖЕН перебрать эпохи
`E-W .. E+W`, где `E` - его собственная эпоха, а `W` - окно
(`DefaultEpochWindow`, по умолчанию **2**), и - если он принимает несколько
контекстов (раздел 4.3) - каждый из них, и взять ту пару, для которой MAC
сошелся. Перебор СЛЕДУЕТ вести от ближней эпохи к дальней и в заданном
порядке контекстов: у клиента с верными часами и текущим контекстом он стоит
один HMAC.

Если не сошлась ни одна, сервер ДОЛЖЕН продолжить так, как если бы сошлась
его собственная: вывести ключи из заведомо неверного секрета и отвергнуть
соединение там же, где отвергается неверный PSK (раздел 3.3). Отказ на
прологе давал бы измеримую разницу во времени между "чужой ключ" и "чужая
нагрузка".

**Почему час, а не секунда.** Все три варианта из блокера исходили из точной
метки времени. VMess с окном ±90 секунд превратил рассинхрон часов в поток
ошибок "invalid user", и в VLESS зависимость от времени убрали вовсе. Провал
там был не в идее часов, а в точности. Модель obfs4 - грубая эпоха плюс окно -
терпит расхождение в часах, а именно такое расхождение и бывает: роутер после
перезагрузки без синхронизации не знает времени вовсе, а NTP приходит через
секунды или минуты.

Окно 2, а не 1: сдвиг ровно в 2 часа смещает эпоху ровно на 2, а приемочный
критерий задачи Ф5-3 требует, чтобы такой клиент работал.

**Что это дает.** Записанный пролог перестает приниматься через
`2W+1` часов сам по себе, без всякой истории на сервере. История из
раздела 3.3 остается нужна внутри окна.

**Диагностика.** Сервер, не нашедший эпохи в окне, МОЖЕТ повторить поиск в
более широком диагностическом окне (по умолчанию 36 эпох) и сообщить о
рассинхроне в лог и в метрику `s5core_obfs_clock_skew_total`. На решение это
не влияет и на проводе не проявляется: соединение отвергается одинаково.
Диагностический поиск ДОЛЖЕН быть ограничен по частоте (не чаще раза в
секунду на слушатель), иначе неаутентифицированный пир покупает расширенный
поиск каждым соединением.

Клиент рассинхрон определить не может - сервер молчит намеренно. Поэтому
клиент, у которого рукопожатие оборвалось после успешного соединения,
ДОЛЖЕН назвать обе возможные причины (PSK и часы) в сообщении об ошибке.

### 3.3 Защита от повторов

Сервер ДОЛЖЕН вести историю виденных прологов (кольцевой буфер фиксированного
размера, `OBFS_REPLAY_WINDOW`, общий на все обфусцированные слушатели узла) и
отвергать соединение с уже виденным прологом.

Отказ ДОЛЖЕН выдаваться **не в момент разбора пролога, а после расшифровки
первого кадра** - там же, где выдается отказ по неверному тегу. Иначе повтор
записанного трафика получает ответ быстрее, чем неверный ключ, и активный
зонд измеряет эту разницу.

Вероятностные структуры (фильтр Блума) применять НЕ СЛЕДУЕТ: ложное
срабатывание рвет легитимное соединение.

### 3.4 Реестр участников

Схема с реестром - та же часовая схема, тот же час, тот же контекст и те же
32 байта на проводе, плюс идентичность, которую сервер разрешает за
постоянное время. Задача Ф5-5.

```
Epoch    = unix_time / 3600                          (целочисленно)
Random   = 16 случайных байтов
Tag      = HMAC-SHA-256(MemberKey, "S5Core/veil v1 user" || uint64_BE(Epoch))[0:8]
Mask     = HMAC-SHA-256(PSK, "S5Core/veil v1 identity" || Random ||
                             uint64_BE(Epoch))[0:8]
Identity = Tag XOR Mask
MAC      = HMAC-SHA-256(MemberKey, "S5Core/veil v1 epoch" || Random || Identity ||
                                   uint64_BE(Epoch) || uint64_BE(len(Context)) || Context)
Prologue = Random (16) || Identity (8) || MAC[0:8]
Secret   = Prologue (32) || uint64_BE(Epoch) || MemberKey
```

`MemberKey` ДОЛЖЕН быть ровно 32 байта и ДОЛЖЕН быть получен из генератора
случайных чисел, а не из пароля: на этом пути нет ни Argon2id, ни какой-либо
другой защиты от перебора по словарю.

Ключ участника входит в секрет сессии, поэтому два участника с одним PSK
выводят разные ключи данных и ни один не читает трафик другого. Это
отличается от схемы раздела 3.2, где ключи сессии определяются прологом и
PSK, то есть одинаковы для всех, кто знает PSK.

**Как сервер разрешает идентичность.** Для каждой эпохи окна он снимает маску
(один HMAC на эпоху, не на участника), получает `Tag` и ищет его в таблице
`Tag -> участник`. Таблица строится заранее, раз в эпоху, в фоне, и содержит
эпохи всего окна; поиск - одно чтение map. Затем сервер проверяет MAC ключом
найденного участника - по одному HMAC на принимаемый контекст. Итого работа
на соединение не зависит от числа участников; замеры - в
[benchmarks/roster.md](benchmarks/roster.md).

Сервер ДОЛЖЕН заранее готовить эпохи окна и по одной запасной эпохе с каждой
стороны, чтобы смена часа до очередного обновления не останавливала прием.
Запасные таблицы НЕ расширяют окно принятия пролога. Поиск, включая
диагностику рассинхронизации часов, НЕ ДОЛЖЕН создавать таблицы: иначе
неизвестный пролог вызывает работу и выделение памяти по числу участников.

`Directory.Run` обновляет снимок каждые 15 минут; встраивающее приложение
ДОЛЖНО запускать его либо вызывать `Refresh` самостоятельно. После большого
скачка системного времени за подготовленные эпохи участник не определяется
до `Refresh`. Диагностика Roster ограничена уже подготовленными эпохами;
произвольные 36 часов диагностического окна Clocked не создают новые таблицы.
Перестройка выполняется вне блокировки читателей, а готовые таблицы и список
участников публикуются вместе. `SetMembers` возвращается после публикации;
параллельный `Refresh` не должен возвращать отозванные ключи.

Столкновение двух участников в одной эпохе (вероятность `2^-64` на пару)
ДОЛЖНО обнаруживаться при построении таблицы, а не при соединении: оба
участника из столкнувшейся пары ДОЛЖНЫ быть отвергнуты и названы в логе.

**Когда участник не нашелся.** Сервер, у которого задан общий аккаунт,
ДОЛЖЕН продолжить по схеме раздела 3.2: это окно миграции, в котором клиенты
без собственного ключа продолжают работать (задача Ф5-7). Сервер без общего
аккаунта ДОЛЖЕН вывести ключи из секрета со **случайным ключом, выбранным
один раз при запуске**, и отвергнуть соединение там же, где отвергается
неверный PSK. Подставлять здесь пустой ключ НЕЛЬЗЯ: секрет тогда совпадет с
секретом схемы 3.2, и сервер примет любого клиента общего аккаунта, которого
как раз и не должно быть.

**Отзыв.** Участник, удаленный из реестра, перестает разрешаться при
следующей перестройке таблицы, которую перезагрузка списка учетных записей
(`SIGHUP`) выполняет немедленно. Установленные соединения это не разрывает -
их обрывают квоты и сроки действия, как и раньше.

**Что это дает.** Пароль уходит с горячего пути полностью: сервер знает, кто
звонит, до первого кадра, и отвечает на рукопожатие SOCKS5 методом "без
аутентификации", называя сессии имя, полученное из туннеля. Argon2id
остается там, где он уместен - вход в панель управления.

**Чего это не скрывает.** Тот, кто держит PSK развертывания - то есть любой
участник, - может снять маску с поля `Identity` чужого соединения и понять,
какому участнику оно принадлежит. Участники не анонимны друг для друга. Они
уже делят PSK, которым держится невидимость всего развертывания, и разделение
этих двух секретов стоило бы второго поля на проводе.

### 3.5 Открытие: пролог на проводе

Пролог из 32 байт (разделы 3.1-3.4) - это то, что **получает схема**. На
провод он уходит закодированным, и вместе с добивкой образует **открытие**
соединения.

```
Opening      = base64(Prologue)           43 символа, алфавит A-Za-z0-9+/
               || Pad                     0..20 символов того же алфавита
клиент -> сервер:  Opening (43..63) || Frame_0 || Frame_1 || ...
```

Открытие предшествует **первому кадру любого вида**: данные, `hello`,
keepalive или FIN - какой бы кадр ни ушел первым, перед ним стоит открытие в
той кодировке, которую выбрал отправитель. Сторона, закрывшая свою половину до
первой записи, не исключение: ее FIN - первый кадр, и открытие перед ним то
же самое. Иначе получатель не вывел бы ключи, а на проводе появилась бы вторая
форма открытия, которая встречается тем реже, чем реже соединение закрывается
молча, - то есть заметная (ревью R04).

Кодирование - **RawStdEncoding** (стандартный алфавит, без символа `=`:
заполнитель был бы константой на фиксированном смещении). 43 символа несут
258 бит, пролог - 256, поэтому два младших бита последнего символа не значат
ничего; отправитель ДОЛЖЕН заполнить их случайно, иначе последний символ
принимает лишь 16 значений из 64 на каждом соединении. Получатель их
игнорирует.

```
PadLen       = uint16_BE(HKDF-Expand(PRK, "S5Core/obfs v1 client opening", 2)) mod 21
```

где `PRK` - тот же `HKDF-Extract(PSK, Secret)`, что и в разделе 4.1. Добивка -
случайные символы того же алфавита. Обе стороны выводят `PadLen` из секрета
сессии, поэтому на проводе его нет, а наблюдатель без PSK не знает, где
кончается открытие и начинается первый кадр.

**Зачем.** Пролог по построению неотличим от случайных байтов, и правило
уровня 1 чек-листа (`internal/stealth`) блокирует именно это: первый пакет,
похожий на полностью зашифрованный, если он не попадает ни под одно из пяти
исключений. Закодированное открытие попадает под Ex2 (первые шесть байт
печатаемые) и Ex4 (печатаемая серия длиннее двадцати байт). Это измерено на
живом пути, а не выведено: первый пакет из 256 случайных байт доставлялся в
20% проб, тот же пакет с 16 печатаемыми байтами впереди - в 98 пробах из 98
([field/stealth.md](field/stealth.md)).

**Почему не префикс известного протокола.** Пять байт заголовка TLS-записи
дают тот же результат на том же пути (93 пробы из 93) и стоят дешевле. Но они
заявляют протокол, которого соединение не говорит: зонд, пославший вслед
настоящий `ClientHello`, ждет `ServerHello` и не получает ничего, а молчание
после заявленного TLS - отличие, которого без заявления не было. Печатаемое
открытие не обещает ничего и не создает такого отличия. Там, где нужен
настоящий TLS, он есть - транспорт WSS (раздел 2).

**Сколько это пакетов - не часть формата.** Открытие и кадры за ним
отправитель МОЖЕТ положить в одну запись в транспорт или в две: получатель
читает поток и границы записей не видит. По умолчанию запись одна, потому что
отдельный короткий пакет в начале каждого соединения - постоянная форма.
Отправитель, которому нужно исключение по длине первого пакета (фильтр,
классифицирующий только пакеты от 100 байт, `docs/field/stealth.md`),
включает `OBFS_SPLIT_OPENING`, и тогда открытие уходит своим пакетом. Кругов
это не добавляет ни в одном из двух случаев: запись не ждет ответа.

**Переменная длина обязательна.** Открытие фиксированной длины вернуло бы
кадрам постоянные смещения: наблюдатель отсчитал бы 43 байта и получил
выравнивание всего потока даром. Поэтому `PadLen` выводится из секрета, а
проверка `pkg/obfs/demo_test.go` требует, чтобы на корпусе в 1000 соединений
встречалось не менее 15 разных длин открытия.

**Совместимость.** Сервер принимает оба представления и различает их по
первым 32 байтам: сырой пролог - равномерно случайные байты и попадает целиком
в 64-символьный алфавит с вероятностью 2^-64, поэтому печатаемое начало
означает кодированное открытие, а не совпадение. Отправитель выбирает
представление настройкой (`OBFS_PROLOGUE`, по умолчанию `printable`; `s5client`
с 2.2 сырое не отправляет), и это единственная часть формата, о которой две
стороны могут не договариваться.
Порядок обновления флота отсюда прямой: сервер первым, клиенты следом
([field/migration.md](field/migration.md)).

**Цена.** 11 байт кодирования плюс 0-20 байт добивки на соединение, один
вызов HKDF-Expand на каждой стороне. Кругов не добавляется: открытие уходит в
том же сегменте, что и первый кадр, как того требует раздел 3.1.

## 4. Вывод ключей

### 4.1 Схема

```
Secret       = Scheme.Accept(PSK, Prologue)     // часовая схема: = Prologue || Epoch (раздел 3.2)
PRK          = HKDF-Extract(SHA-256, salt = Secret, ikm = PSK)
K_data_c2s   = HKDF-Expand(SHA-256, PRK, "S5Core/obfs v1 client data",   32)
K_data_s2c   = HKDF-Expand(SHA-256, PRK, "S5Core/obfs v1 server data",   32)
K_len_c2s    = HKDF-Expand(SHA-256, PRK, "S5Core/obfs v1 client length", 32)
K_len_s2c    = HKDF-Expand(SHA-256, PRK, "S5Core/obfs v1 server length", 32)
```

`PSK` ДОЛЖЕН быть ровно 32 байта. Напрямую ключом шифрования он не
используется никогда.

Каждое направление получает **свой** ключ данных и **свой** ключ маски длины.
Ключ маски отделен от ключа данных намеренно: байты, скрывающие границу
кадра, не должны быть тем же шифром, который защищает содержимое.

### 4.2 Чего схема не дает

Прямой секретности нет. Пролог симметричной схемы лежит на проводе, ключи
выводятся из него и из PSK, поэтому компрометация PSK раскрывает весь ранее
записанный трафик. Это свойство схемы, а не формата: схема с обменом ключами
закрывает его, не меняя ничего в разделах 5-10. Это известный и измеренный
долг, решение по нему - в [gates/g4-first-frame.md](gates/g4-first-frame.md).

### 4.3 Контекст: версия формата, шифр и идентификатор узла

Контекст - тройка `(Version, Cipher, NodeID)`. Каноническая запись:

```
Context = Version
          || " cipher " || Cipher     если Cipher задан и не равен "aes"
          || " node "   || NodeID     если NodeID не пуст
Version по умолчанию = "v1"
Cipher  по умолчанию = "aes"
```

Значение по умолчанию не пишется вовсе: развертывание, которое не знало про
шифры, выводит ровно те метки, что перечислены в разделе 4.1.

Контекст входит в два места и ни в одно из них на проводе:

1. **В MAC пролога** (раздел 3.2) - длиной, затем строкой. Поэтому сервер
   узнает контекст клиента **до** вывода ключей, за одну операцию HMAC, а не
   за вторую попытку расшифровки.
2. **В метки HKDF** - суффиксами ` cipher <имя>` и ` node <id>` (раздел 4.1).
   Поэтому ключи двух узлов не совпадают даже при одинаковом прологе.

**Версия.** Явная версия на проводе - сама по себе детектируемая константа, и
урок TLS 1.3, который не смог воспользоваться собственным полем версии из-за
окостенения промежуточных узлов, здесь прямой. Сервер МОЖЕТ принимать
несколько контекстов (`Accepts`), перебирая их в заданном порядке; цена -
одна операция HMAC на каждый дополнительный контекст, и только на соединение,
которое не опозналось с первого. Это и есть окно миграции: сервер объявляет
новый контекст своим и продолжает принимать старый, пока клиенты в поле не
обновятся (Ф5-7).

**Шифр.** `Cipher` выбирает пару "AEAD + маска длины" (раздел 5.0). Выбирает
его клиент - по тому, что умеет его собственный процессор; сервер принимает
оба варианта и узнает выбор из MAC пролога за один HMAC. На проводе выбора
нет, и по размерам его не видно: у обоих шифров ключ 32 байта, nonce 12 байт
и тег 16 байт, так что форма кадра одинакова. Замеры - в
[benchmarks/ciphers.md](benchmarks/ciphers.md).

**Узел.** `NodeID` делает пролог, выпущенный для узла A, невалидным на узле B.
Следствие: распределенный кеш повторов не нужен - записанное соединение не
переносится между узлами, и локальной истории раздела 3.3 достаточно.

Пустой `NodeID` - это тоже идентичность, а не отсутствие проверки: клиент с
непустым идентификатором на сервере без идентификатора не проходит, и
наоборот.

**Цена решения.** Anycast и прозрачный перенос клиента с узла на узел без
правки его конфигурации становятся недоступны. Размен осознанный:
горизонтальное масштабирование в обмен на отсутствие сетевого запроса в
критическом пути установки соединения.

Расхождение контекста не обсуждается на проводе и проявляется как неверный
ключ - отказ приходит там же и выглядит так же, как отказ мусору.

## 5. Кадр

```
[ MaskedLen (2) ][ Ciphertext (MaskedLen ^ mask байт) ]
```

На проводе у кадра нет ни одного поля, которое читается без ключа: длина
маскирована, nonce не передается вовсе.

### 5.0 Шифры

Кадр шифруется одной из двух пар. Какая именно - определяет `Cipher` в
контексте (раздел 4.3), одинаково для обоих направлений соединения.

| `Cipher` | AEAD | Маска длины |
|---|---|---|
| `aes` (по умолчанию) | AES-256-GCM | AES-256-ECB над счетчиком |
| `chacha` | ChaCha20-Poly1305 | keystream ChaCha20 |

Размеры у пар совпадают: ключ 32 байта, nonce 12 байт, тег 16 байт. Кадр из
раздела 5.3 и накладные расходы `23` байта от выбора не зависят.

Выбирает клиент, и выбирает по железу: на замеренном ARM-роутере AES-256-GCM
быстрее ChaCha20 в 3,4 раза там, где есть аппаратные инструкции AES, и в
5,9 раза медленнее там, где их нет. Сервер принимает оба. Числа - в
[benchmarks/ciphers.md](benchmarks/ciphers.md) и
[benchmarks/arm-router.md](benchmarks/arm-router.md).

### 5.1 Маска длины

```
MaskedLen = uint16(len(Ciphertext)) ^ mask(counter)

Cipher = "aes":
  mask(counter)  = первые 2 байта AES-256-ECB(K_len_dir, block(counter))
  block(counter) = 8 нулевых байтов || uint64_BE(counter)     (16 байт)

Cipher = "chacha":
  mask(counter) = 2 байта keystream ChaCha20(K_len_dir, nonce_len(counter))
                  со смещения (counter mod 32) * 2 внутри блока
  блок keystream = counter / 32, младшие 32 бита в счетчик блока ChaCha20
  nonce_len(counter) = 4 нулевых байта || uint64_BE(counter / 32 >> 32)
```

`counter` - номер кадра в этом направлении, начиная с 0. Маска и nonce берут
один и тот же счетчик, но разные ключи и разные конструкции.

Блок ChaCha20 - 64 байта, то есть 32 маски: реализация считает его один раз
на 32 кадра. Это не свойство провода, а причина, по которой маска ChaCha
стоит дешевле маски AES даже там, где AES аппаратный.

### 5.2 Шифрование

```
Ciphertext = AEAD.Seal(K_data_dir, nonce(counter), Plaintext, aad = пусто)
nonce(counter) = 4 нулевых байта || uint64_BE(counter)      (12 байт)
AEAD = AES-256-GCM при Cipher = "aes", ChaCha20-Poly1305 при Cipher = "chacha"
```

Счетчик ДОЛЖЕН увеличиваться на единицу на каждый отправленный кадр этого
направления, включая keepalive и FIN. Повтор nonce внутри направления
невозможен по построению; случайный nonce не используется - он стоил 12 байт
на кадр и добавлял границу дня рождения при долгоживущем PSK.

### 5.3 Открытый текст

```
[ Kind (1) ][ PayloadLen (2) ][ Payload (PayloadLen) ][ PadLen (2) ][ Padding (PadLen) ]
```

Накладные расходы кадра: `2 + 1 + 2 + 2 + 16 = 23` байта на проводе.
Минимальный шифротекст: `1 + 2 + 2 + 16 = 21` байт.

### 5.4 Типы кадров

| Kind | Имя | Payload | Смысл |
|---|---|---|---|
| `0x00` | data | данные потока | обычный кадр |
| `0x01` | keepalive | пуст | путь удерживается открытым, читателю ничего не отдается |
| `0x02` | FIN | пуст | отправитель закрыл свою половину |
| `0x03` | hello | TLV, см. 8.3 | клиент называет свою сборку и транспорт; читателю не отдается |
| `0x04` | advice | TLV, см. 8.4 | сервер рекомендует транспорт и форму трафика; читателю не отдается |

Тип лежит **внутри** AEAD, поэтому на проводе кадр любого типа - кадр обычной
длины и обычного вида.

Приемник, встретивший неизвестный `Kind`, ДОЛЖЕН разорвать соединение с
причиной `unknown_frame_kind`. Кадр аутентичен, значит его послал носитель
PSK - версия формата, знающая тип, который эта не знает; угадывать нельзя,
неизвестный тип может нести полезную нагрузку с другим смыслом.

## 6. Правила паддинга

- Длина паддинга выбирается **на каждый кадр** равномерно из
  `[0, min(OBFS_MAX_PADDING, budget/2)]`, где
  `budget = MTU - 23`, ограниченный сверху 65535 минус служебные поля.
  Ограничение половиной бюджета не дает большому `OBFS_MAX_PADDING` сжать
  полезную нагрузку до единиц байтов.
- Паддинг ДОЛЖЕН быть **нулевым**, а не случайным. Он лежит внутри AEAD,
  поэтому на проводе в обоих случаях шифротекст, отличить их извне нельзя, а
  единственный, кто видит эти байты, - пир с ключом, который их отбрасывает.
  Так же поступает TLS 1.3 (RFC 8446, 5.4). Заодно это снимает вызов
  `getrandom` с горячего пути, который на сегментированной записи становится
  двадцатью вызовами вместо одного.
- `OBFS_MAX_PADDING` - настройка **отправителя**. Приемник берет длину
  полезной нагрузки из расшифрованного заголовка и поле `PadLen` использует
  только для проверки границ. Совпадение значения на двух сторонах не
  требуется.

## 7. Сегментация и пределы

- Запись любого размера ДОЛЖНА резаться на кадры, ни один из которых не
  превышает `OBFS_MTU` байт на проводе. `OBFS_MTU` ограничивает эту сторону;
  приемник ДОЛЖЕН принимать кадр любой длины, укладывающейся в 16 бит
  (максимум `2 + 65535 = 65537` байт на проводе), потому что у пира MTU может
  быть другим.
- `OBFS_MTU` ДОЛЖЕН превышать 23 байта, иначе на полезную нагрузку не
  остается места.
- Кадры СЛЕДУЕТ отправлять пачками (реализация: 16 кадров или 32 КиБ, что
  меньше), иначе сегментация превращает один системный вызов в двадцать.
- Приемник, получивший `MaskedLen`, который после снятия маски меньше 21,
  ДОЛЖЕН разорвать соединение с причиной `short_frame`. Это самое дешевое
  место, где виден сканер портов.

## 8. Управляющие кадры

### 8.1 Keepalive

Клиент, молчавший дольше случайно выбранного интервала, ДОЛЖЕН отправить
кадр типа `keepalive`. Три правила делают его неотличимым:

1. Интервал рисуется **заново** из `[KEEPALIVE_MIN, KEEPALIVE_MAX]` перед
   каждым кадром, из криптографического источника случайности. Постоянный
   период - сам по себе сигнатура.
2. Реальный трафик **подавляет** кадр: он уходит, только если соединение
   молчало весь интервал.
3. Длина кадра копируется с одного из последних 16 кадров, реально
   отправленных этим соединением; если их еще не было - выбирается случайно
   в пределах бюджета.

Значения по умолчанию - 10-20 с - выбраны по измерению, а не по публикациям:
самый короткий таймаут простоя на пути оказался собственным `READ_TIMEOUT`
сервера (30 с). Таблица измерений - в README, раздел Keepalive.

Серверу keepalive НЕ СЛЕДУЕТ включать по умолчанию: одной стороны,
удерживающей путь, достаточно.

### 8.2 FIN и полузакрытие

`CloseWrite` ДОЛЖЕН отправлять кадр типа `FIN` и **не** трогать транспорт под
собой. После этого:

- отправитель ДОЛЖЕН отвергать дальнейшие `Write` с ошибкой;
- получатель ДОЛЖЕН отдать читателю `io.EOF` и продолжать принимать от него
  запись в обратном направлении;
- кадры, пришедшие после FIN (например, keepalive пира), читателю не
  отдаются.

Клиент, не написавший ни байта, но закрывающий свою половину, ДОЛЖЕН все
равно отправить пролог: без нее пир не выведет ключи, которыми запечатан FIN.

Обоснование и цена - `docs/design/half-close.md`.

### 8.3 Hello: кто подключился

Клиент, у которого настроено представление, ДОЛЖЕН отправить один кадр
типа `hello` **впереди первого кадра данных и в той же записи** в транспорт,
что и первый кадр данных. Кадр не стоит ни круга, ни отдельного пакета -
первый пакет клиента остается "кадры одной записью", как измерено в
`docs/gates/g4-first-frame.md`. Уходит ли в той же записи открытие, решает отправитель
(раздел 3.5): на hello это не влияет, он в любом случае едет вместе с
кадрами данных.

Payload - последовательность TLV: `[Type 1B][Len 1B][Value Len B]`. Типы
пространства `hello`:

| Type | Значение | Смысл |
|---|---|---|
| `0x01` | строка до 32 байт | версия сборки клиента (`internal/buildinfo`) |
| `0x02` | строка до 32 байт | транспорт, на котором клиент считает себя: `obfs` или `ws` |

Пустое поле не передается. Строка длиннее 32 байт обрезается отправителем.
Весь payload не длиннее 255 байт и ДОЛЖЕН помещаться в один кадр при MTU
отправителя, иначе соединение не создается (ошибка конфигурации, не провода).

Приемник ДОЛЖЕН пропускать TLV неизвестного типа - так добавляется поле без
нового типа кадра. Приемник ДОЛЖЕН доставить только первый `hello` на
соединении; повторы отбрасываются, чтобы пир не управлял счетчиком. Кадр
`hello`, пришедший к клиенту, отбрасывается без ошибки.

Сервер использует поле транспорта как мнение клиента: какой слушатель
принял соединение, он знает сам. Метка транспорта в метрике - от слушателя.

### 8.4 Advice: какой транспорт использовать дальше

Сервер, у которого настроена рекомендация, ДОЛЖЕН отправить один кадр типа
`advice` **впереди первого кадра данных, который он пишет, и в той же
записи** - то есть вместе с ответом на приветствие SOCKS5. Сервер не говорит
первым: кадр ждет первой записи, как и любой кадр этого направления.

Payload - TLV того же вида. Типы пространства `advice`:

| Type | Значение | Смысл |
|---|---|---|
| `0x01` | строка до 32 байт | рекомендуемый транспорт: `obfs` или `ws` |
| `0x02` | uint16 BE | `WS_MIN_FRAME` для клиента |
| `0x03` | uint16 BE | `WS_MAX_FRAME` для клиента |
| `0x04` | uint16 BE | `WS_MAX_JITTER_MS` для клиента |
| `0x05` | uint16 BE | `OBFS_MAX_PADDING` для клиента |
| `0x06` | uint16 BE, секунды | `KEEPALIVE_MIN` для клиента |
| `0x07` | uint16 BE, секунды | `KEEPALIVE_MAX` для клиента |

Нулевое поле не передается и при разборе остается нулем - "мнения нет".
Числовое поле не той ширины - ошибка `bad_control_frame`: пир, согласный в
типе, но не в ширине, - пир, за которым эта сборка не пойдет.

Все перечисленные поля - настройки **отправляющей** стороны у клиента
(раздел 12), поэтому сервер раздает их, ничего не меняя у себя, и клиент
может применить любое из них, не ломая совместимость. Применяет он их к
**следующим** соединениям, не к текущему.

Это рекомендация, не команда. Что клиент с ней делает - политика клиента:
оператор мог закрепить транспорт (`TRANSPORT=obfs|ws`), у клиента может не
быть настройки для рекомендованного транспорта (`WS_URL`), или он только
что видел его отказ. Обязательство формата одно: кадр аутентифицирован
сессионными ключами, поэтому подделать рекомендацию может только носитель
PSK - тот, кто и так читает туннель. Кадр `advice`, пришедший к серверу,
отбрасывается без ошибки; доставляется только первый на соединении.

Зачем это в формате, а не в отдельном канале: клиенты стоят на роутерах и
обновляются вручную (план, Ф5-7). Смена транспорта у такого клиента без
замены бинарника возможна только если сервер может ее попросить, а канал,
по которому он просит, уже аутентифицирован. Второго такого канала нет.

## 9. Первый кадр

### 9.1 Состояние v1

Первый кадр клиента - обычный кадр данных, которому предшествует пролог.
Аутентификация клиента выполняется **внутри** туннеля, средствами SOCKS5
(RFC 1928 и RFC 1929), а не форматом кадра. Знание PSK - единственное, что
проверяет формат, и проверяет он его тегом AEAD первого кадра.

Первый пакет соединения попадает под исключение политики блокировки полностью
зашифрованного трафика за счет кодированного открытия (раздел 3.5): на корпусе в
1000 соединений блокируется 0% против 98,9% до его появления. История вопроса и
решение шлюза - [gates/g3-wire-format.md](gates/g3-wire-format.md), полевая
проверка - [field/stealth.md](field/stealth.md).

### 9.2 Зарезервировано под фазу 5

Блок аутентификации первого кадра ДОЛЖЕН быть отдельной секцией формата с
явной границей: схема аутентификации заменяется без переделки остального
формата. Это единственное, что защищает от ошибки в выборе схемы.

Требования к будущей схеме, вытекающие из уже принятых решений:

- клиент шлет полезную нагрузку в первом же сегменте (раздел 3.1);
- метка версии - контекстная строка HKDF, а не байт на проводе (раздел 4.3);
- идентификатор узла входит в вывод ключей (раздел 4.3);
- выход схемы проходит проверки уровней 1 и 2 чек-листа стелса
  (`internal/stealth`), включая правило Ex1: поток, слишком близкий к
  идеально случайному, блокируется так же, как открытый текст.

Выбранная схема - симметричная, вариант Б шлюза G4
([gates/g4-first-frame.md](gates/g4-first-frame.md)).

## 10. UDP внутри туннеля: команда `0x83`

До этого документа формат был продублирован в `internal/socks5/associate.go`,
`cmd/s5client/udp_client.go` и тестах, и не описан нигде.

### 10.1 Зачем

RFC 1928 задает для UDP команду ASSOCIATE (`0x03`), которая переносит
датаграммы по отдельному UDP-сокету. Отдельный сокет - это утечка: WebRTC,
QUIC и DNS уходят мимо туннеля. Команда `0x83` мультиплексирует все UDP-потоки
сессии в то же TCP-соединение.

Клиент ДОЛЖЕН переписывать байт команды `0x03` на `0x83` при проксировании
запроса приложения. Цена решения измерена: `docs/benchmarks/udp-over-tcp.md`.

### 10.2 Установление

1. Приложение шлет клиенту обычный `UDP ASSOCIATE` (`0x03`).
2. Клиент открывает туннель и шлет серверу тот же запрос с командой `0x83`.
3. Сервер поднимает несвязанный UDP-сокет и отвечает обычным ответом SOCKS5.
   `BND.ADDR`/`BND.PORT` в ответе ДОЛЖНЫ быть `0.0.0.0:0`: трафик идет по TCP,
   и адрес не значит ничего.
4. Клиент открывает **локальный** UDP-сокет для приложения и отвечает ему
   обычным ответом SOCKS5 с адресом этого сокета.
5. Соединение перестает быть запросом и становится туннелем. Таймаут простоя
   к нему ДОЛЖЕН быть снят: туннель простаивает всегда, когда приложению
   нечего слать.

### 10.3 Кадрирование

Внутри туннеля каждая датаграмма переносится так:

```
[ Length (2) ][ SOCKS5 UDP request header || Payload ]
```

`Length` - длина всего, что за ней, включая заголовок SOCKS5.
`Length == 0` - keepalive, ДОЛЖЕН игнорироваться приемником.

Датаграмма вместе с заголовком ДОЛЖНА укладываться в 65535 байт. Запас здесь
узкий и его стоит знать: максимальная полезная нагрузка UDP - 65507 байт, а
заголовок с адресом IPv6 занимает 22, что дает 65529. Кадр с именем вместо
адреса в обратном направлении не встречается - сервер всегда ставит туда
адрес источника.

Заголовок - обычный заголовок UDP-запроса SOCKS5 (RFC 1928, 7):

```
[ RSV (2) = 0x0000 ][ FRAG (1) ][ ATYP (1) ][ ADDR (переменно) ][ PORT (2) ]
```

- `RSV` ДОЛЖЕН быть нулевым; приемник ДОЛЖЕН отвергать кадр с ненулевым.
- `FRAG` не поддерживается. Отправитель ДОЛЖЕН слать `0x00`; приемник
  ДОЛЖЕН отбрасывать датаграмму с любым другим значением (RFC 1928, 7).
  Прежняя редакция требовала обратного - трактовать любое значение как
  единичный пакет, - и это было неверно: сборки фрагментов здесь нет, а
  пересылка куска датаграммы отдает цели часть сообщения под видом целого.
  Отказ делает видимым то, что и так происходит, только раньше это выглядело
  как испорченный ответ цели, а теперь - как таймаут у клиента (F18).
- `ATYP`: `0x01` - IPv4 (4 байта), `0x03` - имя (1 байт длины + имя),
  `0x04` - IPv6 (16 байт).

### 10.4 Направления

**Приложение → интернет.** Клиент проверяет, что датаграмма пришла с того же
IP, что и управляющее TCP-соединение (иначе отбрасывает), и пересылает ее
**целиком, как есть** - приложение уже поставило заголовок SOCKS5. Сервер
разбирает заголовок, при `ATYP = 0x03` разрешает имя, и шлет `Payload`
нативным UDP.

**Интернет → приложение.** Сервер строит заголовок SOCKS5 с адресом
**источника** датаграммы и шлет `header || payload` в туннель. Клиент
пересылает полученное приложению целиком: заголовок нужен приложению, чтобы
понять, от кого пакет.

### 10.5 Ограничения

- Одно управляющее TCP-соединение - одна UDP-сессия. Мультиплексирование
  разных потоков идет по адресу в заголовке каждой датаграммы, отдельных
  идентификаторов потоков в формате нет.
- Порядок доставки - порядок TCP. Потерянный сегмент задерживает все
  мультиплексированные потоки до повторной передачи; измеренная цена - в
  `docs/benchmarks/udp-over-tcp.md`.
- Клиент запоминает адрес последней датаграммы приложения и шлет ответы туда.
  До первой датаграммы от приложения обратные пакеты отбрасываются: адрес
  неизвестен.

## 11. Ошибки

Причина отказа ДОЛЖНА различаться в телеметрии, но НЕ ДОЛЖНА различаться на
проводе: во всех случаях сервер не отвечает ничего, и время до закрытия не
должно зависеть от причины.

Сервер, не аутентифицировавший соединение, НЕ ДОЛЖЕН закрывать его сам
(задача Ф5-6). Он ДОЛЖЕН дочитывать и выбрасывать приходящие байты, пока
соединение не закроет бюджет рукопожатия - тот же, что закрывает пира,
подключившегося и ничего не отправившего. Иначе полностью собранный кадр с
неверным тегом закрывается мгновенно, а случайные байты, обещавшие длину
кадра, висят до таймаута, и разница между этими двумя временами отвечает
зонду на вопрос, разбираются ли здесь его байты. Подробности и цена -
[design/decoy.md](design/decoy.md).

| Причина | Когда |
|---|---|
| `eof_before_frame` | поток кончился до того, как кадр собрался |
| `short_frame` | снятая маской длина меньше 21, либо открытый текст короче заголовка |
| `decrypt_fail` | тег AEAD не сошелся: чужой PSK, порча, сканер |
| `replay` | пролог уже встречался (проверяется после расшифровки, см. 3.3) |
| `bad_opening` | открытие прочитано целиком, но сессия из него не вывелась: схема отвергла пролог либо не вывелись ключи или добивка (см. 3.1, 3.5) |
| `unknown_frame_kind` | тип кадра не принадлежит этой версии формата |
| `bad_control_frame` | кадр `hello`/`advice` аутентичен, но его TLV не разбирается: обрыв внутри поля, числовое поле не той ширины, payload длиннее 255 (см. 8.3, 8.4) |

| Параметр | Сторона | Обязан совпадать | Значение по умолчанию |
|---|---|---|---|
| `OBFS_PSK` | обе | **да**, ровно 32 байта | нет |
| `OBFS_MTU` | своя | нет | 1400 |
| `OBFS_MAX_PADDING` | отправителя | нет | 256 |
| `OBFS_REPLAY_WINDOW` | сервера | нет | 10000 |
| окно эпох `W` | сервера | нет | 2 (терпимость ±2 часа) |
| `OBFS_CIPHER` | клиента | нет, сервер принимает оба | по процессору: `aes` при аппаратном AES, иначе `chacha` |
| `OBFS_MEMBER_ID` / `OBFS_MEMBER_KEY` | клиента | ключ обязан быть в реестре сервера | пусто (общий аккаунт) |
| `tunnel_key` в `USERS_FILE` | сервера | см. выше, 32 байта в base64 | пусто (у аккаунта нет ключа) |
| `OBFS_REQUIRE_MEMBER_KEY` | сервера | нет | `false` (общий аккаунт еще принимается) |
| `OBFS_NODE_ID` | обе | **да**, если задан | пусто (узел без идентичности) |
| `OBFS_ACCEPT_NODE_IDS` | сервера | нет | пусто (только собственный) |
| диагностическое окно | сервера | нет | 36 эпох, не чаще раза в секунду |
| `KEEPALIVE_MIN` / `KEEPALIVE_MAX` | клиента | нет | 10 с / 20 с |
| `TRANSPORT` | клиента | нет | `auto`: `ws` при заданном `WS_URL`, иначе `obfs`, с учетом рекомендации сервера (8.4) и отказов |
| `TRANSPORT_ADVICE` | сервера | нет, клиент проверяет форму сам | пусто (кадр `advice` не посылается) |
| `OBFS_PROLOGUE` | клиента | нет, сервер узнает кодировку сам (3.5) | `printable`: пролог уходит в base64 с добивкой; `raw` (прежний провод) сервер принимает, клиент с 2.2 не отправляет |
| `OBFS_FORMAT` | клиента | нет, сервер принимает только текущий формат | `auto` и `v1` - текущий формат, `legacy` с 2.2 - ошибка старта ([field/migration.md](field/migration.md)) |
