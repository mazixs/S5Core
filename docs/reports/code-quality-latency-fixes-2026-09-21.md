# Исправления аудита задержек и бенчмарков S5Core

Дата: 2026-09-21. Локальные изменения относительно `112c4ffdd2ee941b6987f122fde6aa5235861c88`.
Исходные находки и воспроизведения: [аудит](code-quality-latency-audit-2026-09-21.md).
Все девять находок обработаны. Изменения не закоммичены и не опубликованы;
пользовательский `docs/field/nodes.md` не редактировался.

## Что исправлено

| Находка | Изменение | Проверка |
| --- | --- | --- |
| F01: неизвестный пролог строит таблицы пользователей | `Directory.lookup` только читает подготовленный снимок; диагностика не расширяет реестр. | Неизвестные прологи не увеличивают число эпох; часы вне подготовленного окна требуют `Refresh`. |
| F02: дедлайн ждет заблокированный WS Write | Отдельный mutex дедлайна и переиспользуемый таймер прерывают активную запись. Gorilla больше не получает конкурентные изменения своего поля deadline. | Запись в `net.Pipe` без читающего получателя прерывается; перенос и очистка дедлайна проверены под `-race`. |
| F03: Close зависает на служебном кадре | `Close` сразу закрывает транспорт, не отправляя предварительный WebSocket Close frame. | Закрытие соединения с молчащим получателем завершается. |
| F04: Refresh блокирует подключения | Таблицы строятся вне mutex читателей, обновления сериализованы отдельным mutex. Публикуется готовый снимок; ключи копируются. | Конкурентные Refresh/SetMembers не возвращают отозванных участников; добавлен совместный benchmark поиска и перестройки. |
| F05: аллокации метрик каждого кадра | Наборы атрибутов и variadic options для конечного набора переходов создаются заранее. | Настоящий SDK: 0 аллокаций на переход, существующие проверки значений метрик сохранены. |
| F06: ложный успех измерителей | `wirebench` проверяет HTTP 200, длину download, счетчик upload, реально прочитанный источник и частичные отказы. `connlat` также возвращает ошибку при частичном отказе. Скрипт проверяет все четыре пути и возвращает ненулевой код при любой ошибке. | 503, короткий/длинный ответ, неверный счетчик, раннее ложное подтверждение, частичный отказ. |
| F07: EndToEnd меряет только Write | Receiver проверяет payload и отправляет ACK на каждую операцию; RoundTrip проверяет полное эхо. WS throughput дожидается точного объема и проверяет ошибку приемника. | Все benchmarks проходят smoke-прогон. Названия и комментарии отделяют локальный Write от подтвержденной доставки. |
| F08: DNS тормозит UDP-пакеты | Асинхронные ограниченные запросы, объединение одного имени, кеш на ассоциацию; IP-пакеты идут напрямую. Учет сериализован, правила проверяются до DNS. | Оба реальных UDP handler передают IP-эхо, пока DNS заблокирован; отмена, порядок, кеш, истечение и границы очереди проверены. |
| F09: Accept крутится при EMFILE | Отменяемый backoff 5 мс - 1 с, ограничение частоты журналирования, дедлайн локального handshake и лимит активных клиентов. | Synctest, реальный процесс с NOFILE=64, проверка лимита двух клиентов и освобождения слота. |

Дополнительно исправлен генератор upload: короткие чтения транспортного буфера
теперь последовательно используют весь случайный блок 256 КиБ, а не повторяют
только его начало. Сам блок по-прежнему повторяется: это не проверка
устойчивости к любому алгоритму сжатия с произвольным размером окна.

Финальный прогон также обнаружил нестабильный существующий тест
`TestTheOpeningPadFollowsThePSKAndTheContext`: два допустимых совпадения
значений по модулю 21 считались ошибкой. Проверки padding переведены на
фиксированный набор входных данных; влияние PSK и каждого поля контекста
проверяется отдельно по последовательности результатов. Криптографическая
реализация не менялась. Сто повторений этих тестов под `-race` прошли.

Основные регрессионные тесты находятся в `pkg/transport/ws/deadline_interrupt_test.go`,
`pkg/veil/directory_bounds_test.go`, `internal/socks5/udp_dispatch_test.go`,
`internal/socks5/udp_resolve_test.go`, `cmd/s5client/accept_test.go`,
`cmd/wirebench/main_test.go` и `cmd/connlat/main_test.go`.

## Измерения до и после

Go 1.26.6, linux/amd64, i7-11700K, GOMAXPROCS=16. По шесть последовательных
прогонов `-benchtime=200ms`; race-тесты и сборки одновременно с ними не запускались.
В варианте "до" через `go test -overlay` подставлялся соответствующий исходник
из исходного коммита. Тестовый сценарий в каждой паре одинаковый.

| Сценарий | До | После |
| --- | ---: | ---: |
| 32 КиБ, обфускация + session + настоящий SDK метрик | 26,73 мкс; 5440 Б; 32 аллокации | 21,78 мкс; 0 Б; 0 аллокаций |
| Поиск при конкурентной перестройке, 32 768 участников: среднее с инструментированием | 1425,5 нс | 75,74 нс |
| Максимальная задержка поиска за прогон, медиана шести максимумов | 23,493 мс | 0,160 мс |
| p99 выборки lookup в том же сценарии | 60 нс | 59 нс |
| Plain WS: локальный Write 1422 Б | 3,382 мкс | 3,330 мкс, статистически значимого изменения нет |
| Shaped WS: локальный Write 1422 Б | 8,909 мкс | 8,980 мкс, статистически значимого изменения нет |
| Shaped WS: подтвержденный прием объема 1 МиБ | 904,4 мкс | 844,2 мкс |

Устранение аллокаций метрик дало **-18,53% времени** в изолированном сценарии
с SDK. Это не заявление о таком же ускорении всего прокси. Контрольный bare
вариант между сериями сдвинулся на -5,35%, state-only статистически не изменился:
короткие замеры имеют шум, а нулевые аллокации проверены отдельно тестом.

В реестре редкие длительные блокировки практически не влияли на p99 успешных
вызовов. Поэтому приведен также максимум каждого прогона. Benchmark измеряет
одного вызывающего в замкнутом цикле, с перестройкой в фоне; это не p99 потока
новых подключений с фиксированной интенсивностью и не измерение очереди под
перегрузкой. Максимумы после исправления также зависят от планировщика и GC.
Процентили берутся из ограниченной выборки, максимум учитывает каждый lookup.

В проверке NOFILE=64 при 73 открытых клиентских сокетах за наблюдаемые 200 мс
CPU-время дочернего процесса не выросло с точностью `/proc` (0,00 с). Записано
одно предупреждение Accept вместо исходного непрерывного потока. При
`CLIENT_MAX_CONNECTIONS=2` третий клиент отвергнут, незавершенные handshake
закрыты по 250 мс, следующий клиент занял освобожденный слот.

## Проверки

- `go test -race -count=1 -timeout=5m -covermode=atomic ./...` с coverage-файлом вне репозитория.
- `go vet ./...`, `golangci-lint run ./...`: без замечаний.
- `go mod verify`, `go mod tidy -diff`: зависимости целы, изменений не требуется.
- `govulncheck ./...`: 0 вызываемых уязвимостей. Сканер также отметил 2 уязвимости импортированных пакетов и 19 модулей без найденного вызова из приложения.
- `go test -run '^$' -bench . -benchtime=1x -timeout=5m ./...`: все benchmarks запускаются. Этот прогон проверяет работоспособность, не производительность.

## Изменения поведения и границы результата

- `CLIENT_MAX_CONNECTIONS=1024` по умолчанию; неположительное значение тоже
  выбирает 1024. Локальный handshake получает `HANDSHAKE_TIMEOUT`, либо 15 с
  при неположительном значении. Бюджет удаленного setup остается отдельным.
- При окне Roster=2 хранятся семь таблиц вместо пяти: две дополнительные
  готовятся на смену часа, не расширяя окно принятия. Встраивающий код должен
  запускать `Directory.Run` либо вызывать `Refresh`. Большой скачок часов
  требует обновления; диагностика ищет только среди подготовленных эпох.
- На UDP-ассоциацию: четыре DNS-запроса, максимум 64 ожидающих доменных
  пакета и 256 записей кеша на 30 с. Это локальный интервал повторного
  использования, а не DNS TTL: интерфейс resolver не возвращает TTL.
  Переполнение отбрасывает доменные пакеты, IP-путь не занимает эту очередь.
  Очередь может удерживать до примерно 4 МиБ pooled-буферов на ассоциацию.
- Истекший дедлайн активной WS-записи закрывает соединение: Gorilla не
  поддерживает продолжение записи после такого таймаута. Дедлайн,
  истекший без активной записи, можно очистить и продолжить работу.
- Числа нового EndToEnd нельзя напрямую сравнивать со старым send-only
  измерением. WS benchmarks остаются loopback без TLS; для полной задержки
  нужны внешний маршрут, TLS, DNS, учет, потери и конкурентная нагрузка.
- Измеренный в исходном аудите компромисс нового формата обфускации против
  старого `c4a41f0` для 32 КиБ не устранен откатом протокола. Исправлены
  дополнительные дефекты поверх текущего формата; сам wire format не менялся.
- Docker/netem и производственный VPS в этой задаче не запускались. Нагрузочный
  SLA на реальной сети этими локальными результатами не подтверждается.
