# Документация S5Core

Каталог разложен по тому, на какой вопрос отвечает документ, а не по тому, к
какому пакету он относится: замер отвечает "сколько это стоит", решение -
"почему сделано так", полевой документ - "что происходит на настоящем пути".
Один документ живет ровно в одном месте, ссылки между ними относительные.

| Что нужно | Куда смотреть |
| --- | --- |
| Формат провода, единственный источник истины | [veil-spec.md](veil-spec.md) |
| Почему устроено так, а не иначе | [design/](design/) |
| Сколько это стоит, с числами | [benchmarks/](benchmarks/) |
| Что происходит на боевом пути | [field/](field/) |
| Вердикты шлюзов плана | [gates/](gates/) |
| Материалы плана работ (HTML) | [plan/](plan/) |
| Записи прогонов | [reports/](reports/) |
| Найдено и не исправлено (сейчас пусто) | [fix-plan.md](fix-plan.md) |
| Решено, но не начато | [backlog.md](backlog.md) |
| Записи прошлого состояния | [archive/](archive/) |

## Верхний уровень

- [`veil-spec.md`](veil-spec.md) - спецификация формата S5Veil (задача Ф5-1).
  Реализация обеих сторон ведется по нему; расхождение кода и документа - баг
  одного из двух, и его ловят `pkg/obfs/spec_test.go` и
  `internal/socks5/spec_test.go`. Правка формата начинается здесь.
- [`fix-plan.md`](fix-plan.md) - подтвержденные дефекты, которые не исправлены,
  с приоритетом, порядком работ и критерием закрытия у каждого. Живой документ:
  пункт уходит из него, когда правка и ее регрессия в дереве. Сейчас очередь
  пуста - все 32 дефекта аудита и ревью закрыты, - и в документе остались
  происхождение пунктов, места, которые дефектами не стали, и правило, по
  которому пункт считается закрытым. Соседствует с `backlog.md` намеренно -
  обе очереди работ, но эта про найденное в коде, а та про решенное и не
  начатое.
- [`backlog.md`](backlog.md) - работа, по которой решение принято и обосновано,
  но она не начата. У каждого пункта записано, что считается его выполнением.

## `design/` - решения по устройству

Почему сделано так; цена решения - в замере, на который документ ссылается.

- [`design/session-fsm.md`](design/session-fsm.md) - конечный автомат
  соединения. Разделы 2-5 - анализ до задачи Ф6-1, раздел 6 - то, что реально
  сделано в `internal/session`; при расхождении прав раздел 6.
- [`design/half-close.md`](design/half-close.md) - полузакрытие кадром формата,
  а не `CloseWrite` транспорта (Ф4-9).
- [`design/writer-serialisation.md`](design/writer-serialisation.md) - мьютекс
  на направление вместо горутины-писателя (Ф4-6).
- [`design/decoy.md`](design/decoy.md) - чем сервер отвечает тому, кто пришел
  не за туннелем (Ф5-6).
- [`design/observability-policy.md`](design/observability-policy.md) - что
  метрике и логу знать не положено. Условие приемки каждой новой метрики.

## `benchmarks/` - замеры

Лабораторные числа: стенд повторяем, контроль рядом.

- [`benchmarks/argon2-cost.md`](benchmarks/argon2-cost.md) - цена Argon2id на
  пути установки соединения (Ф2-5, вердикт шлюза G2).
- [`benchmarks/ciphers.md`](benchmarks/ciphers.md) - AES-GCM против
  ChaCha20-Poly1305, на чем основан выбор шифра клиентом (Ф5-5).
- [`benchmarks/roster.md`](benchmarks/roster.md) - поиск участника по тегу
  пролога не зависит от их числа (Ф5-5).
- [`benchmarks/frame-shaping.md`](benchmarks/frame-shaping.md) - цена шейпинга
  кадров WebSocket и почему полоса начинается с 256 (Ф4-7).
- [`benchmarks/relay-profile.md`](benchmarks/relay-profile.md) - откуда берутся
  аллокации в релее (Ф2-6).
- [`benchmarks/local-bandwidth.md`](benchmarks/local-bandwidth.md) - локальный
  стенд полосы, откалиброванный по боевому каналу. Числа сравнивать с
  локальными же.
- [`benchmarks/arm-router.md`](benchmarks/arm-router.md) - замер на целевом
  железе клиента: потянет ли роутер и будет ли OOM.
- [`benchmarks/udp-over-tcp.md`](benchmarks/udp-over-tcp.md) - цена команды
  `0x83` на канале с потерями (Ф4-10).
- [`benchmarks/ws-read.md`](benchmarks/ws-read.md) - что стоила буферизация
  целого сообщения WebSocket и что дало потоковое чтение (F05).

## `field/` - боевой путь

Числа, снятые не на стенде. У каждого есть контроль без туннеля.

- [`field/nodes.md`](field/nodes.md) - боевые узлы, сколько канала доходит
  через туннель и что уходит мимо него.
- [`field/stealth.md`](field/stealth.md) - что сеть делает с первым пакетом
  (уровень 3 чек-листа стелса) и что о клиенте записывает принимающая сторона:
  отпечаток TLS и настоящий адрес (уровень 4). Инструменты уровня 4 -
  `cmd/fpcollect` (свой приемник, считает JA3/JA4 из `ClientHello`) и
  `scripts/leak_matrix.py` (матрица адресов по порту, протоколу, географии и
  версии IP).
- [`field/migration.md`](field/migration.md) - смена транспорта и формата в
  поле без замены бинарника (Ф5-7), с порядком обновления парка.
- [`field/mihomo.md`](field/mihomo.md) - клиент как выходной узел прокси-ядра
  mihomo: конфигурация, UDP, охват перехвата и порядок правил.

## `gates/` - шлюзы плана

- [`gates/g3-wire-format.md`](gates/g3-wire-format.md) - нужен ли новый формат

## `plan/`, `reports/`, `archive/` - записи

- [`plan/`](plan/) - исследование, аудит, блокеры, план работ и итог, в виде
  автономных HTML. Порядок чтения - в [`plan/README.md`](plan/README.md).
- [`reports/`](reports/) - записи прогонов и проверок:
  [`reports/v1.4.4-field-run.md`](reports/v1.4.4-field-run.md) (полевой отчет
  по релизу v1.4.4), [`reports/f2-7-rerun.md`](reports/f2-7-rerun.md)
  (повторный прогон, которым закрыт баг 1),
  и
  [`reports/code-quality-audit-2026-09-20.md`](reports/code-quality-audit-2026-09-20.md)
  (аудит рабочего дерева от 20.09.2026, дефекты F01-F19 со сценариями
  воспроизведения). Что с этими дефектами делать и в каком порядке - не здесь,
  а в [`fix-plan.md`](fix-plan.md): аудит записывает состояние, план ведет
  работу.
- [`archive/`](archive/) -
  [`archive/ice-audit-2026-05-30.md`](archive/ice-audit-2026-05-30.md): аудит
  кода от 30.05.2026, все 23 пункта закрыты.

Документы в `reports/` и `archive/` описывают прошлое состояние кода, а не
текущее. Правят их только тогда, когда меняется сама запись о прошлом.
