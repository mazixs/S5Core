# Всплеск ответов UDP: буфер приема и очередь отката (28.09.2026)

Замер к Ч-2 черновика ([`../plan/draft.md`](../plan/draft.md)) и задачам К-5,
К-6 и К-14 плана rc3 ([`../plan/v2.3-rc3.md`](../plan/v2.3-rc3.md)). На узле,
где матч терял 5% входящих, потери шли всплесками, и приемный буфер сокета
ассоциации их не держал ([`../field/nodes.md`](../field/nodes.md), раздел
"Вниз: буфер сокета на узле"). Здесь та же форма всплеска воспроизведена на
стенде, до и после двух правок:

- каждый UDP-сокет релея просит 2 МиБ приемного буфера (`internal/udpbuf`);
- очередь `socks5.TunnelWriter`, через которую ответы native-ассоциации идут
  по TCP, выросла с 64 кадров и 256 КБ до 1024 кадров и 2 МиБ.

## Форма всплеска

Из захвата на узле: волна из 443-465 датаграмм за 4-10 мс, до 128 за одну
миллисекунду, почти все по 928 байт полезной нагрузки, за ней хвост около 2000
в секунду. Стенд шлет волну из 450 датаграмм по 928 байт за 5 мс, затем еще
450 с шагом 500 мкс (всего 900 за 230 мс), пауза 2 с, 10 всплесков на прогон.
Вариант `wave900`: 900 за 5 мс без хвоста, то есть две волны сразу.

## Стенд

`scripts/udp_burst_stand.py` поднимает в своем сетевом пространстве
(`unshare`) источник всплесков (`udpprobe -echo`), `s5core`, при путях
`native` и `tcp` еще `s5client`, и приложение (`udpprobe -target ... -socks`),
которое считает дошедшее. Пути:

- `native` - `0x84` через `s5client` с `UDP_NATIVE=true`;
- `tcp` - `0x83` через `s5client`;
- `plain` - `0x03` прямо в `s5core`;
- `direct` - контроль: те же всплески прямо в приложение.

Отброшенное стенд раскладывает по сокетам (прирост столбца `drops` в
`/proc/net/udp` за время замера, в отчет попадают только сокеты, которые
теряли), а также снимает `RcvbufErrors` сетевого пространства,
отбросы на очереди приема процессора (второй столбец
`/proc/net/softnet_stat`) и метрики сервера.

Под root стенд создает только сетевое пространство, а `--server-user 65534`
запускает `s5core` под этим uid без capabilities, как в контейнере: буфер
сервера тогда ограничен `net.core.rmem_max` хоста. Источник и приложение
остаются под root и держат всплеск целиком, поэтому все отбросы принадлежат
серверу и клиенту; контроль это подтверждает. Без root стенд живет в user
namespace, и потолок `rmem_max` действует на все процессы.

`--cut-native 1` через секунду после начала отбрасывает датаграммы сервера к
клиенту по native правилом nftables на входе: клиент перестает слышать сервер,
и ответы до конца прогона идут по TCP управляющего соединения, через очередь
`TunnelWriter`. Отброс на выходе не годится: он возвращает отправителю
`EPERM`, сервер получает ошибку записи и сам уводит ответ на TCP
(`tcp_failed`) раньше, чем клиент заметит потерю, а в сети такого сигнала нет.

Сборки: 2.3.0-rc2, rc3 до правки очереди (с буфером) и rc3 с обеими
правками.

## Рабочая станция

16 потоков, ядро 7.0, `rmem_max` хоста 4 194 304, `rmem_default` 212 992, стенд
без root. Контроль: 0 потерь из 4500.

| Путь | 2.3.0-rc2 | rc3 |
|---|---:|---:|
| native | 20 из 9000 (0,22%) | 0 |
| tcp | 114 (1,27%) | 0 |
| plain | 31 (0,34%) | 0 |
| native, `s5core` на одном процессоре с циклом-нагрузкой | 1118 (12,42%) | 0 |
| tcp, так же | 1160 (12,89%) | 0 |

Почти все отбросы 2.3.0-rc2 - на сокете сервера, принимающем ответы источника,
остаток (до 6 за прогон) - на сокете native у клиента. На свободной машине
читатель почти успевает за волной, под нагрузкой на том же процессоре - нет, и
буфер в `rmem_default` теряет восьмую часть всплеска.

## Тестовый узел D

1 vCPU, 2 ГБ памяти, ядро 6.12, сервер под uid 65534 без capabilities.
Контроль: 0 из 9000 при обоих значениях `rmem_max`, 0 из 9000 на `wave900`.

| Путь | 2.3.0-rc2 | rc3, `rmem_max` 212 992 | rc3, `rmem_max` 2 097 152 |
|---|---:|---:|---:|
| native | 2012 из 9000 (22,36%) | 1348 (14,98%) | 0 |
| tcp | 1825 (20,28%) | 754 (8,38%) | 0 |
| plain | 1518 (16,87%) | 336 (3,73%) | 0 |

2.3.0-rc2 размера не просит и получает `rmem_default` при любом `rmem_max`. rc3
при потолке 212 992 получает 425 984 байта учета (ядро удваивает запрошенное)
и пишет при старте предупреждение с нужным значением, при потолке 2 097 152
получает 4 194 304. Там же при потолке 2 097 152:

| Прогон | 2.3.0-rc2 | rc3 |
|---|---:|---:|
| native, 30 всплесков | - | 0 из 27 000 |
| native, `wave900` | 6812 из 9000 (75,69%) | 0 |

От 98 до 100% потерь каждого прогона приходится на волну, хвост теряет
единицы. Отбросы на очереди приема процессора - 0 везде, где стенд их снимал,
то есть датаграммы теряются в буфере сокета, а не раньше.

## Откат на TCP

При потере native-пути ответы идут по TCP через очередь `TunnelWriter`. Кадр
сверх очереди отбрасывается (`s5core_native_udp_stream_drops_total{reason="queue"}`),
кадр старше 250 мс - тоже (`reason="age"`). Прогоны с `--cut-native 1`:

| Где | Сборка | Потеряно | В очереди |
|---|---|---:|---:|
| станция | rc3 до правки очереди | 49 и 62 из 9000 | 49 и 62 |
| станция | rc3 | 0 и 0 | 0 |
| узел D | 2.3.0-rc2 | 2430 (27,00%) | 683, остальное - буфер сокета |
| узел D | rc3 до правки очереди | 2338 (25,98%) и 2197 (24,41%) | все |
| узел D | rc3 | 0 и 456 (5,07%) | 0 |
| узел D, `wave900` | rc3 до правки очереди | 5935 (65,94%) | все |
| узел D, `wave900` | rc3 | 0 | 0 |

На станции первый прогон каждой сборки шел с отбросом на выходе, второй - на
входе; ответов на TCP по `EPERM` там не ушло ни одного (`tcp_failed` = 0).

456 во втором прогоне rc3 - одна волна, которую сервер успел отправить по
native после отреза и до того, как клиент перестал его слышать: так теряет и
настоящий обрыв, очередь тут ни при чем (0 отброшенных, клиент получил по
native 810 из 1266 отправленных). Отбросов по возрасту нет ни в одном прогоне:
1024 кадра поток отдает быстрее, чем кадр стареет на 250 мс. Первая серия на
узле D шла с отбросом на выходе и дала те же числа (25,29%, 25,28% и 68,17% до
правки, 0 после), но в одном прогоне 554 ответа ушли на TCP по `EPERM`, и в
выводы она не взята.

Очередь на 64 кадра переполнялась при здоровом потоке: читатель отдает кадры
быстрее, чем поток их пишет, и на одном vCPU за 5 мс волны поток успевает
взять около 130 кадров из 450 (450 минус 255 потерянных в медианном всплеске
минус 64 места очереди). На станции поток быстрее, и потерь десятки, а не
сотни.

## Выводы

- Запрос 2 МиБ держит волну из 900 датаграмм целиком даже на одном vCPU. Без
  `CAP_NET_ADMIN` его ограничивает `net.core.rmem_max` хоста: при значении по
  умолчанию rc3 теряет в 1,5-4,5 раза меньше 2.3.0-rc2, но не ноль. Хосту
  узла нужно `net.core.rmem_max=2097152`
  ([`../guides/docker.md`](../guides/docker.md)).
- Очередь отката держит волну дважды. Цена - память: ассоциация, чей поток
  стоит, держит до 2 МиБ буферов вместо 256 КБ.
- Потери в буфере видны без стенда: `s5core_udp_receive_buffer_drops_total`
  на сервере, строка `UDP receive buffer` при старте обоих бинарей.

## Как повторить

```bash
go build -o bin/s5core ./cmd/s5core
go build -o bin/s5client ./cmd/s5client
go build -o bin/udpprobe ./cmd/udpprobe
./scripts/udp_burst_stand.py --path direct --bursts 10 --label control
./scripts/udp_burst_stand.py --server bin/s5core --client bin/s5client --path native --bursts 10 --label native
./scripts/udp_burst_stand.py --server bin/s5core --client bin/s5client --path tcp --pin 3 --hog --bursts 10 --label tcp-hog
sudo ./scripts/udp_burst_stand.py --server bin/s5core --client bin/s5client --server-user 65534 --bursts 10 --label node
sudo ./scripts/udp_burst_stand.py --server bin/s5core --client bin/s5client --server-user 65534 --cut-native 1 --bursts 10 --label cut
```

Результаты ложатся в `bench/burst/` (`<label>.json` и журналы процессов).
