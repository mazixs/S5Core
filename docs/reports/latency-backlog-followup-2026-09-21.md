## 1. Еще два воспроизведенных дефекта

### L21-01. Остановка WSS может ждать decoy без ограничения

`pkg/transport/tlsdecoy/listener.go`, `Listener.Close`: вызов
`server.Shutdown(context.Background())` ждет завершения активного HTTP handler.
В `proxy.go` есть таймаут получения заголовков, но нет общего ограничения
длительности чтения тела upstream. Если upstream отдал заголовки и перестал
отдавать тело, HTTP WriteTimeout не прерывает это чтение. Ожидание задерживает
закрытие серверных слушателей и завершение процесса.

Проба поднимает настоящий TLS listener и локальный upstream. Upstream отдает
заголовки с Content-Length и останавливается. **Close остается заблокированным
31 секунду**, дольше настроенного WriteTimeout=30s. После освобождения upstream
Close завершается. Это воспроизведение отсутствующего ограничения, а не
измерение задержки обычного проксирования. Из кода следует, что ожидание может
продолжаться, пока handler не завершится; 31 секунда не является верхней границей.

Приоритет исправления: высокий для корректной остановки. Нужен ограниченный
бюджет graceful shutdown с принудительным закрытием оставшихся HTTP соединений
и завершением upstream-запросов при его исчерпании. Один context timeout у
Shutdown недостаточен: он прекращает ожидание, но сам не закрывает активные
соединения. Отдельно сохранить очистку уже upgraded WS и очереди передачи.

Доказательство: [shutdown.txt](followup-2026-09-21/shutdown.txt).

### L21-02. Close не прерывает задержку шейпера

`pkg/transport/ws/shaped.go`, `ShapedConn.Write`: перед каждым выбранным кадром
с вероятностью 10% выполняется `time.Sleep` под `writeMu`. Закрытие базового
`ws.Conn` не будит этот Sleep. Поэтому уже закрытый сокет оставляет вызывающий
Write и следующих писателей ждать окончания искусственной задержки.

Проба `testing/synctest` с фиксированным seed=9 и jitter=10s показывает:
**Write возвращается через 1,206120304 секунды после немедленного Close**.
Это точное виртуальное время выбранной паузы, а не погрешность планировщика.
Исправление Close базового WS из предыдущего аудита не устраняет этот внешний
Sleep. Во время такого Sleep дедлайн базового Conn также не будит шейпер.

По умолчанию `WS_MAX_JITTER_MS=0`, поэтому дефект не добавляет эту паузу при
стандартной конфигурации. Клиентский transport advice допускает до 60 000 мс;
это может сделать ожидание существенным. Нужна отменяемая пауза с соблюдением
Close и меняющегося WriteDeadline, сохранив выбранное распределение jitter.
Проверить Close, истечение/перенос/очистку дедлайна и несколько писателей.

Доказательство: [jitter.txt](followup-2026-09-21/jitter.txt).

## 2. Где еще возникают задержки

### Подключение к домену теряет альтернативные IP

Подтверждено чтением всей цепочки: `internal/socks5/resolver.go` возвращает
только `ips[0]`; `request.go` записывает этот IP в DestAddr; `AddrSpec.Address`
предпочитает IP доменному имени; `handleConnect` передает числовой адрес в Dial.
Поэтому стандартный net.Dialer уже не имеет списка адресов и не может выбрать
другой IPv4/IPv6 адрес домена.

При недоступности первого адреса запрос заканчивается ошибкой либо расходует
бюджет подключения (по умолчанию 10s), хотя другой адрес мог бы работать.
Быстрый connection refused не обязан ждать 10s. Нужен тест с несколькими
адресами и нерабочим первым, затем поддержка альтернатив в общем бюджете DNS
и Dial. При изменении интерфейса resolver сохранить пользовательские Resolver,
Rewriter и правила доступа; нельзя обойти проверку правил повторным DNS внутри
другого dialer. В этой проверке сценарий сетевого blackhole не запускался.

### Два линейных обхода под общей блокировкой

Локально измерены 20 последовательных вызовов на каждый размер. Таблица
показывает длительность операции, основная работа которой выполняется под
блокировкой. Это не измеренный p99 ожидания конкурентного подключения.

| Размер | FlushTraffic, медиана / максимум | Registry.Snapshot, медиана / максимум |
| --- | ---: | ---: |
| 10 000 | 0,112 / 0,347 мс | 0,659 / 0,832 мс |
| 32 768 | 0,560 / 0,966 мс | 2,791 / 3,991 мс |
| 262 144 | 9,977 / 11,895 мс | 36,202 / 37,522 мс |

В первом столбце размеров речь о пользователях, во втором сценарии - о
живых сессиях. Это независимые пробы, а не одна установка с таким числом
пользователей и подключений. Штатный MaxConnections=10 000; большие варианты
показывают масштабирование сверх этого значения.

- `internal/userstore/store.go`: FlushTraffic берет общий write lock и
  обходит всех пользователей. Периодический flush по умолчанию идет раз в
  60s. За этим lock ждут Lookup и SessionStatus; последний проверяется на
  границе учета трафика 64 КиБ. Файловая запись выполняется за пределами этого
  lock, поэтому приписывать ему время записи JSON на диск неправильно.
- `internal/session/registry.go`: Snapshot держит mutex реестра на всем
  обходе сессий при сборе метрик. Open/remove ждут его. Переходы состояния
  кадров атомарные, поэтому сам этот mutex не останавливает каждый пакет
  уже работающего релея.

На 10 000 записей это небольшие локальные паузы. При больших реестрах или
частом scrape стоит проверить хвост задержки новых подключений и quota-check
под конкурентной нагрузкой. Замена обхода счетчиками переносит стоимость на
каждый переход состояния; нужна проверка до/после, а не безусловная замена.

Доказательства: [store.txt](followup-2026-09-21/store.txt),
[sessions.txt](followup-2026-09-21/sessions.txt).

### Fallback помогает следующему запросу

`cmd/s5client/transport.go`, `dialTunnel` делает одну попытку. При ошибке
`onFailure` меняет политику для следующего подключения и возвращает ошибку
текущему. Поэтому наличие запасного транспорта само по себе не избавляет
текущий запрос от таймаута. Ошибка greeting/auth также может временно выбрать
legacy-формат, даже если причиной была временная потеря связи с новым сервером.

Это существующая политика, а не найденный бесконечный цикл. Вариант улучшения:
ограниченный retry до передачи пользовательских данных в общем бюджете, с
раздельными причинами отказа транспорта и формата. Отказ аутентификации и
ошибку CONNECT к конечному адресу нельзя автоматически считать поломкой
транспорта и повторять без учета последствий.

### Намеренная стоимость маскировки и холодной аутентификации

Shaping дробит один write на несколько WS-кадров и увеличивает число записей
в сокет. При включенном jitter паузы суммируются. Это цена заданной маскировки;
отключать ее как "лишний цикл" без оценки стелса нельзя.

Argon2 на промахе кеша остается дорогой операцией. В verifier есть ограничение
параллелизма и очереди, но всплеск холодных входов отличается от повторного
входа одного прогретого пользователя. Кеш ограничен 4096 записями. Его влияние
на p99 в этом дополнительном прогоне не измерялось; снижать параметры Argon2
ради красивого результата бенчмарка оснований нет.

## 3. Что показывает профиль и чего он не доказывает

Запущен TestObfsRelayProfile с настоящим SDK метрик: четыре соединения,
8 ГиБ принятого трафика, 1,748s, Go 1.26.6, linux/amd64. В CPU-профиле процесса:

- системные вызовы: 44,70% flat;
- AES-GCM encrypt/decrypt: суммарно 35,57% flat;
- memmove: 2,28% flat.

В этой передаче полезных данных основная стоимость - I/O и шифрование.
Это профиль общего процесса: в нем и клиент, и сервер, и конечный получатель.
Он не дает долю CPU одного s5core. Сценарий без WSS/TLS, пользовательской
аутентификации, конкурентного открытия подключений и периодического scrape.
SDK подключен, но не все направления нагружают серверный frame observer
одинаково. Результат 4686,9 МиБ/с на loopback не является скоростью VPS или
доказательством низкого p99. У нулевой полезной нагрузки здесь нет преимущества
от компрессии, но реальный сетевой маршрут этим не моделируется.

После предыдущих исправлений бенчмарки проверяют прием данных и ошибки.
Остается методическое ограничение: замкнутый цикл замедляет подачу запросов,
когда система тормозит, и скрывает часть очереди при фиксированной внешней
нагрузке. Следующий полезный нагрузочный сценарий - соединения с заданной
интенсивностью, реальные DNS/auth/WSS и scrape, p50/p95/p99/max, число ошибок
и пропущенных по расписанию запусков. CPU-профиль и микробенчмарки его не заменяют.

Доказательства: [прогон](followup-2026-09-21/profile-sdk-long.txt),
[CPU top](followup-2026-09-21/cpu-top.txt).

## 4. Что с бэклогом

В [backlog.md](../backlog.md) три принятые, не начатые задачи. Их состояние
перепроверено по реализации:

| Пункт | Состояние | Отношение к задержкам |
| --- | --- | --- |
| Б-1: профили мимикрии | Нет слоя профилей транспорта; есть TLS fingerprint, decoy и shaping. | Новая функция, может добавить накладные расходы. |
| Б-2: WSS за внешним TLS-фронтом | Валидация требует cert/key; listener всегда поднимает TLS. | Удобство развертывания; ускорение заранее не гарантировано. |
| Б-3: согласование ALPN | TLS listener не задает NextProtos. | Совместимость и стелс; нельзя просто включить h2 для HTTP/1.1 WebSocket. |

Предложенный порядок: сначала L21-01/L21-02 и проверка нескольких DNS-адресов;
затем нагрузочный сценарий хвостов задержки и оптимизация lock по его
результатам. Среди принятых функций: Б-3 как компактная задача совместимости,
Б-2 при развертывании за фронтом, Б-1 после них. Это рекомендация приоритетов,
а не запись о согласовании новых функций.

`fix-plan.md` обновлен: старая очередь 34 исправлений релиза v2.0.0 отделена
от девяти новых локальных исправлений; из кандидатов удалены уже исправленные
Close базового WS и локальный handshake. Два новых воспроизведенных дефекта
записаны в очередь. Остаются непроверенные кандидаты: join фонового flush,
fsync при сохранении и internal-типы в публичном SDK. Это не подтвержденные
причины задержек.

## 5. Воспроизведение и границы проверки

Исходники проб сохранены как `.go.txt`, чтобы не добавлять тестовые пакеты в
обычный `go test ./...`. Запуск из корня репозитория:

```sh
python3 docs/reports/followup-2026-09-21/reproduce.py all
```

Скрипт создает Go overlays и результаты во временном каталоге. Можно выбрать
`shutdown`, `store`, `sessions`, `jitter` или `profile`. Shutdown-проба занимает
около 31 секунды. Пробы shutdown/jitter намеренно подтверждают текущий дефект:
после исправления их ожидания надо инвертировать в постоянных регрессионных
тестах. Фикстура jitter использует helper из предыдущих локальных исправлений.
Фикстура профиля - снимок loadtest с подключенным SDK, не новый приемочный тест.

Сетевые вызовы проб ограничены loopback. Производственные серверы, Docker и
netem не запускались. Полный race/lint был пройден предыдущим набором
исправлений; в этой проверке выполнялись целевые пробы и обновлялась документация.
