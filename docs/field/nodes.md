# Боевые узлы: сколько стоит туннель на настоящем пути

Замеры в [`benchmarks/local-bandwidth.md`](../benchmarks/local-bandwidth.md) и
[`benchmarks/arm-router.md`](../benchmarks/arm-router.md) отвечают, сколько
берет код. Здесь другой вопрос: сколько из канала доходит через туннель и что
происходит с задержкой. Поэтому у каждого числа есть контроль - тот же путь,
та же точка, то же время, но мимо туннеля.

Без контроля полоса не значит ничего: 33 МБ/с это провал, если канал дает 90,
и почти потолок, если канал дает 39.

Снято 20.09.2026, версия на всех точках `v1.5.0-rc1`, транспорт `obfs`,
формат провода `v1`, пролог `printable`, шифр AES-256-GCM (выбран клиентом по
аппаратному AES). Раздел "Контроль после обновления" повторяет те же замеры
21.09.2026 на `v2.0.0`.

## Стенд

Два узла в разных ЦОД, оба с одним кодом и одной настройкой; отличаются длина
плеча и железо. Клиент - один и тот же ARM-роутер, два экземпляра `s5client`.

| | узел A | узел B |
|---|---|---|
| сервер | 1 vCPU, 967 МБ | 4 ядра, 5,9 ГБ |
| RTT ICMP с клиента | 42,8 мс (42,6-43,0) | 25,1 мс (24,4-25,7) |

Длина плеча - единственное, что различает узлы в выводах ниже. Адреса, порты и
имена машин к результату отношения не имеют и здесь не приводятся.

## Полоса: прямо и через туннель

Один файл в 50 МБ с того же сервера, прогоны чередуются (прямо, туннель,
прямо, туннель), чтобы состояние канала было общим.

| | прямо, МБ/с | туннель, МБ/с | доля канала |
|---|---|---|---|
| узел A, прогон 1 | 40,3 | 33,5 | |
| узел A, прогон 2 | 38,5 | 32,6 | |
| **узел A, среднее** | **39,4** | **33,1** | **84,0%** |
| узел B, прогон 1 | 47,4 | 43,6 | |
| узел B, прогон 2 | 50,3 | 42,6 | |
| **узел B, среднее** | **48,9** | **43,1** | **88,1%** |

Порог SLO из README - 85% канала. Короткое плечо его берет, длинное не берет
четырех десятых процента. Разница объясняется не кодом: код на обеих сторонах
один, а RTT отличается почти вдвое. Остаток полосы съедает окно TCP на длинном
плече - тот же вывод, что у шлюза G1 в
[`gates/README.md`](../gates/README.md): упор в канал и RTT, а не в процессор.

Прошлый замер на том же узле давал 80,3%, нынешний 84,0% - это не улучшение
кода, а другой измеритель: там полоса снималась через второй туннель, здесь с
клиента, который и есть боевой.

## Задержка установки

Медиана десяти запросов к `http://cp.cloudflare.com/generate_204`: сначала
прямо, потом через узел.

| | прямо | через узел | разница |
|---|---|---|---|
| узел A | 0,056 с | 0,185 с | +0,129 с |
| узел B | 0,052 с | 0,133 с | +0,081 с |

Это цена маршрута, а не туннеля: прямой запрос уходит в ближайшую точку
Cloudflare, через узел он сначала доезжает до узла. Разница между узлами
повторяет разницу их RTT. Цена самой обфускации измерена отдельно и в кругах:
4,03 RTT против 5,02 у голого SOCKS5, то есть кадрирование не добавляет ни
одного круга ([`gates/g4-first-frame.md`](../gates/g4-first-frame.md)).

## UDP через туннель

200 датаграмм по 60 байт с интервалом 20 мс, `cmd/udpprobe`, эхо на сервере.
Контроль - тот же UDP по тому же пути, но мимо туннеля.

| | p50 | p95 | p99 | джиттер | потери |
|---|---|---|---|---|---|
| узел A, прямо | 43,3 мс | 43,7 мс | 44,0 мс | 0,3 мс | 0/200 |
| узел A, туннель | 43,9 мс | 50,1 мс | 51,8 мс | 1,3 мс | 0/200 |
| узел B, прямо | 26,9 мс | 30,0 мс | 30,9 мс | 1,2 мс | 0/200 |
| узел B, туннель | 26,8 мс | 29,8 мс | 32,1 мс | 1,2 мс | 0/200 |

Медиана не меняется ни на одном пути (+0,6 мс и -0,1 мс), платит хвост: там,
где на пути есть потери, p95 растет на 6,4 мс, где потерь нет - не растет
вовсе. Это ровно предсказание
[`benchmarks/udp-over-tcp.md`](../benchmarks/udp-over-tcp.md): мультиплекс
`0x83` чинит потери участка до сервера, а цену выставляет редким датаграммам,
попавшим на ретрансмиссию.

Потерь ноль во всех четырех прогонах, то есть худший случай из
`udp-over-tcp.md` (один RTO, в Linux минимум 200 мс) здесь не наступает.

## Устойчивость установки соединения

25-30 подключений подряд на каждый узел, чередуя две формы открытия (в одной
записи с кадрами и отдельным пакетом, `OBFS_SPLIT_OPENING`):

| | открытие с кадрами | открытие отдельным пакетом |
|---|---|---|
| узел A | 30/30, 0,190 с | 30/30, 0,186 с |
| узел B | 25/25, 0,165 с | 25/25, 0,175 с |

Ни один из путей не режет первый пакет, поэтому `OBFS_SPLIT_OPENING` выключен
на обоих: выигрыша нет, а короткий пакет на фиксированном месте - это своя
постоянная форма. Путь, на котором она нужна, и измеренный там порог в 100
байт - в [`stealth.md`](stealth.md).

## Контроль после обновления до 2.0.0

Повтор 21.09.2026, когда парк перешел на `v2.0.0` (сначала клиенты, следом
серверы). Вопрос здесь один: не стало ли хуже. Контроль тот же - прямая
закачка по тому же пути в том же окне.

| | RTT ICMP | установка через узел | туннель, МБ/с | прямо, МБ/с |
|---|---|---|---|---|
| узел A, 20.09 (rc1) | 42,8 мс | 0,185 с | 33,1 | 39,4 |
| **узел A, 21.09 (2.0.0)** | **43,3 мс** | **0,188 с** | **31,9-33,2** | **29,0-32,8** |
| узел B, 20.09 (rc1) | 25,1 мс | 0,133 с | 43,1 | 48,9 |
| **узел B, 21.09 (2.0.0)** | **26,7 мс** | **0,136 с** | **40,8-44,8** | **48,3-52,0** |

Полоса туннеля воспроизвелась на обоих узлах, задержка установки совпала до
трех миллисекунд, RTT - в пределах суточного разброса пути. Доля канала на
узле B - 78-89% против записанных 88,1%.

Прямой контроль на узле A в этот раз просел до 29-32,8 МБ/с, и туннель вышел
быстрее него (97-114%). Это не заслуга туннеля: через узел A в момент замера
шел боевой трафик (46 живых сессий на сервере), и проседал именно тот прогон,
который шел без туннеля. Число полосы на узле A за этот день считать нельзя -
контроль недостоверен; сам туннель дал свои прежние 32-33 МБ/с.

Версия клиента проверена отдельно, потому что заменялись обе стороны сразу.
Старый бинарник rc1 поднимался рядом с новым на своем порту петли и качал с
того же сервера, чередуя с ним: 33,0 / 35,8 / 28,7 МБ/с у rc1 против
27,8 / 29,0 / 30,8 у 2.0.0, то есть разницы между версиями нет - обе версии
лежат внутри разброса пути. Клиент при 50 МБ/с занимает 55% одного ядра из
трех, то есть упора в процессор роутера нет.

### Чем мерить, чтобы число значило скорость, а не разгон

Одиночная закачка в 50 МБ на коротком плече длится около секунды, и в эту
секунду попадает разгон окна TCP, а не установившийся поток. Такой замер дал
28-35 МБ/с там, где установившаяся скорость - 41-45. Поэтому скорость берется
серией из четырех закачек подряд, первая отбрасывается, а считает ее сам
`curl` (`%{speed_download}`), а не секундомер оболочки: `date +%s` на четырех
секундах округляет до 25%.

Так же снимается и фон. Замер на роутере считает все, что на нем в это время
работает: на первом прогоне 21.09 треть ядра занимал забытый `awk` по
14-мегабайтному логу, и полоса туннеля падала до 28-30 МБ/с при свободном
канале. Перед замером стоит посмотреть `top` и убедиться, что idle близок к
95%, иначе меряется загрузка роутера, а не путь.

## Узел C: 2.2 rc против 2.1.0 (23-24.09.2026)

Третий узел, тот же клиент. Сервер 1 vCPU и 967 МБ, RTT ICMP с роутера
51,1 мс (50,5-51,4). Вопрос один: не хуже ли 2.2 rc (рабочее дерево без
legacy и raw-пролога) релиза 2.1.0 на настоящем пути. Этот код вышел как
2.2.0: после замера менялись только текст ошибки старта и генератор нагрузки.

Мерит пайплайн `scripts/matrix` в режиме `network = "wan"` (план -
`scripts/matrix/plans/wan.example.toml`): сервер и origin - отдельные юниты
systemd на своих портах рядом с боевым контейнером, клиент и генератор - на
роутере рядом с боевыми `s5client`. Контроль `raw` - тот же генератор прямо в
тот же origin, мимо туннеля. Аутентификация по ключу участника, 3 раунда,
ячейки по одной, порядок вариантов в четных раундах обратный. Медиана трех
раундов, в скобках разброс:

| | raw | 2.1.0 obfs | 2.2 rc obfs | 2.1.0 wss | 2.2 rc wss |
|---|---|---|---|---|---|
| TCP connect + эхо, мс | 104 | 158 | 158 | 267 | 267 |
| эхо 64 Б на открытом соединении, мс | 51,7 | 52,9 | 52,5 | 52,5 | 51,8 |
| HTTPS, новое соединение, мс | 162 | 215 | 215 | 327 | 324 |
| HTTP/2 на открытом соединении, мс | 52,5 | 52,9 | 52,6 | 53,8 | 53,9 |
| HTTP/3 на открытом соединении, мс | 52,8 | 53,8 | 52,6 | 53,3 | 53,2 |
| скачивание 8 МиБ, МБ/с | 17,5 (17-19) | 13,5 (7-14) | 16,4 (8-18) | 15,8 (11-18) | 16,1 (5-17) |
| отдача 8 МиБ, МБ/с | 18,1 (17-24) | 11,2 (0,5-18) | 3,8 (0,3-10) | 2,2 (0,3-16) | 4,6 (0,4-15) |
| HTTP/3 скачивание, МБ/с | 15,9 | 2,7 | 8,9 | 3,2 | 3,0 |
| UDP эхо 64 Б, p50, мс | 52,5 | 52,8 | 52,2 | 51,9 | 53,2 |
| UDP 5 Мбит/с, p50 / потери | 52,2 мс / 0% | 54,4 мс / 0% | 52,9 мс / 0% | 52,5 мс / 1,6% | 52,0 мс / 1,3% |
| UDP 40 Мбит/с, потери | 64% | 65% | 32% | 87% | 89% |

Ошибок ноль во всех 15 ячейках. CPU и память версий совпадают: клиент на
роутере 2,0-2,4 с процессора за ячейку у обеих версий obfs и 3,4-4,1 с у wss,
пик RSS клиента 12 МБ (obfs) и 14 МБ (wss), сервера 19-24 МБ.

Что из этого следует:

1. **2.2 rc не хуже 2.1.0.** Задержка совпадает до миллисекунды на всех
   сценариях. Трехраундовое сравнение дало два флага, оба сняты. Отдача через
   obfs у rc была ниже во всех трех раундах (3,8 против 11,2 МБ/с), и
   прицельный повтор только этого сценария на 8 раундах (24.09, около
   полуночи) дал 19,0 против 19,0 МБ/с: rc быстрее в 5 раундах из 8. Второй
   флаг (скачивание по wss у rc медленнее, по obfs быстрее) имеет разный знак
   на одном и том же коде `pkg/obfs` и отдельно не проверялся.
2. **Цена туннеля считается в кругах, а не в миллисекундах.** Raw тратит 2
   RTT на подключение и эхо, obfs 3, wss 5: первый кадр obfs несет
   приветствие и CONNECT без лишнего круга, wss добавляет TLS и upgrade. На
   открытом соединении туннель добавляет не больше 1,5 мс к медиане.
3. **Полоса.** На спокойном пути туннель отдает столько же, сколько raw
   (19,0 МБ/с на повторе при 18,1 у raw в основном прогоне), скачивает 77-94%
   raw. HTTP/3 через туннель скачивает в 2-6 раз медленнее: это QUIC внутри
   UDP-over-TCP, цена из
   [`benchmarks/udp-over-tcp.md`](../benchmarks/udp-over-tcp.md). Мелкие
   запросы HTTP/3 на открытом соединении она не задевает.
4. **Первый раунд шел в перегруженном окне** (вечер): эхо 70 мс вместо 52, а
   отдача через любой туннель 0,3-0,5 МБ/с, хотя raw незадолго до этого отдал
   24. К третьему раунду туннели вернулись к 10-18 МБ/с. Одиночный замер из
   такого окна выглядит как регрессия, поэтому вердикт выносится только по
   парам внутри раунда.
5. **UDP 40 Мбит/с этот путь не несет и без туннеля** (64% потерь у raw).
   Через туннель датаграммы сначала встают в очередь TCP (p50 95-465 мс против
   52), а не теряются сразу. На 5 Мбит/с медиана не меняется.

Прогоны лежат в `bench/runs/` (вне git),
полезная нагрузка обоих - 1,5 ГиБ.

### Игровая сессия: час UDP 64 Гц (24.09.2026)

Тот же узел и клиент, 2.2.0, сценарий `game/64hz-200b` пайплайна
`scripts/matrix`: 64 датаграммы в секунду по 200 байт в обе стороны, час,
рядом тихий TCP-канал с эхом раз в 40 с. Контроль - тот же поток с того же
клиента прямо в тот же UDP-эхо, в те же минуты. Транспорты шли по часу один
за другим в один день, поэтому каждый сравнивается со своим контролем, а не
друг с другом. plain - контроль другого рода: SOCKS5 без
обфускации, без `s5client`, генератор идет в сервер сам, и UDP ASSOCIATE
(`0x03`) остается настоящим UDP. Так видно, сколько стоит перенос UDP в TCP
отдельно от шифрования. Порт без пароля открыт только клиенту фильтром юнита
стенда, как развертывание это не годится: адрес назначения и данные идут
открытыми.

| | obfs | прямо | wss | прямо | plain | прямо |
|---|---|---|---|---|---|---|
| датаграмм | 230 400 | 230 400 | 230 400 | 230 400 | 230 400 | 230 400 |
| потери | 0% | 0,028% | 0% | 0,054% | 0,04% | 0,33% |
| p50, мс | 52,3 | 51,7 | 53,0 | 52,3 | 51,8 | 51,4 |
| p99, мс | 55,2 | 53,6 | 56,7 | 54,5 | 54,2 | 53,3 |
| p99.9, мс | 69,4 | 67,6 | 98,0 | 78,3 | 68,2 | 70,4 |
| максимум, мс | 154 | 146 | 163 | 148 | 141 | 139 |
| джиттер (средний \|ΔRTT\|), мс | 0,47 | 0,38 | 0,63 | 0,51 | 0,47 | 0,40 |
| рывки (медиана + 50 мс) в час | 43 | 45 | 88 | 59 | 46 | 53 |
| замирания (нет ответа дольше 100 мс) | 9 | 3 | 17 | 8 | 3 | 3 |
| обрывы ассоциации | 0 | 0 | 0 | 0 | 0 | 0 |
| тихий TCP-канал | 89 из 89 | | 89 из 89 | | 0 из 89 | |

CPU за час: клиент 35 с у obfs и 56 с у wss (1-1,6% одного
ядра), сервер 89, 135 и 68 с у plain. RSS клиента 8,0 и 11,4 МБ, сервера
22-24 МБ, к концу часа не растет. Результат wss забран с клиента вручную: оркестратор
прогона остановился посреди ячейки, генератор доработал до конца, а минуты
остановки в обоих потоках ничем не отличаются от соседних.

1. **Туннель добавляет к медиане 0,6-0,7 мс, к p99 1,6-2,2 мс, и за час
   ничего не копится**: p50 первой и последней минуты совпадает с точностью
   до 0,02 мс, обрывов нет, тихий TCP-канал дольше `READ_TIMEOUT` жив во
   всех проверках.
2. **Потерь через туннель нет, вместо них - задержка.** Датаграмму, которую
   путь теряет, TCP пересылает, и ответ приходит через 110-160 мс вместо 52:
   замираний у туннеля больше, чем у контроля (9 против 3, 17 против 8). Для
   игры это рывок, а не потерянный пакет.
3. **obfs рывков не добавляет (43 против 45 в час), wss добавляет (88 против
   59) и поднимает p99.9 на 20 мс.** Это один час на транспорт, то есть
   наблюдение, а не вердикт. Вероятная причина - шейпер WSS режет каждую
   запись минимум на два кадра и пишет их по одному, так что тик уходит
   несколькими сегментами и чаще попадает под потерю. Не проверено. Для
   игрового трафика на этом пути выбор - obfs.
4. **Нативный UDP через тот же сервер почти не отличим от прямого потока:**
   +0,4 мс к медиане, +0,9 мс к p99, замираний столько же (3 и 3). Потери
   0,04% - того же порядка, что у пути в другие часы. Во всех трех часах у
   прямого потока по 3 замирания, у нативного UDP 3, у obfs 9, у wss 17.
   Разница между obfs и plain и есть цена переноса UDP в TCP на этом пути:
   при потерях 0,03-0,05% (60-120 датаграмм за час) это 6 лишних замираний
   в час.
   На рывки (медиана + 50 мс) она не влияет: 43 и 46. Путь чистый, поэтому
   рост этой цены с потерями замер не показывает
   ([`plan/gaming.md`](../plan/gaming.md), решение 6).
5. **Контроль plain-часа терял 0,33%, в 6-12 раз больше, чем в другие часы.**
   Нативный UDP через сервер за тот же час потерял 0,04%, а у прямого потока
   потери были во все 60 минут, в отдельные до 0,8%. Значит, потери
   зависели от конкретного потока (адреса и порты), а не от пути в целом.
   Причину не разбирали. Сравнивать задержку с этим контролем можно, потери -
   с уровнем пути в другие часы.
6. **Тихий TCP-канал через plain не живет, и так и должно быть.** У SOCKS5
   без туннеля нет keepalive, и сервер закрывает соединение, молчащее дольше
   `READ_TIMEOUT` (30 с). Ради этого keepalive в туннеле и есть. В UDP-транспорте
   из плана управляющее соединение остается в obfs-туннеле вместе с keepalive.
7. **Счетчик недопустимых переходов сессии показал 1 за час.** Причина -
   гонка в релее: половина, закончившаяся чисто уже после разрыва обеих
   сторон, пыталась перевести закрытую сессию в `half_closed`. На провод это
   не влияло. Исправлено, тест `internal/socks5/relay_teardown_test.go`.

## Что уходит мимо туннеля

Полоса и задержка меряют трафик, который до туннеля дошел. Этот раздел про
трафик, который до него не дошел: два сервиса проверки WebRTC показали
настоящий адрес клиента при том, что обычный HTTP-запрос с той же машины
показывал адрес узла.

Проверяется без браузера: WebRTC узнает внешний адрес не у сайта, а у
STUN-сервера, поэтому достаточно послать тот же Binding Request самому
(`scripts/leak_matrix.py`, запускать с проверяемой машины). Замер 20.09.2026:

| STUN сервер | порт | нас видят как | почему так |
|---|---|---|---|
| stun.l.google.com | 19302 | адрес узла | порт в списке перехвата |
| stun.cloudflare.com | 3478 | адрес узла | порт в списке перехвата |
| stun.sipgate.net | 3478 | адрес узла | порт в списке перехвата |
| **stun.sipgate.net** | **10000** | **настоящий адрес** | **порт вне списка** |
| **stun.sipnet.ru** | 3478 | **настоящий адрес** | **правило по стране отдает прямой путь** |
| stun.linphone.org | 3478 | адрес узла | контроль |

Две строки выделены, потому что это две **разные** причины, и лечатся они в
разных местах. Пара sipgate 3478/10000 доказывает первую без рассуждений: один
и тот же сервер, один и тот же протокол, отличается только номер порта.

1. **Перехват висел на списке портов, а не на всем диапазоне.** Все, чего в
   списке нет, идет мимо туннеля, и это касается не только UDP: SSH на порт 22
   приходил на сервер с настоящего адреса.
2. **Правило "страна клиента - напрямую" в конце набора** отдает прямой путь
   любому серверу с адресом этой страны, в том числе STUN-серверу. Локальный
   сервис проверки этим и пользуется. Лечится правилом для STUN/TURN **до**
   правила по стране.

Ни одна из причин не в s5core: на всех путях, где трафик до туннеля дошел,
наружу виден адрес узла. Это охват перехвата, то есть свойство развертывания,
и проверять его надо на каждом новом отдельно - для этого проба и лежит в
репозитории. `scripts/leak_matrix.py` сверяет адреса по четырем осям: порт,
протокол (UDP и TCP), география сервера и версия IP. С ключом `--node` она
выносит вердикт сама и возвращает код 1, если ответ пришел с адреса, которого
в списке узлов нет.

Номер порта для такого решения плохой признак, и дело не только в дырках
списка: на одном номере живут разные вещи - на UDP 10000 и STUN, раскрывающий
адрес, и медиа Jitsi. Утечка STUN-ом не ограничивается: WebTransport ходит
поверх HTTP/3, то есть по UDP на произвольном порту, и сервис проверки,
собранный на нем, читает настоящий адрес, пока перехвачен не весь диапазон -
при этом обычный WebRTC-тест на стандартных 3478 и 19302 показывает путь
чистым. Отсюда правило: **перехватывать весь диапазон портов, а решать "что
идет напрямую" по домену, ASN или стране на стороне прокси-ядра.**

Настройка перехвата на стороне роутера - в [`mihomo.md`](mihomo.md).

### Чем закрыто

Диапазон перехвата раскрыт на все порты, STUN/TURN (3478-3481, 5349-5352,
19302-19309, tcp и udp) вынесены в правила прокси-ядра до правила по стране.
Контрольный прогон 20.09.2026 после правок: все шесть серверов пробы видят
один адрес - адрес узла. SSH на внешний сервер приходит с адреса узла.

Там же выяснилось, почему вердикт выносится по адресу, а не по конфигурации:
правило прокси-ядра, отбрасывающее весь UDP на порт 443, живо и срабатывает
(1201 раз), но датаграммы пробы на тот же порт до ядра не доходят вообще - их
не забирает перехват, и ни один счетчик ядра они не двигают. Правило в конфиге
не говорит о том, что трафик через него идет; говорит только адрес, который
видит сервер ([`stealth.md`](stealth.md), уровень 4).

## MTU пути до узлов (М-3, 26.09.2026)

Задача М-3 из [`../plan/game-fixes.md`](../plan/game-fixes.md): что на
настоящих путях с размером пакета, от которого зависят предел native UDP
(1400 байт UDP-нагрузки, IP-пакет 1428) и черная дыра TCP. Только чтение:
на узлах ничего не запускалось и не менялось. Точка клиента - та же машина в
Нидерландах, что и во всех замерах выше, мимо туннеля.

| | узел A | узел B | узел C |
|---|---|---|---|
| MTU внешнего интерфейса и мостов docker | 1500 | 1500 | 1500 |
| глобальный IPv6 | нет | нет | нет |
| `tcp_mtu_probing` на хосте / sysctls контейнера | 0 / нет | 0 / нет | 0 / нет |
| PMTU клиент -> узел, `ping -M do` | 1500 | 1500 | 1500 |
| PMTU узел -> клиент, TCP этой же SSH-сессии | 1500, `mss:1448`, без повторов | 1500, `mss:1448`, без повторов | 1500, `mss:1448`, без повторов |
| RTT ICMP | 43,0 мс | 25,9 мс | 49,9 мс |

- Ядро всех трех узлов - 6.12.107, `ip_no_pmtu_disc` 0, `tcp_base_mss` 1024.
- В сторону узла `ping -M do -s 1472` проходит, `-s 1473` отказывает
  локально (`EMSGSIZE`): предел - MTU своего интерфейса, узкого звена на пути
  нет. `tracepath` до узла C дает `pmtu 1500` и те же хопы, что ICMP
  `traceroute`, то есть UDP до узлов идет мимо перехвата роутера.
- Обратное направление ping'ом не снять: домашний роутер на ICMP не
  отвечает, а `tracepath` на узлах не установлен. Поэтому оно снято по TCP:
  узел отдает 3 МБ в ту же SSH-сессию (около 1 с), и `ss -tin` на узле
  показывает `pmtu:1500 mss:1448` без повторов. Сегмент 1448 байт с
  timestamps - это IP-пакет 1500, то есть обратный путь его несет.
- Отсюда: на этих путях native-датаграмма предельного размера (IP 1428)
  проходит в обе стороны без фрагментации, и полоса потерь по размеру из
  F4 аудита здесь не проявится. Она проявится там, где путь уже 1428:
  клиент внутри чужого VPN, мобильные сети, туннели провайдера (разделы 5.3 и 5.6
  [`../research/mtu.md`](../research/mtu.md)); на таких путях ее меряет
  стенд М-1, а не поле.
- Проба форм UDP на 1001, 1300, 1364 и 1400 байт снята позже и только на
  узле C, раздел ниже. Датаграммы до 1200 байт проходят все формы по пробе
  У-0.

Повторить (клиент, затем каждый узел):

```bash
ping -n -c2 -W2 -M do -s 1472 <узел>        # перебор -s до последнего ответа
ip -o link show; sysctl net.ipv4.tcp_mtu_probing
docker inspect -f '{{.Name}} {{.HostConfig.Sysctls}}' $(docker ps -q)
# обратное направление: с клиента
ssh <узел> 'head -c 3000000 /dev/urandom; ss -tin state established "( sport = :22 )" >&2' | wc -c
```

### Размеры 1001-1400 байт на узле C (М-3, 26.09.2026)

Вторая половина М-3: проходят ли датаграммы у предела native и у порога
1001 байт из раздела 4 [`../research/path-degradation.md`](../research/path-degradation.md),
мимо туннеля и через него. Приемник `cmd/udpshape serve` - transient unit
systemd на портах 3478 и 41999 с IP-фильтром на адрес клиента (443 у узла C
закрыт хостером, 51820 ограничен по темпу, [`udp-shapes.md`](udp-shapes.md)),
после замера удален. Сборка туннеля - `0adc874`, стенд `scripts/matrix` в
режиме WAN, клиент и генератор на ARM-роутере.

**Мимо туннеля форма и размер не решают.** Семь форм на четыре размера
(`quic-initial` - от 1200 байт), по 100 датаграмм на порт с темпом 16 в
секунду на поток: uplink 100% во всех 54 тестах на обоих портах, downlink
98-100%, p50 RTT 50,9-53,6 мс.

**Путь режет по темпу, а не по форме.** Та же матрица с темпом 64 в секунду на
поток (3456 датаграмм в секунду на все 54 потока) дала uplink 50-53% в
каждой ячейке, одинаково на всех формах, размерах и портах. Отдельные потоки
по 5 с:

| Поток | Отправлено в секунду | Дошло |
|---|---:|---:|
| `random` 1300 байт | 1000 | 100% |
| `random` 1300 байт | 1800 | 69,9% (1258 в секунду) |
| `random` 1300 байт | 2600 | 48,7% (1267 в секунду) |
| `random` 200 байт | 3456 | 36,2% (1252 в секунду) |
| два порта по 1000 одновременно | 2000 | 67,3% на каждом (1347 в секунду вместе) |

Проходит около 1250-1350 датаграмм в секунду при любом размере, то есть
ограничено число пакетов, а не байты, и на весь источник, а не на порт. С
самого роутера то же самое (3000 в секунду - 44,6-44,8%), то есть домашняя
сеть за роутером ни при чем. Режут до узла: его интерфейс принимает 7130
пакетов из 15 000, а `UdpRcvbufErrors` и `rx_drop` не растут. Кто режет,
хостер узла C или провайдер клиента, без второго адреса назначения не
разделить. Проба У-0 24.09.2026 пропускала всплески по 1216 датаграмм в
секунду на каждом из четырех портов, а сегодняшний всплеск той же длины (1,6 с)
проходит наполовину: предел либо появился позже, либо зависит от времени суток,
это не установлено. Игре предел не мешает: 64-128 датаграмм в секунду. Он
ограничивает native на загрузку к этому узлу, около 13 Мбит/с при 1300
байтах, и так же прямой UDP, потому что это предел пути, а не транспорта;
`0x83` идет по TCP и под него не попадает.

**Через туннель** - игровой поток 64 Гц по минуте на размер, в той же ячейке
прямой контроль тем же размером от роутера к узлу:

| Размер | Путь | Предел native | Потери native / прямо | p50 native / прямо | p99 native / прямо |
|---|---|---:|---:|---:|---:|
| 1001 | native | 1396 | 0,365% / 0,625% | 53,32 / 52,04 мс | 71,20 / 69,94 мс |
| 1300 | native | 1395 | 0% / 0,417% | 52,48 / 51,82 мс | 55,08 / 54,09 мс |
| 1364 | `0x83` после 8 отброшенных | 1396 | 0,286% / 0,547% | 52,26 / 51,46 мс | 54,89 / 53,27 мс |
| 1400 | `0x83` после 8 отброшенных | 1392 | 0,208% / 0,755% | 52,28 / 52,08 мс | 54,46 / 53,50 мс |

Это ровно то, что обещает раздел 10.7 [`../veil-spec.md`](../veil-spec.md):
предел на пути 1500 лег в 1392-1396 байт, датаграмма 1364 байт к IPv4-адресу
влезает только при пределе 1400, поэтому 1364 и 1400 ушли на `0x83` по
правилу восьмой, а потери у них - те 8 отброшенных в начале (0,21% минуты).
Поиск предела стоил 7 проб на ассоциацию. У 1001 оба потока в одну минуту
получили всплеск задержки, отсюда p99 около 70 мс у обоих.

Повторить:

```bash
udpshape serve -listen :3478,41999 -allow <адрес клиента>/32 -log serve.jsonl  # на узле
udpshape probe -to <узел>:3478,41999 -sizes 1001,1300,1364,1400 -rate 16 -json
udpshape probe -to <узел>:41999 -sustain random@1300 -rate 1800 -duration 5s -window 5s -json
# через туннель: план по образцу scripts/matrix/plans/wan.example.toml,
# only = ["=game/64hz-1001b", "=game/64hz-1300b", "=game/64hz-1364b", "=game/64hz-1400b"], scale = 1/60
```

## Живая игра через узел C: где теряются пакеты (27.09.2026)

Жалоба с клиента на Windows в full tunnel (схема
[`scripts/s5vpn-win.ps1`](../../scripts/s5vpn-win.ps1): приложения -> tun2socks
-> `s5client`), `v2.3.0-rc2` на обеих сторонах. На игровом сервере в том же
городе, что узел C, игра показывает пинг 70-80 мс и постоянные входящие
потери, в лобби пинг регионов 300-600 мс. Надо было понять, чьи это потери:
узла, пути или клиента.

Игровой сервер от узла в 1 мс. От маршрутизатора клиента напрямую до него
41-45 мс, до узла 51 мс (ICMP), поэтому через туннель ожидается около 52 мс:
крюк через узел добавляет 8-10 мс к прямому пути. Поток матча идет по native:
вверх 47-48 датаграмм в секунду по 70 байт, вниз 50-53 по 700-1100 байт.
Больше 1100 байт не было ни одной, поэтому по размеру на `0x83` не ушло ничего.

**Счетчики живого потока.** Счетчики nft на внешнем интерфейсе узла стояли на
потоке к клиенту и на обмене с игровым сервером, на маршрутизаторе клиента
считал conntrack того же потока. Окно 121 с с метками времени на обеих
сторонах:

| Участок | Отправлено | Принято |
|---|---:|---:|
| игровой сервер -> узел | - | 6129 |
| узел -> клиент (native) | 6372 | 6382 на маршрутизаторе |
| клиент -> узел | 5751 | 5747 на узле |

К клиенту ушло на 243 датаграммы больше, чем пришло от игры: это 2 в секунду
проб пути и ответов на них. Вниз все датаграммы игры ушли по native. На
участке игровой сервер - узел - маршрутизатор клиента потерь нет в пределах
точности сверки (0,3%).

**Единственный отброс на узле.** Сокет ассоциации матча отбросил 91 датаграмму
(`skmem ... d91` в `ss -uam`, `UdpRcvbufErrors` сетевого пространства
контейнера). Это был один всплеск: за 3 минуты наблюдения счетчик не вырос.
Приемный буфер сокета - 212 992 байта (`net.core.rmem_default`, он же
`rmem_max` хоста), датаграмма 1100 байт занимает в нем 2304. Значит, буфер
держит около 90 датаграмм, и всплеск больше этого, например при загрузке
матча, теряется раньше, чем его прочтет релей. Сервер размер буфера не задает,
а без поднятия `rmem_max` на хосте и не смог бы задать больше.

**Та же частота с маршрутизатора.** 64 датаграммы в секунду по 200 байт, 90 с.
Эхо стояло на узле, поток шел одновременно через туннель и прямо:

| | Потери вверх | Потери вниз | p50 | p99 | Максимум |
|---|---:|---:|---:|---:|---:|
| туннель (native) | 0,02% | 0,03% | 52,0 мс | 54,1 мс | 120,8 мс |
| прямо | 0,14% | 0,03% | 51,4 мс | 52,7 мс | 59,0 мс |

**Новая ассоциация.** Первый ответ на новой UDP-ассоциации приходит через
159-161 мс от ее открытия (5 попыток), прямо - через 53 мс. Из них 2 круга
уходят на TCP и ASSOCIATE, третий - на саму датаграмму, дальше RTT 52-53 мс.
tun2socks открывает ассоциацию на каждый новый поток приложения, а пинг
регионов в лобби - каждый раз новый поток: в conntrack узла это десятки
коротких потоков к порту пингов с разными портами источника. Поэтому лобби
показывает цену установки, а не RTT пути. 160 мс этого стенда объясняют
300-600 мс в лобби не полностью, остаток на Windows-клиенте не измерен.

**Вывод.** Между игровым сервером и маршрутизатором клиента туннель пакеты
не теряет, кроме разового всплеска на сокете, и RTT у него тот же, что у
прямого пути до узла. Постоянные входящие потери и разница между 70-80 мс
в игре и 52 мс пути возникают за маршрутизатором клиента: в Windows-стеке
(tun2socks, `s5client`) или в том, как игра считает пинг, куда входят кадры
клиента и сервера.

**Контроль мимо full tunnel.** Ту же игру пустили мимо full tunnel, через
`s5client` на маршрутизаторе. Прокси-ядро отнесло игровые адреса по GeoIP к
узлу A, поэтому контроль шел через узел A, а не через C. Входящих потерь в
игре больше нет, пинг в игре тот же, 70-80 мс. Круг до игрового сервера по
ICMP: прямо 44,6 мс, через узел A около 50 мс (42,4 до узла и 7,6 от него),
через узел C около 52 мс (51 и 1,1). Пинг в игре на 20-30 мс выше любого из
путей, то есть эту разницу дает сама игра, а не туннель, а туннель добавляет
к прямому пути 5-7 мс крюка.

Тогда игру перевели на узел C через тот же клиент на маршрутизаторе, и
входящие потери вернулись. Значит, дело не в Windows-стеке, а в пути к узлу C:
сверка счетчиками выше точна до 0,3% и потерю меньше этого не видит. Замер
размером игрового пакета, 1000 байт 50 раз в секунду, 90 с, все четыре потока
одновременно с маршрутизатора, эхо на самих узлах:

| Путь | Потери вверх | Потери вниз | p50 | p99 |
|---|---:|---:|---:|---:|
| узел C прямо | 0,27% | 0,04% | 51,4 мс | 52,6 мс |
| узел C, туннель | 0% | 0,04% | 52,7 мс | 54,7 мс |
| узел A прямо | 0,02% | 0% | 43,3 мс | 51,4 мс |
| узел A, туннель | 0,02% | 0% | 43,3 мс | 46,9 мс |

Плечо от узла до игрового сервера эхо не покрывает, его проверили ping размером
1000 байт 50 раз в секунду, 3000 пакетов: у узла C 2 потери (0,07%), у узла A
ни одной. Потери одиночные, серий нет, на маршрутизаторе `UdpRcvbufErrors` за
замер не выросли. На каждом пути туннель теряет столько же, сколько прямой UDP,
поэтому входящие потери в игре - свойство пути к узлу C и его сети, а не ядра
и не клиента. Для игры на этом сервере узел A лучше: круг почти тот же, 50 мс
против 52, а потерь нет.

Повторить (порт игрового потока клиента берется из conntrack маршрутизатора):

```bash
# на узле: счетчики на время замера, потом nft delete table ip probecount
nft add table ip probecount
nft add chain ip probecount pre '{ type filter hook prerouting priority -300; }'
nft add chain ip probecount post '{ type filter hook postrouting priority 300; }'
nft add rule ip probecount pre iifname <if> ip saddr <клиент> udp sport <порт> counter
nft add rule ip probecount post oifname <if> ip daddr <клиент> udp dport <порт> counter
nsenter -t <pid контейнера> -n ss -uanm   # d<N> в skmem - отбросы сокета
# на маршрутизаторе клиента: packets= обоих направлений того же потока
grep 'sport=<порт> ' /proc/net/nf_conntrack
```

**Всплеск ассоциаций не рвет путь.** Разовые провалы на узле C (в игре до 51%
входящих потерь за раз) совпадали по времени с пингами регионов, поэтому
проверили, не вызывает ли их сам всплеск новых ассоциаций. Поток 64 датаграммы
в секунду по 800 байт, 60 с, поверх него два залпа по 36 коротких ассоциаций:
на узле C 0,03% вверх и 0% вниз, p99 61 мс, ни одной потери пути; на узле A 0% и
0%, p99 47,5 мс. Провалы - события пути, нагрузка установкой их не объясняет.

## Узел B для игры: путь делится по потокам (27.09.2026)

Ту же игру перевели на узел B. Пинг в игре 280-500 мс, через несколько минут
игрок выброшен с сервера, в следующем матче пинг 120 мс. Ожидалось около 80:
круг до узла 26,3 мс по ICMP, от узла до игрового сервера 28,3 мс, плюс те же
20-30 мс самой игры.

**Туннель круга не добавляет.** 64 датаграммы в секунду по 300 байт, 20 с, эхо
на узле A: через туннель узла B p50 54,5 мс, а сумма плеч - 26,3 до узла B и
28,7 от узла B до A сырым UDP. Потерь нет ни на одном из трех замеров.

**Путь до узла B зависит от портов потока.** 16 сырых UDP-потоков с разными
портами источника и 16 ассоциаций туннеля, 10 датаграмм в секунду по 200 байт,
4 с, эхо на самом узле:

| | Быстрый путь (p50 26-35 мс) | Медленный путь (p50 52-57 мс) |
|---|---:|---:|
| узел B, сырой UDP | 9 | 7 |
| узел B, туннель | 13 | 3 |

ICMP до узла B всегда идет быстрым путем. У узла C все 16 потоков легли в
51-53 мс, у узла A - в 48-59 мс без разделения на две группы. Медленный путь длиннее ровно на
круг до узла, то есть это другой маршрут, а не очередь, и выбирается он по
5-tuple: каждая новая ассоциация - новый порт native и новая попытка. Матч на
медленном пути получает 54 + 28 = 82 мс сети и около 110 мс в игре, что и
показал второй матч. Одновременный замер пакетами 1000 байт дал ту же картину на
одном узле: сырой поток лег на медленный путь (p50 54,2 мс), туннель - на
быстрый (28,1 мс).

**Выброс с сервера.** Матч начался через узел A и был переведен на узел B в
середине: прокси-ядро при смене узла закрыло поток, игра продолжила слать с
того же сокета, и поток открылся заново через новую ассоциацию, то есть
игровой сервер увидел игрока с другого адреса. За следующие 3 минуты
прокси-ядро насчитало на этом потоке 2,4 КБ вверх и 12 МБ вниз. Через 3 минуты
игра открыла новый сокет, через 7-8 минут игрока выбросило. В это же время
долгая ассоциация пробы через узел B отвечала с p95 36-40 мс и теряла 0-1
запроса из 120 в минуту, то есть путь до узла B был исправен. Не установлено,
не пережила ли игра смену адреса или клиент потерял верхнее направление
пересозданной ассоциации: клиент писал лог на уровне warn, сервер - только
старт.

**Путь к узлу A сменился за полчаса.** Через 30 минут после замера выше круг
до узла A по ICMP вырос с 42 до 47 мс, и с того же момента путь теряет вниз
около 11% датаграмм 1000 байт: 11,3% сырым UDP и 11,1% через туннель, пробы на
маршрутизаторе теряли 4-28 запросов из 120 в минуту. Туннель снова теряет
столько же, сколько прямой путь. Вывод "для игры узел A лучше" держался на
одном замере и на этом пути верен не всегда.

**Что из этого следует для клиента.** На пути, который делит потоки по
портам, качество native-ассоциации определяется при ее открытии и дальше не
меняется. Пробы пути уже меряют srtt, поэтому клиент мог бы открыть native с
нескольких портов и оставить самый быстрый; сейчас этого нет. Смена узла в
середине матча меняет адрес игрока для игрового сервера, и узел лучше
переключать между матчами.

## Как повторить

На сервере (порт открыт только на время замера, отдается случайный blob):

```bash
head -c 50000000 /dev/urandom > /tmp/blob.bin
python3 -m http.server 38080 --bind 0.0.0.0 &
/tmp/udpprobe -echo 0.0.0.0:39999 &
```

С клиента:

```bash
ping -c 10 <сервер>
curl -s -o /dev/null -w '%{speed_download}\n' http://<сервер>:38080/blob.bin
curl -s -o /dev/null -w '%{speed_download}\n' \
     --socks5-hostname 127.0.0.1:<порт клиента> http://<сервер>:38080/blob.bin
udpprobe -target <сервер>:39999 -n 200 -interval 20ms -label direct
udpprobe -target <сервер>:39999 -socks 127.0.0.1:<порт> -n 200 -label tunnel
```

Прогоны обязательно чередовать: канал клиента общий с остальным трафиком, и
два подряд замера одной стороны меряют не туннель, а соседа по каналу. Стенд
после замера убирать - открытый HTTP на публичном интерфейсе это лишняя
поверхность, а `blob.bin` занимает 50 МБ на диске сервера.
