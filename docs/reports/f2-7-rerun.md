# Ф2-7. Повторный боевой прогон: баг 1 закрыт, а не объяснен

Задача Ф2-7 требует воспроизвести сценарий полевого отчета
([`reports/v1.4.4-field-run.md`](v1.4.4-field-run.md)) на боевом стенде с включенным
Debug и работающими счетчиками отказов. Условие приемки: ноль зависаний на
50 соединениях и в метриках видно, что отказов обфускации не было.

Прогон 19.09.2026. Сервер - боевой VPS (1 vCPU, 967 МБ RAM),
отдельный контейнер `s5core:bench` рядом с рабочим сервисом, `LOG_LEVEL=debug`,
экспортер метрик на localhost. Клиент - `cmd/s5client` на том же VPS.

## Почему клиент на сервере, а не в клиентской сети

Первая попытка шла из клиентской сети и провалилась не из-за продукта:
путь от этой сети до VPS отбрасывал первый пакет обфусцированного
соединения, и клиент не мог установить туннель вообще. Это измерено отдельно и
описано в [`field/stealth.md`](../field/stealth.md); там же показано, что
SOCKS5 открытым текстом и прямой HTTP с того же адреса в то же время шли без
единого отказа.

Для Ф2-7 такой путь непригоден: задача проверяет продукт, а не сеть между
клиентом и сервером. Поэтому клиент запущен на самом VPS и ходит на внешний
адрес того же VPS - весь стек продукта участвует целиком (обфускация,
кадрирование, SOCKS5, релей), исключен только участок публичной сети.

## Что прогонялось

| Прогон | Соединений | Объем на соединение | Результат |
| --- | --- | --- | --- |
| 5 раундов подряд | 50 | 4 МБ, скачивание | 0 отказов, 436-569 Мбит/с, 2,8-3,7 с на раунд |
| длинный, скачивание | 50 | 32 МБ | 0 отказов, 473 Мбит/с, 27,1 с |
| длинный, отдача | 50 | 32 МБ | 0 отказов, 429 Мбит/с, 29,8 с |

Инструмент - `cmd/wirebench`, полезная нагрузка несжимаемая, keep-alive
выключен, то есть каждое соединение проходит полный цикл установки.

## Что показали метрики

Счетчики сняты после всех прогонов, сервер поднят непосредственно перед ними,
то есть значения относятся только к этому прогону:

```
s5core_connections_total{transport="obfs"}                    350
s5core_client_connections_total{client_version=...}           350
s5core_connections_active{transport="obfs"}                     0
s5core_obfs_handshake_failures_total                    отсутствует
s5core_session_transitions_total{illegal="true"}        отсутствует
```

Переходы состояний сошлись ровно: 350 раз `accepted -> handshake`,
`handshake -> dialing`, `dialing -> relay`, `relay -> half_closed`,
`half_closed -> closed`. Ни одного отвергнутого перехода, ни одного отказа
обфускации, ни одной незакрытой сессии. В логе сервера за весь прогон
0 записей уровня ERROR и WARN и 350 записей DEBUG о представившихся клиентах.

Отсутствие метрики `s5core_obfs_handshake_failures_total` - не пропуск в
снятии: счетчик создается при первом отказе, и до него его в выводе нет.

## Вывод

Условие приемки выполнено: 350 соединений через обфусцированный туннель,
из них 250 в пачках по 50 одновременно, ноль зависаний, ноль отказов
обфускации, ноль незакрытых сессий.

Механика бага 1 (потеря склеенного CONNECT) была объяснена и исправлена
раньше; этот прогон - подтверждение на стенде, которого требовала задача.
Баг 1 закрыт.

## Оговорка снята: тот же прогон через публичную сеть

Разбор выше кончался тем, чего он не покрывал: участка публичной сети между
клиентом пользователя и сервером. Клиент стоял на самом VPS именно потому, что
из клиентской сети туннель не устанавливался вовсе.

После кодированного открытия (раздел 3.5 [спецификации](../veil-spec.md))
этого препятствия нет, и прогон повторен оттуда, откуда он изначально и
должен был идти - из клиентской сети на узел, через тот самый путь:

| Прогон | Соединений | Объем | Результат |
| --- | --- | --- | --- |
| 3 раунда, скачивание | 50 | 4 МБ | 0 отказов, 176-316 Мбит/с, 5,1-9,1 с на раунд |
| 2 раунда, отдача | 50 | 4 МБ | 0 отказов, 312-389 Мбит/с, 4,1-5,1 с на раунд |

Счетчики до и после (сервер работал с прошлых замеров, поэтому считается
разность, а не абсолютное значение):

```
s5core_connections_total{transport="obfs"}           178 -> 428   (ровно 250)
s5core_obfs_handshake_failures_total                  45 ->  45   (не изменился)
s5core_session_transitions_total{illegal="true"}     отсутствует
```

45 отказов в счетчике - наследство соседнего замера, где второй клиент
намеренно ходил с сырым прологом ([`field/stealth.md`](../field/stealth.md));
на этих 250 соединениях счетчик не сдвинулся ни на единицу. В логе сервера за
время прогона - 320 записей DEBUG и ни одной уровня WARN или ERROR.

Первый раунд медленнее остальных (176 против 310-316 Мбит/с) - это разгон
окна TCP на 50 одновременных соединениях, а не отказ: `failed 0` во всех
раундах, медиана на соединение одинакова (1,75-1,83 МБ/с).

Итого условие приемки Ф2-7 выполнено дважды и на двух разных путях: 350
соединений с клиентом на сервере и 250 соединений через публичную сеть с
машины пользователя. Оговорки не осталось.
