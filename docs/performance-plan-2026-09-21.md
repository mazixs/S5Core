# План ускорения S5Core и снижения задержек

Дата: 2026-09-21. Область: `s5client`, `s5core`, SOCKS5, obfs, WSS, DNS, HTTPS и учет нагрузки.

Исполнение плана и отдельные выпускные условия: [отчет 2026-09-22](reports/performance-implementation-2026-09-22.md). Числа ниже относятся к исходным прототипам; измерения конечной реализации приведены в отчете.

**Первое изменение для реализации: отдавать payload нескольких полностью полученных obfs-кадров в одном `Read`, не ожидая новых сетевых данных.** На текущем коде это подтверждено отдельным прототипом: полный HTTPS-ответ 8 МиБ передается через obfs в 2,1-2,5 раза быстрее, через WSS на 22-34% быстрее в локальном тесте. Изменение не требует другого шифра или формата кадров. Для маленьких ответов ускорение в этой серии не установлено.

Для снижения задержки новых соединений следующие действия зависят от измеренной фазы: убрать лишний обмен greeting при авторизации ключом участника, устранить повторное медленное разрешение DNS, затем разбирать задержки TCP/TLS. Процент ускорения рабочего маршрута заранее неизвестен. Ниже зафиксированы конкретные изменения и условия, при которых каждое из них следует принимать.

## 1. Проверенная база и границы результата

- Проверялось **рабочее дерево**, включая незакоммиченные исправления H01-H05 и R01, поверх `c0f137a9f79b748dd5bb8f24a0c1d7559cb4d890`. Один SHA коммита не описывает измеренный код.

- [Исходное состояние Git](benchmarks/performance-plan-2026-09-21/git-status-before.txt) и [SHA-256 всех 458 исходных файлов снимка](benchmarks/performance-plan-2026-09-21/baseline.json) сохранены. В конце подготовки плана проверено отсутствие изменений этих файлов.
- Все эксперименты выполнялись в `/tmp/s5core-performance-plan-20260921/repo` через Go overlay. В рабочий код оптимизации не внесены. В репозитории добавлены этот план и текстовые материалы его проверки. Коммит, push и развертывание не выполнялись.

## 2. Что показали новые измерения

### 2.1. Объединение готовых данных после расшифровки

Сейчас [`conn.Read`](../pkg/obfs/conn.go) возвращает результат одного `readFrame`. Даже если `ensure` уже загрузил несколько целых кадров, следующий кадр отдается отдельным `Read`. В [`handleClient`](../cmd/s5client/main.go) и серверном relay это приводит к множеству мелких записей в следующий сокет. Встроенное объединение исходящих obfs-кадров эту проблему на принимающей стороне не решает.

В прототипе после первого payload читаются только **полностью имеющиеся в памяти** следующие кадры, пока есть место в буфере вызывающего кода. Неполный заголовок или тело следующего кадра немедленно заканчивают текущий `Read`. Дополнительного сетевого чтения, таймера накопления или изменения padding нет.

| Контрольный механизм, полезные данные 1 МиБ | Текущий код | Прототип |
| --- | ---: | ---: |
| Вызовы `destination.Write` при `io.CopyBuffer` | 856 | 108 |
| Средний payload одной записи | 1225 байт | 9709 байт |
| Полнота и SHA-256 | Совпадают | Совпадают |

Число вызовов сократилось на 87,4%. Это счетчик вызовов `Write` в проверочной фикстуре, **не измерение количества системных вызовов**. Реальная группировка зависит от доставки TCP и размера буфера.

Следующая таблица показывает медиану шести медиан полного времени HTTPS-ответа. Это download 8 МиБ по HTTP/1.1 через настоящий локальный SOCKS-клиент, сервер и TLS origin. Скорость рассчитана по полному времени запроса, включая setup в сценарии нового соединения.

| --- | --- | ---: | ---: | ---: | ---: |
| obfs | Новое | 23,851 | 11,162 | 53,2% | 335,4 / 716,8 |
| obfs | Повторное использование | 23,508 | 9,244 | 60,7% | 340,3 / 865,5 |
| WSS | Новое | 28,976 | 23,783 | 17,9% | 276,1 / 336,4 |

В `benchstat` для четырех ускорившихся сценариев `p=0.002`, `n=6` на вариант. Входные наблюдения здесь - **медианы отдельных прогонов**, а не все запросы, ошибочно объявленные независимыми измерениями. Общий geomean разнородных сценариев для решения не используется.

У малого ответа 23 байта значимого изменения не обнаружено: например, obfs с новым соединением 1,823 -> 1,833 мс, WSS 2,512 -> 2,517 мс. Из этой выборки нельзя заключить, что p99 на рабочем маршруте гарантированно останется прежним.

Повторная серия с реальным **OpenTelemetry SDK**, а не noop provider, дала тот же результат. Использован ManualReader, без одновременного Prometheus scrape:

| Путь, 8 МиБ | Новое соединение, до / после | Reuse, до / после |

Профиль всей этой серии согласуется с механизмом: CPU samples 39,41 -> 32,68 CPU-секунды; flat samples в `linux.Syscall6` 17,50 -> 11,73. Это один профиль на вариант, включающий оба прокси, origin, клиента нагрузки, TLS и проверку SHA-256. Его нельзя выдавать за изолированное снижение CPU сервера на 17%. Около 96% `alloc_space` приходится на `io.ReadAll` **в измерительной фикстуре**, поэтому этот профиль не доказывает проблему памяти самого S5Core.

### 2.2. Буфер записи WebSocket

[`NewUpgrader`](../pkg/transport/ws/upgrader.go) не задает `WriteBufferSize`. В используемой Gorilla WebSocket v1.5.3 сервер может переиспользовать буфер `net/http` размером 4096 байт. После резерва под заголовок для payload остается 4082 байта. Shaping допускает куски до 4096, поэтому часть записей идет через путь с дополнительными выделениями памяти.

Второй, независимый прототип устанавливает `WriteBufferSize: DefaultMaxFrame`, то есть 4096 байт payload. Gorilla выделяет место с учетом своего заголовка. Shaping и размер WebSocket-сообщений остаются прежними.

| Shaped WS, сервер -> клиент, без TLS | Время записи с доставкой | Выделения памяти на операцию |
| --- | --- | --- |
| 1422 байта | 10,46 -> 10,13 мкс, изменение незначимо | 23 -> 23 байта; 2 -> 2 allocs |
| 22752 байта, размер типичного batch | 27,80 -> 27,11 мкс, -2,47% | 106 -> 55 байт; 8 -> 6 allocs |
| 1 МиБ, граничный случай | 1,080 -> 1,033 мс, -4,37% | 744 -> 256 allocs |

Шесть прогонов по 300 мс на сценарий, успешная доставка включена в замер. Большая экономия на записи 1 МиБ не описывает обычный размер batch в obfs. Это основание для небольшой отдельной оптимизации, не обещание аналогичного прироста всего WSS. Цена создания соединения и память удерживаемого write buffer этим benchmark не измерены.

Источники: [benchstat](benchmarks/performance-plan-2026-09-21/ws-benchstat.txt), [прототип](benchmarks/performance-plan-2026-09-21/ws-buffer.patch), [фикстура](benchmarks/performance-plan-2026-09-21/ws_buffer_test.go.txt). Поведение буферов также описано в [документации Gorilla](https://pkg.go.dev/github.com/gorilla/websocket#hdr-Buffers).

### 2.3. Условия и ограничения эксперимента

Go 1.26.6, Linux amd64, Intel i7-11700K, 16 логических CPU, стандартный GOMAXPROCS=16. MTU 1400, padding до 256, shaping WSS 256-4096, jitter=0. Для больших ответов в каждом прогоне 15 запросов, для маленьких 50; перед каждой серией 3 прогрева. Проверяются HTTP status, размер и SHA-256 тела. Время включает чтение тела, SHA-256 проверяется после фиксации времени. Origin использует тестовый сертификат; внешняя WSS-цепочка доверяет отдельному тестовому CA.

Сначала выполнены шесть baseline-прогонов, затем шесть прогонов с overlay; порядок путей внутри теста фиксирован. Direct/plain служат контролем дрейфа. Серия SDK дополнительно выполнялась с профилированием. Эти две серии нельзя смешивать в одну статистическую выборку. Benchmark не запускался одновременно с race или сборкой.

Измерения не покрывают рабочий ARM-роутер, потери, ограниченную полосу, множество одновременных клиентов, user/pass и квоты в performance-сценарии. Краткий HTTPS-тест не оценивает долгосрочный p99. Совместный эффект двух прототипов еще не измерен; проценты складывать нельзя. Исторические [замеры ARM](benchmarks/arm-router.md) полезны как схема стенда, но их числа не являются baseline текущего дерева.

### PERF-00. Сделать эффект проверяемым на нужном оборудовании

**Файлы:** [`cmd/httpsprobe`](../cmd/httpsprobe/main.go), [`cmd/wirebench`](../cmd/wirebench), [`internal/socks5/phase.go`](../internal/socks5/phase.go), [`pkg/s5server/telemetry.go`](../pkg/s5server/telemetry.go), стенд в `docs/benchmarks/`.

1. Зафиксировать версии клиента/сервера, хеш рабочего дерева, CPU и крипторасширения, GOMAXPROCS, лимиты контейнера, MTU/padding/shaping, режим auth, DNS и маршрут. Числовой IP назначения и FQDN проверять отдельно: IP исключает DNS только назначения, не обязательно адреса WSS-сервера.
2. Снять baseline тремя процессами: генератор с HTTPS origin отдельно от `s5client` и `s5core`. Сохранить CPU-seconds/GiB и RSS каждого процесса, wire bytes/useful bytes, распределения setup, TLS, HTTP TTFB, total, скорость, ошибки и retransmits. Для роутера отдельно измерять CPU процесса и CPU системы с softirq.
3. Использовать уже существующий `httpsprobe`, собирающий настоящее время первого HTTP-ответа. Серверный `first_byte` часто означает первый TLS-байт и не является HTTPS TTFB. `connect_setup_ms` включает SOCKS и удаленный DNS; серверная фаза `dns` помогает отделить DNS. Не складывать пересекающиеся интервалы trace.
4. Для profiling запускать отдельный диагностический build/стенд с явными `pprof.StartCPUProfile`, alloc, mutex и block profiles. В текущем metrics mux нет автоматически опубликованного pprof. Не добавлять profiling handlers на публичный metrics-порт. Профили client/server собирать раздельно; SHA-256 генератора нагрузки не должен становиться целью оптимизации прокси.
5. Сравнивать baseline/candidate в чередующемся порядке A/B/B/A, минимум 6 независимых прогонов. Для приемки p99 коротких запросов собрать не менее 10000 наблюдений на вариант и сценарий, оценить доверительный интервал с учетом отдельных прогонов; для длительной передачи минимум 30 секунд steady state. Учитывать прогрев DNS/TLS отдельно. Контроль direct/plain запускать в каждом блоке.

Первый smoke на контролируемом HTTPS-origin, без внешнего случайного сайта:

```bash
go build -o /tmp/s5-httpsprobe ./cmd/httpsprobe
/tmp/s5-httpsprobe -url https://controlled-origin.example/small -count 1000 -http2=false > /tmp/direct.jsonl
/tmp/s5-httpsprobe -url https://controlled-origin.example/small -socks 127.0.0.1:1080 -count 1000 -http2=false > /tmp/proxy-new.jsonl
/tmp/s5-httpsprobe -url https://controlled-origin.example/small -socks 127.0.0.1:1080 -count 1000 -reuse -http2=true > /tmp/proxy-reuse.jsonl
```

Адрес в примере заменяется адресом собственного стенда; 1080 означает локальный s5client выбранного транспорта. Зонд умеет последовательные GET, но не заменяет инструмент для конкурентной нагрузки, upload и UDP. HTTP/2 проверять по выведенному `protocol`, а не только по разрешающему флагу.

**Готовность этапа:** получены baseline и доли задержки по фазам; можно определить, что ограничивает конкретный режим: CPU, сеть, DNS, TCP connect, TLS или origin. Предлагаемые пороги приемки ниже - критерии будущей работы, а не уже измеренные production SLO. Официальные инструменты profiling описаны в [Go diagnostics](https://go.dev/doc/diagnostics).

### PERF-01. Уменьшить число передач данных между слоями

**Файл:** [`pkg/obfs/conn.go`](../pkg/obfs/conn.go), функции `Read`, `readFrame`, `ensure`, поля `readBuf`, `readRest`, `readCounter`. Текущая точка входа `Read` находится около строки 925. Потребители: `handleClient`, `metricsConn.WriteTo`, metered relay.

**Реализация:**

1. Под существующим `readMu` получить первый payload штатным `readFrame`.
2. Пока в выходном буфере осталось место, отдать `readRest`, затем обрабатывать только целые кадры, уже находящиеся в `readBuf`. Наличие заголовка еще не означает наличия полного тела; размер определяется с текущим counter/mask.
3. Если после первого payload следующего полного кадра нет, немедленно вернуть прочитанное. Не вызывать `ensure` с недостаточным количеством данных, не ждать заполнения 32 КиБ и не добавлять flush timer.
4. Сохранить счетчики, replay/AEAD-проверки, обработку FIN, keepalive, hello/advice и события frame observer для каждого обработанного кадра. Корректно возвращать `n>0` вместе с EOF/ошибкой; проверить дальнейшее поведение после terminal error. Нулевой буфер, маленькие чтения и остаток payload должны оставаться корректными.
5. Не менять размер кадра, выбор шифра, padding и внешнее shaping. Повторное вычисление length mask в прототипе сначала оставить как есть; устранять его отдельно только при подтвержденной стоимости и сохранении инвариантов счетчика.

**Что уже прошло:** [весь `go test -race ./...`](benchmarks/performance-plan-2026-09-21/coalesce-race.txt) с overlay; проверки целостности HTTPS; [отдельная проверка](benchmarks/performance-plan-2026-09-21/coalesce-targeted.txt), что следующий кадр с доступными 0, 1, 2 или 9 байтами не вызывает дополнительного чтения после готового payload. Это проверки прототипа, не завершенная приемка промышленной реализации.

**Дополнительная приемка:**

- Small-read 1/2/127 байт, payload больше буфера, много кадров одним TCP-read и один кадр многими TCP-read; FIN после данных; keepalive/control между данными; поврежденный tag после корректного payload, truncation, неизвестный kind, replay, `n>0,error` через `io.Copy`, `io.ReadFull` и bufio. Нет потери/дублирования байтов и busy loop.
- Все сценарии H01-H05/R01 остаются зелеными: активный download/upload >30 секунд, настоящий idle, абсолютный FrameBody deadline, остановка keepalive, отмена dial, два кандидата максимум, half-close, quota и отзыв аккаунта.
- Локальный исходный стенд: целевой минимум +25% throughput obfs и +10% WSS на 8 МиБ либо эквивалентное уменьшение CPU-seconds/GiB при насыщенном канале. Это консервативный порог относительно прототипа.
- На ARM и VPS: нет повторяемого ухудшения p95/p99 малого ответа более `max(5%, 1 мс)`, нет потери пропускной способности более 3%. Проверить p99 малого запроса одновременно с большой загрузкой.
- Совместимость: старый клиент / новый сервер и новый клиент / старый сервер. Downstream-группировка может влиять на размер следующих записей и тайминг даже при неизменном формате; прогнать существующие wire/shaping/fingerprint-тесты.

При download основная выгода ожидается на чтении в s5client, при upload - на чтении в s5core. Это вывод из направления данных; отдельные численные A/B для обновления только одной стороны пока не сняты. Выпускать обе стороны, сохранив возможность независимого отката бинарей.

### PERF-02. Устранить промах по емкости WebSocket write buffer

**Файл:** [`pkg/transport/ws/upgrader.go`](../pkg/transport/ws/upgrader.go), `NewUpgrader` около строки 33. Использовать явный `WriteBufferSize: DefaultMaxFrame`. Не менять `WS_MAX_FRAME` ради этого исправления.

Проверить стандартное значение 4096 и нестандартные пользовательские пределы shaping. Большие кадры остаются допустимыми, даже если не помещаются целиком в буфер. Для произвольного очень большого `WS_MAX_FRAME` не выделять автоматически такой же постоянный буфер без ограничения памяти.

**Приемка:** `22752 B` сохраняет уменьшение allocs/op хотя бы на одну аллокацию; p95/p99 и throughput настоящего WSS не ухудшаются. Повторить full HTTPS, upload, TLS/uTLS, certificate/pinning, read limits, concurrent write и wire histogram. Отдельно измерить создание соединений и RSS на 1000/10000 idle connections: новый буфер перестает переиспользовать старый и может увеличить постоянную память. Если стоимость существенна, проверить ограниченный `WriteBufferPool` отдельным A/B; не добавлять pool автоматически.

Все существующие [тесты пакета WS с race](benchmarks/performance-plan-2026-09-21/ws-race.txt) на прототипе прошли. Совместный performance-замер PERF-01 + PERF-02 является обязательной следующей проверкой.

### PERF-03. Уменьшить стоимость нового соединения

**3A. Member-auth без лишнего greeting RTT.** В [`dialObfsTunnel`](../cmd/s5client/main.go) около строки 778 заполненный `PROXY_USER` включает ожидание ответа greeting до отправки CONNECT. Даже если одновременно задан member key и сервер выберет NoAuth на основании проверенной личности, CONNECT уйдет только после этого ожидания. В [`authenticate`](../internal/socks5/auth.go) сервер уже умеет проверять актуальную доступность member-аккаунта.

Сначала проверить конфигурацию. На сервере с поддержкой member-auth, при действительных `OBFS_MEMBER_ID` и `OBFS_MEMBER_KEY`, клиенту, которому не нужен password fallback, достаточно убрать `PROXY_USER/PROXY_PASS`: существующая ветка отправит greeting+CONNECT сразу. `RequireAuth` сервера при этом не отключать. Это потенциальная экономия **одного RTT client-server при новом туннеле**, а не каждого ping существующей сессии.

Для кодового улучшения оформить явный режим member-only с fail-closed при отказе ключа и ошибкой противоречивой конфигурации. Совместимый password-fallback оставить отдельным режимом с документированной ценой RTT. Не переключать режим молча по наличию строки ключа. Проверить действительный, отозванный, просроченный ключ, квоту, старый сервер и требующий user/pass сервер.

**Приемка:** при управляемом RTT 20/50/100 мс соответствующее уменьшение setup примерно на один RTT только у подходящих новых соединений; неизменные отказы при недействительных credentials. Если конфигурация уже использует pipelined NoAuth, этот пункт не даст ускорения и дополнительный pipeline не нужен. Cold Argon2id измерять отдельно от cache hit; параметры хеширования не ослаблять.

**3B. Повторные WSS handshakes.** В [`ws.DialContext`](../pkg/transport/ws/dialer.go) и [`internal/utls/DialContext`](../internal/utls/dialer.go) обычный путь создает новую TLS-конфигурацию; s5client не передает общий session cache. Если в профиле доминируют новые WSS handshakes, добавить ограниченный cache, живущий на уровне client configuration, отдельно для crypto/tls и uTLS. Разделять/инвалидировать его при смене endpoint, SNI, доверенных CA, pins и fingerprint. Не менять wire fingerprint без существующей проверки совместимости.

Проверить, что `DidResume` действительно появляется, уменьшается CPU/setup, а проверка сертификата и pin сохраняется при resumed session. TLS 1.3 resumption само по себе не обещает устранить целый RTT; 0-RTT в этот план не входит. Приемочный порог: повторяемое снижение CPU нового WSS handshake хотя бы на 10% или заметное снижение setup без регрессий проверки доверия. Если профиль setup мал, работу отложить.

### PERF-04. Снизить вклад DNS

**Файлы:** [`internal/socks5/resolver.go`](../internal/socks5/resolver.go), `DNSResolver.ResolveAll`; [`request.go`](../internal/socks5/request.go), разрешение и проверка кандидатов.

Встроенный resolver вызывает `net.DefaultResolver.LookupIP` для доменных CONNECT и не хранит собственный TTL-кеш. Это не доказывает отсутствие кеша у системного DNS. Сначала сравнить повторный FQDN и числовой IP, посмотреть `phase=dns`, ответы локального resolver и его cache hit.

1. Если системный resolver уже дает быстрые cache hits, оставить текущий код.
2. Если повторный DNS занимает, например, более 5 мс или 20% setup, сначала проверить доступный локальный кеширующий resolver на стенде. Это отдельная настройка окружения, а не доказанная необходимость новой Go-библиотеки.
3. Если нужен кеш именно в SDK, расширить контракт **необязательным TTL-aware интерфейсом**, возвращающим весь набор адресов и срок действия. Старые `NameResolver/MultiNameResolver`, не возвращающие TTL, не кешировать автоматически: `LookupIP` не сообщает DNS TTL.
4. Кеш ограничить числом записей и памятью, учитывать пространство DNS-конфигурации, возвращать независимую копию адресов; совпадающие запросы объединять. Отмена одного waiter не должна отменять остальных. Общий lookup имеет собственный верхний бюджет и прекращается при отсутствии потребителей. Timeout/SERVFAIL не превращать в долгий отрицательный кеш; NXDOMAIN кешировать только при достоверном сроке отрицательного ответа.
5. Кешировать результат разрешения, а не решение ACL. Rules и Rewriter должны проверяться после cache hit в прежнем порядке. Не потерять все A/AAAA, общий deadline, ограничение двух dial и минимум попытки R01. Для legacy resolver с возвращаемым context нельзя сохранять чужие request values и отмену в общем кеше.

**Приемка:** cold/hot DNS, смена адреса по TTL, истечение, NXDOMAIN, временная ошибка, массовый miss, отмена waiter, смена DNS-конфигурации, Rules/Rewriter и IPv6 blackhole. Фазы измеряются без домена или IP в labels. Снижение setup на hit должно соответствовать убранному DNS-времени; bulk throughput уже открытой сессии от этого не увеличится.

### PERF-05. Устранить оставшиеся затраты по профилю

Работы ниже не следует выполнять все сразу. Для каждой сначала снять профиль после PERF-01 на целевой нагрузке и оценить достижимый выигрыш. Наличие mutex или цикла само по себе не делает его узким местом.

| Наблюдаемая проблема | Точка в коде | Конкретное действие | Условие принятия |
| --- | --- | --- | --- |
| Всплески latency во время flush/scrape | `Store.FlushTraffic`, `Store.SessionStatus`, `Registry.Snapshot` | Сначала объединить два соседних `RLock` чтения account в `SessionStatus`; при доказанной блокировке глобального store рассмотреть immutable/atomic policy snapshot. Для registry сравнить копирование указателей под lock с подсчетом вне lock | Mutex/block profile связывает ожидание с запросами; p99 лучше; удаление аккаунта и quota продолжают действовать; память snapshot ограничена |
| Per-chunk telemetry занимает заметную долю CPU | `metricsConn.Read/Write`, session/frame observers | Разделить стоимость byte counters, состояний и histogram. Для byte metrics проверить локальное накопление с ограниченным периодом публикации и финальным flush | Экономия CPU >=5%; сохранены totals после close, активная наблюдаемость и ограниченная задержка публикации; quota и billing не переведены на отложенный учет |
| Deadline lock/установка сроков стали hotspot | `timeoutConn.Read/Write`, `Session.ReadDeadline` | Сначала убрать только повторную установку **точно совпадающего** deadline. Любое укрупнение сроков проектировать отдельно с явной верхней границей | H01 и абсолютный FrameBody проходят; idle/grace/отмена не увеличены молча; измеренный CPU выигрыш |
| Большие списки доменных маршрутов замедляют CONNECT | `matchDomain` в s5client около строки 993 | Lowercase, trim и IDNA patterns один раз при чтении конфигурации; exact map + проверка суффиксов по границам DNS-label. FQDN нормализовать один раз | Benchmark 0/10/1000/10000 правил; wildcard, базовый домен и IDN совпадают со старым контрактом; влияние на setup подтверждено |
| Аллокации на churn соединений | `handleClient`, `metricsConn.ReadFrom/WriteTo`, `internal/relay` | Найти фактический владелец и выбранный `ReaderFrom/WriterTo`, затем добавить pool только недостающего временного буфера с ограниченным размером | Меньше alloc bytes/connection и GC, без роста idle RSS и ухудшения throughput |

В серверном `metricsConn` pool на 32 КиБ уже есть. Простая замена `io.Copy` на `io.CopyBuffer` не гарантирует его использования: `WriterTo/ReaderFrom` имеют приоритет. Не отключать интерфейсы и возможный TCP fast path без сравнения. См. контракт [io.CopyBuffer](https://pkg.go.dev/io#CopyBuffer).

Не начинать с замены Gorilla, OpenTelemetry или uTLS. Сначала измерить затраты конкретного слоя; предложенные два прототипа работают с текущими зависимостями. Обновление библиотеки и изменение поведения проводить отдельными A/B, не смешивая их с PERF-01.

### PERF-06. PGO после стабилизации горячего пути

После предыдущих принятых изменений собрать CPU profiles **отдельно** для реальных `s5client` и `s5core`, с репрезентативным сочетанием obfs/WSS, коротких запросов, большой передачи и авторизации. Профили сравниваемых нагрузок взвешивать по реальной частоте, а не по удобству benchmark.

Собрать каждый бинарь с `-pgo=off` и с соответствующим `-pgo=/path/to/profile`. Сравнить на тех же сценариях и архитектурах, записать размер бинаря и время сборки. Профиль совмещенного HTTPS-теста из этого документа не использовать как готовый production `default.pgo`: в нем есть origin, тестовые проверки и посторонняя для каждого бинаря работа.

**Приемка:** воспроизводимое улучшение CPU-seconds/GiB или throughput минимум на 3%, без нарушения общей latency-приемки. Если эффекта нет, PGO в релиз не добавлять. Профиль должен обновляться после существенного изменения горячего пути. Требование репрезентативной нагрузки соответствует [Go PGO](https://go.dev/doc/pgo).

## 4. Общая матрица приемки и выпуск

| Измерение | Обязательные сценарии |
| --- | --- |
| Путь | direct, plain, obfs, WSS; текущая и новая версии по отдельности и вместе |
| HTTPS | HTTP/1.1 и HTTP/2, новый TLS и reuse; малый ответ, 8 МиБ, streaming >30s, upload, одновременный малый запрос и большая передача |
| Нагрузка | 1/4/16/64 активных соединения; отдельно churn и 1000/10000 idle connections при достаточных ресурсах стенда |
| CPU | amd64 и настоящий arm64; один CPU как ограниченный стенд и штатный GOMAXPROCS; выбранный шифр и crypto extensions записаны |
| Сеть | Изолированный netem-стенд: RTT 0/20/50/100 мс, loss 0/0,1/1%, полоса 10/100/1000 Мбит/с; задержка учитывается на обоих направлениях, qdisc не переполняется незаметно |
| Auth/учет | NoAuth в лаборатории, действительный member key, password cold/hot, quotas/revoke; SDK с настоящим scrape и periodic flush |
| Отказы | DNS timeout/TTL/несколько IP, IPv6 blackhole, отмена WSS, закрытие origin, медленный читатель, half-close, поврежденный кадр |

Матрица выполняется слоями: сначала локальный smoke и correctness, затем выбранные крайние комбинации WAN/нагрузки, затем профиль реального маршрута. Полное декартово произведение не требуется. Netem на рабочем интерфейсе пользователя не применять.

Решение о выпуске принимается по полным ответам и p95/p99 под нагрузкой, а не только по MB/s. ICMP ping не проходит через SOCKS5; для интерактивности измерять application echo/HTTP TTFB. UDP через TCP отдельно проверять на loss: блокировка следующих данных при потере TCP-сегмента не устраняется заменой AEAD или размером буфера. Переход на другой транспорт потребует самостоятельного проекта и проверки свойств маскировки.

**Общие критерии:**

1. Нет поврежденных/неполных тел, новых ошибок, утечек соединений/горутин или обхода auth/ACL/quota. Корректны все ранее исправленные deadline и fallback-сценарии.
2. Малые запросы: нет повторяемого ухудшения p95/p99 больше `max(5%, 1 мс)` в сопоставимом сценарии; особенно во время bulk, scrape и flush. Зафиксирован источник каждого выброса.
3. Для сетевого потолка оценивается экономия CPU, а не обещается скорость выше канала. Throughput не проседает более 3% ни в одном обязательном сценарии. Регрессия памяти более 5% требует отдельного объяснения и проверки абсолютного бюджета целевого устройства.
4. Для реализации проходят `./scripts/pre-commit.sh` и release-кросс-сборки двух бинарей: linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, windows/amd64. Кросс-сборка не заменяет runtime/performance на ARM.
5. Изменения принимаются раздельно: baseline -> PERF-01 -> PERF-02 -> нужные setup/DNS/профильные изменения -> PGO. На каждом шаге измеряется предыдущая принятая версия; суммирование процентов из независимых A/B запрещено.
6. После лабораторной приемки отдельный ограниченный canary на рабочем маршруте. Сохранены предыдущие бинарь и конфигурация; откат при ошибке целостности, auth/ACL/quota, новых timeout или устойчивом нарушении latency-порогов. Сравнение охватывает пик нагрузки и несколько flush/scrape циклов. Локальный зеленый тест не считается выпуском.

## 5. Что не использовать как способ ускорения

- Не возвращать старые directional idle timeouts и не увеличивать все таймауты: это скрывает задержку и может вернуть обрывы HTTPS.
- Не менять шифр вслепую: аппаратный выбор уже есть. Текущий подтвержденный выигрыш получен при прежней криптографии.
- Не отключать padding/shaping, проверки сертификата, pinning, auth, учет или квоты ради benchmark. Их стоимость должна оставаться в целевом режиме.
- Не увеличивать MTU и socket buffers глобально без измерения памяти, tail latency и wire-совместимости. Размер obfs-кадра и IP MTU - разные величины.
- Не объединять произвольные уже установленные SOCKS CONNECT к разным назначениям в общий HTTP connection pool: клиентский origin TLS и адресная политика принадлежат конкретному потоку.
- Не называть удаление мертвого кода или обновление зависимостей доказанной performance-оптимизацией, пока они не затрагивают измеренный горячий путь.
