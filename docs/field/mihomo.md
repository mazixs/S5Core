# Встраивание в mihomo без поддержки с его стороны

mihomo не знает протокола s5core и знать его не должен. `s5client` - это
локальный SOCKS5-прокси: снаружи обычный RFC 1928, внутри обфусцированный
туннель. Для mihomo это просто `type: socks5` на петле, то есть транспорт,
который он поддерживает с самого начала.

Отсюда все свойства схемы: патчей нет, форка нет, обновление mihomo и
обновление s5core независимы, а протокол провода можно менять (`OBFS_FORMAT`,
`OBFS_PROLOGUE`, `TRANSPORT`), не трогая прокси-ядро вовсе.

```
приложение -> mihomo (правила, перехват) -> 127.0.0.1:1089 SOCKS5
                                              |
                                          s5client
                                              |
                                    обфусцированный туннель
                                              |
                                           s5core -> цель
```

## 1. Клиент

По экземпляру `s5client` на узел, каждый на своем порту петли:

```bash
CLIENT_LISTEN_ADDR=127.0.0.1:1089 \
SERVER_ADDR=<сервер>:<порт> \
OBFS_PSK=<32 байта> \
OBFS_NODE_ID=<идентификатор узла> \
OBFS_MEMBER_KEY=<ключ участника> \
s5client
```

Переменные и их значения по умолчанию - в [справочнике конфигурации](../guides/configuration.md). Совпадать
у клиента и сервера обязаны `OBFS_PSK` и `OBFS_NODE_ID`, часы - расходиться
меньше чем на два часа. Шифр (`OBFS_CIPHER`) согласовывать не нужно: клиент
берет его по своему процессору, сервер принимает оба.

На роутере два экземпляра одного бинарника запускаются **копиями под разными
именами, а не симлинками**: busybox `pidof` сравнивает путь к исполняемому
файлу, и с симлинком init-скрипты двух экземпляров видят чужой процесс своим.

## 2. Конфигурация mihomo

```yaml
proxies:
  - name: "S5CORE-A"
    type: socks5
    server: 127.0.0.1
    port: 1089
    udp: true          # обязательно, см. раздел 3

  - name: "S5CORE-B"
    type: socks5
    server: 127.0.0.1
    port: 1090
    udp: true

proxy-groups:
  - name: "PROXY"
    type: select
    proxies: ["S5CORE-A", "S5CORE-B"]
```

Аутентификация в SOCKS5 не нужна: участник опознается туннелем по
`OBFS_MEMBER_KEY` еще до рукопожатия SOCKS5, и сервер отвечает `NoAuth`. Если
у аккаунта нет ключа участника и сервер требует пароль, добавьте `username` и
`password` в тот же блок.

Проверка узла отдельно от правил:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
     --socks5-hostname 127.0.0.1:1089 https://cp.cloudflare.com/generate_204
```

## 3. UDP

`udp: true` обязательно. Без него mihomo отправит UDP мимо прокси, и это
ровно та утечка, от которой защищает туннель.

Сам UDP идет внутри TCP-туннеля: mihomo шлет обычный SOCKS5 UDP Associate
(`0x03`), `s5client` переписывает команду в `0x83` и мультиплексирует
датаграммы в тот же туннель. Отдельного UDP-пути в обход туннеля нет
намеренно. Цена решения измерена: медиана не меняется, растет только хвост и
только там, где на пути есть потери
([`benchmarks/udp-over-tcp.md`](../benchmarks/udp-over-tcp.md),
[`nodes.md`](nodes.md)).

## 4. Перехват на роутере

Главный вывод полевого замера
([`nodes.md`](nodes.md), раздел "что уходит мимо туннеля"): **перехватывать
надо весь диапазон портов**, а решать "что идет напрямую" - на стороне mihomo
по домену, ASN или стране.

Номер порта про трафик не говорит ничего:

- на одном номере живут разные вещи (UDP 10000 - и STUN, раскрывающий адрес,
  и медиа Jitsi);
- WebTransport ходит поверх HTTP/3, то есть по UDP на произвольном порту, и
  сервис проверки на нем читает настоящий адрес, пока перехвачен не весь
  диапазон - при этом обычный WebRTC-тест на 3478 и 19302 показывает путь
  чистым;
- дырка в списке портов касается не только UDP: с открытым портом 22 SSH
  уходил напрямую.

Если прошивка задает диапазон списком, "весь диапазон" указывается явно
(`1:65535`): при пустом списке она подставляет в исключения проброшенные
порты роутера, и утечка возвращается через них. Входящие пробросы полный
перехват переживают, если цепочка перехвата первым делом делает `RETURN` по
`conntrack --ctstate DNAT`.

## 5. Порядок правил

Правило вида "страна клиента - напрямую" в конце набора отдает прямой путь
любому серверу с адресом этой страны, включая STUN-сервер. Локальные сервисы
проверки IP этим и пользуются. Поэтому STUN и TURN идут **до** него:

```yaml
rules:
  - DST-PORT,3478-3481,PROXY
  - DST-PORT,5349-5352,PROXY
  - DST-PORT,19302-19309,PROXY
  # ... остальные правила ...
  - GEOIP,<страна клиента>,DIRECT
  - MATCH,PROXY
```

## 6. Проверка

`scripts/leak_matrix.py` запускается с проверяемой машины (не с роутера: у
роутера свой путь наружу) и сверяет адреса по четырем осям - порт, протокол
(UDP и TCP), география сервера и версия IP:

```bash
python3 scripts/leak_matrix.py --node <адрес узла A> --node <адрес узла B>
```

С `--node` проба выносит вердикт сама и возвращает код 1, если ответ пришел с
адреса, которого в списке узлов нет.

Вердикт выносится по адресу, а не по конфигурации. Правило mihomo,
отбрасывающее весь UDP на порт 443, может быть живым и срабатывать, но не
видеть трафика пробы вообще, если перехват его не забирает: счетчики ядра при
этом не двигаются, а адрес наружу уходит настоящий.

## 7. Границы схемы

- mihomo видит обычный SOCKS5 и о туннеле не знает, поэтому не может
  отличить отказ туннеля от отказа цели: диагностика туннеля - в логе
  `s5client`, не в логе mihomo.
- Смена транспорта по рекомендации сервера (`TRANSPORT_ADVICE`) происходит
  внутри `s5client` и до mihomo не доходит - это свойство, а не ограничение.
- Проверка живости узла в mihomo (`url-test`) меряет весь путь целиком, а не
  туннель: порог надо ставить с запасом на RTT плеча.
