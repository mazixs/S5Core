# Raw, опубликованная 2.0.0 и текущее дерево: WAN

21.09.2026. Клиент - рабочий ARM64-роутер, цель - узел A из
[полевого стенда](../../field/nodes.md), через настоящий интернет.
Искусственная задержка, netem и внешняя CDN не использовались. Рабочие службы
не обновлялись: поднимались отдельные временные процессы с тестовой учетной
записью. После проверки они остановлены, файлы и учетные данные удалены.

## Вердикт

Продолжение: [TCP-диагностика двух дополнительных серий](tcp-diagnostics/README.md).
В них медиана current уже выше 2.0.0; просадки наблюдались у обеих версий,
с изменениями cwnd и окна приема. Следовательно, прежнее отставание не
оказалось устойчивым между сериями. WAN-UP-01 остается открытым: причина
эпизода 2,05 МиБ/с не установлена. Ниже сохранены исходные три серии.

Скачивание и медиана времени до первого байта практически совпали с 2.0.0.
**По отдаче текущая версия показала более низкую медиану в исходных трех сериях.**
Это открытый сигнал возможной регрессии; проверка пропускной способности не
считается пройденной. Причина в коде пока не установлена: прямой контроль
сильно колебался, а на малом VPS была подкачка. В последнем контроле два
тестовых сервера уже не конкурировали за память и порт был один и тот же.

Из этих результатов нельзя заключить ни "все стало быстрее", ни "потеря
отдачи точно вызвана правками S5Core". Смешанные версии не отделили причину
однозначно. Для продолжения была назначена запись TCP_INFO/ss
для самого измеряемого соединения: retransmits, RTT, cwnd, receive window,
и сопоставлять их с CPU/ожиданиями процесса. Менять код на основе придуманной
паузы вместо этого не требуется.

## Бинарники и одинаковые условия

- Клиент 2.0.0 скопирован с роутера. Build info: Go 1.26.6,
  `vcs.revision=112c4ffdd2ee941b6987f122fde6aa5235861c88`, `vcs.modified=false`,
  встроенная версия `v2.0.0`.
- Сервер 2.0.0 извлечен из работающего контейнера с образом
  `ghcr.io/mazixs/s5core:2.0.0`. Go 1.26.6 и встроенная версия `v2.0.0`;
  VCS revision в этом Docker-бинарнике не записан. ID образа сохранен в
  [cleanup.txt](cleanup.txt), SHA256 файлов - в [manifest.json](manifest.json).
- Current - локальное дерево поверх того же коммита с девятью исправлениями
  первого аудита и L21-01/L21-02. Go 1.26.6, ARM64-клиент и AMD64-сервер.
  [Build info](build-info.txt) содержит параметры обеих сборок.
- Транспорт `obfs`, формат `v1`, пролог `printable`, MTU=1400, padding=256,
  авторизация включена, временный пользователь один, MAX_CONNECTIONS=5000.
  Метрики включены штатным серверным CLI. Боевые USERS_FILE и пароли не
  копировались. Первый вход прогревался отдельной передачей.
- Измеритель во всех вариантах один: текущий `wirebench`, который проверяет
  HTTP-статус, объем скачивания, объем отправки и подтверждение upload.
  Старая версия измерителя из релиза не применялась. Его сервер получил
  только локальную обертку ограничения доступа по IP клиента/loopback.
- Случайный блок 256 КиБ повторяется до заданного объема. Компрессии в
  S5Core нет; это не тест несжимаемости для произвольного внешнего компрессора.

Каждая измеряемая передача - 128 МиБ, одно TCP-соединение. Скорость включает
установку соединения и разгон TCP; это не изолированная установившаяся
пропускная способность. Строка wirebench называет единицу MB/s, но делит на
2^20: ниже везде **МиБ/с**. Проверки/прогрев по 4 МиБ сохранены отдельно и
не включены в таблицы.

Raw идет прямо с роутера на HTTP-измеритель узла A. Туннель идет с того же
роутера на тот же VPS и обращается к тому же измерителю через loopback VPS.
Правила OUTPUT роутера и прямой маршрут проверены; proxy-переменных в среде
измерений нет. Это контроль до конкретного VPS, не оценка всего интернета.

## Основная серия

Шесть раундов: все шесть перестановок raw/v2/current, оба направления.
Серверы временно работали одновременно на разных портах. Затем 60 новых
HTTP-соединений на вариант к одному ответу размером 1 байт, также с чередованием
порядка. TTFB включает соединение, SOCKS5/авторизацию у туннеля и HTTP-запрос.
IP-адреса заданы явно, стоимость DNS здесь не измеряется.

| Режим | Скачивание, медиана (диапазон), МиБ/с | Отдача, медиана (диапазон), МиБ/с | TTFB p50 / p95, мс |
| --- | ---: | ---: | ---: |
| Raw | 32,65 (27,26-50,94) | 45,34 (31,66-52,20) | 87,93 / 101,97 |
| 2.0.0 | 38,52 (36,43-43,35) | 40,62 (33,62-47,84) | 177,68 / 218,48 |
| Current | 38,44 (27,01-41,98) | 33,15 (12,57-45,93) | 177,54 / 200,55 |

В этой серии отдача current ниже по отношению медиан на 18,4%. Это
описательная разница, не доказанный размер регрессии кода. В парных раундах
разница current/v2 менялась от -65,0% до +36,0%.

Максимальный TTFB: raw 200,94 мс, v2 1224,47 мс, current 242,55 мс. Один
выброс v2 не объявляется устраненным дефектом. P99 по 60 запросам не используется
как приемочный показатель. Все 36 измеряемых передач и 180 запросов завершились
успешно. Отношение туннеля к raw временами превышает 100%; такой контроль
не позволяет оценить надежную долю канала или закрыть SLO 85%.

Данные: [samples](main-samples.jsonl), [summary](main-summary.json),
[ход прогона](main-run.txt).

## Перестановка портов и смешанные версии

Серверы поменялись портами. Добавлены старый клиент с новым сервером и новый
клиент со старым сервером. Пять раундов upload по 128 МиБ, каждый режим
побывал на каждой позиции порядка запусков.

| Клиент / сервер | Отдача, медиана (диапазон), МиБ/с |
| --- | ---: |
| Raw | 51,38 (33,31-52,08) |
| v2 / v2 | 42,19 (30,93-48,53) |
| current / current | 37,03 (26,44-46,77) |
| v2 / current | 39,79 (21,33-45,04) |
| current / v2 | 44,06 (26,15-47,04) |

Current/current ниже v2/v2 по отношению медиан на 12,2%. Смешанные пары

доказывают дефект нового сервера: времена запусков различаются, а интервалы

## Один тестовый сервер за раз, один серверный порт

Четыре раунда upload. В каждом: raw до, две версии в чередующемся порядке,
raw после. Каждая версия запускается на одном и том же порту; после
прогрева выполняется передача, затем временный сервер останавливается.
Вторая тестовая версия в этот момент на VPS не работает. Рабочий сервер
и прочие рабочие службы продолжают работать.

| Режим | Отдача, медиана (диапазон), МиБ/с | Измерений |
| --- | ---: | ---: |
| Raw | 31,17 (11,62-53,01) | 8 |
| v2 / v2 | 41,08 (33,41-42,22) | 4 |
| current / current | 32,14 (2,05-44,79) | 4 |

Разница медиан -21,8%. Выброс current=2,05 МиБ/с сохранен, не исключен.
Даже без него медиана трех оставшихся current равна 35,78 МиБ/с; удалять
его ради положительного вердикта нельзя. При этом в третьем раунде current
был быстрее v2: 44,79 против 33,41 МиБ/с.

В этом контроле VmSwap обоих тестовых серверов до и после каждой измеряемой
передачи был **0**. Самый медленный current-прогон занял около 62 секунд
передачи, а прирост CPU сервера между снимками составил 158 ticks при
CLK_TCK=100, то есть около 1,58s; major faults выросли на один. Это не похоже
на минуту вычислительного цикла, но не отделяет сетевое ожидание от блокировки
в приложении. TCP_INFO для этого соединения не записывался.

Данные: [samples с памятью/CPU до и после](single-samples.jsonl),
[summary](single-summary.json), [ход прогона](single-run.txt).
Все 16 измеряемых передач успешны.

## Помехи и границы

Первый запуск был прерван: временные бинарники попали в RAM-backed `/tmp`
малого VPS, рос swap. Его результаты не входят ни в одну таблицу:
[исключенная серия](discarded-samples.jsonl), [журнал](discarded-run.txt).
Далее серверные файлы размещались в `/var/tmp` на диске.

Перенос файлов не исключил всю подкачку на узле с 1 ГБ памяти. В основной
серии глобальные счетчики pswpin/pswpout выросли на 22166/10948 страниц
между контрольными снимками. В перекрестной серии у current оставались
страницы в swap, хотя число major faults за позднюю часть прогона выросло
незначительно. Поэтому контроль переделан с одним экземпляром и учетом
VmSwap самого процесса. Редкий снимок vmstat с нулями si/so не доказывает,
что подкачки не было во всей серии.

[Память до](memory-start.txt), [после](memory-end.txt),
[процессы перекрестной серии](crossover-memory-active.txt),
[последующие снимки](crossover-memory-series.txt). SSH-монитор в конце
перекрестной серии оборвал соединение; неполнота снимков не скрыта.

Это живой узел с фоновым рабочим трафиком. Raw сильно менялся, и этот шум
не устранен отбрасыванием неудобных чисел. Доступ по SSH ко второму VPS
в этой сессии получить не удалось. WSS, UDP, реальные пользовательские
наборы учетных записей и DNS этой серией не проверялись.

Для следующего сравнения сохраняются три обязательные колонки: raw,
опубликованная 2.0.0, candidate. Короткие проверки корректности и искусственные
сценарии отказа дополняют их, но не заменяют WAN-контроль. Для закрытия
WAN-UP-01 нужны объяснение просадки, воспроизведение на сопоставимом raw,
и повтор после правки; одной хорошей медианы или локального бенчмарка мало.
