# Вклад сервера в ключи: предложение следующего формата

Статус: предложение для разбора протокола. Этот формат не включен в RC2 и
не объявлен криптографически проверенным. Исправление истории replay в RC2
не меняет кадры: мусор не занимает емкость, проверка и вставка атомарны,
действующие записи не вытесняются. Заполнение емкости дает отказ свежему
соединению до освобождения записи. История остается локальной для процесса;
после рестарта или между независимыми процессами она не предотвращает повтор.
Срок хранения зависит от принятого окна эпох, включая допустимые часы клиента.

## Почему одного изменения истории недостаточно

В текущем формате ключи ответов зависят от секрета участника и клиентского
пролога. Принятие той же записи после утраты истории воспроизводит ключи
ответов. Требование уникальности пары ключ/nonce для GCM описано в
[NIST SP 800-38D, раздел 8](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf).
Предложение ниже должно исключить повторное шифрование разных ответов на
такой паре; оно также требует подтверждения нового обмена перед CONNECT.

## Предлагаемый обмен

1. Выделить отдельный вариант пролога и отдельную область вывода ключей.
   Его выбор аутентифицируется ключом участника. Сервер не пытается менять
   вариант уже начатой сессии по таймауту или по неаутентифицированному ответу.
2. Первый клиентский кадр проверяется ключом открытия, полученным из
   клиентского секрета. Этот кадр только начинает обмен. Сервер не выполняет
   CONNECT, DNS-запрос или UDP-запрос назначения до подтверждения ниже.
3. После проверки сервер получает 32 новых случайных байта из системного
   источника. Ошибка источника завершает обмен без ответа. Эти байты идут
   в заголовке первого ответа. Ключ первого ответа выводится уже с их
   участием, а заголовок и хеш пролога входят в AAD. Шифрование ответа под
   прежним ключом с прежним нулевым nonce недопустимо даже для сообщения,
   которое всего лишь несет новые случайные байты.
4. Ключи последующих кадров, масок длины, native AEAD и native тегов выводятся
   из секрета участника, клиентского секрета, серверных случайных байтов и
   хеша обмена. Для каждого назначения используется отдельная строка HKDF
   info. Правила HKDF и разделения контекстов см. в
   [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html).
5. Клиент подтверждает новый обмен кадром под новым ключом. Только после
   его проверки сервер открывает SOCKS5-обмен и регистрирует native сессию.
   Запись старого CONNECT без этого подтверждения не выполняет запрос.

Публичность случайных байтов допустима для этой конструкции только при
сохранении секрета участника и аутентификации всего контекста. Это не добавляет
forward secrecy; для него потребуется отдельное согласование с эфемерными
асимметричными ключами и разбор его цены и внешней формы обмена.

## Совместимость и критерий перехода

Текущий формат остается явно выбранным режимом совместимости. Новый клиент
не откатывается на старый по ошибке расшифровки. До выключения старого режима
оба конца должны поддерживать новый вариант; перед этим проверяются
открытия через obfs и WS, native/fallback, все выбранные AEAD, размерные
ограничения и задержка первого ответа. Старый режим продолжает иметь
ограничения истории в памяти; их нельзя скрывать рекламой нового режима.

Обязательные проверки нового формата:

- Повтор записанного открытия после рестарта и между двумя серверами не
  повторяет ни ключи ответов, ни native теги и не выполняет назначение.
- Замена случайных байтов, варианта или хеша обмена отвергается; сервер не
  отправляет данные назначения до подтверждения.
- Конкурентные открытия и отказ источника случайности не переиспользуют
  состояние шифрования; истории разных listener используют общий контекст.
- Неверный AEAD и replay сохраняют одинаковое внешнее поведение отказа.
- Старые клиенты обслуживаются только в явно разрешенном старом режиме.
- Формат, тестовые векторы и анализ nonce утверждены до внедрения.
