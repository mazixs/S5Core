Native obfs и wss выполнили пороги У-5 во всех восьми сериях: разница
потерь с прямым путем не больше 0,21 п.п. при лимите 0,3; разница p99 не
больше 0,18 мс при лимите 1; замирания не превышают прямой путь больше чем
на 10%. У `0x83` потери скрыты повторной передачей TCP, но задержка на
потерях выросла, а замираний стало больше.

Отчет пайплайна пометил 64 проблемы при 56 статусах `ok`: 48 предупреждений
о запуске тестового сервера без аутентификации и 16 сообщений `idle tcp echo:
EOF` у plain SOCKS5, где нет `s5client` с keepalive. Эти plain-ячейки
используют стандартный UDP ASSOCIATE `0x03` в обоих вариантах и служат
контролем, а не проверкой native UDP. У obfs и wss ошибок игрового сценария
нет.

Полный прогон собран до добавления счетчиков UDP и сценария принудительного
отказа UDP в тот же день. Эти добавления не меняют формат или выбор пути, но
после них проведены отдельные короткие сценарии отказа UDP на 64 и 128 Гц.
Финальный часовой WAN-прогон проводится отдельно.

## Принудительный отказ UDP

Две дополнительные минутные ячейки после добавления счетчиков и фильтра
`tc` ([JSON](nativeudp-blackout-2026-09-25.json), локальный netns, RTT 50 мс):

- UDP заблокирован с начала на 55 с: 0% потерь, 0 замираний, 0 обрывов.
  Клиент проверил native UDP только после снятия блока; весь основной поток
  до этого шел по `0x83`.
- UDP исчез на десятой секунде на 12 с: клиент зафиксировал тайм-аут native
  UDP и перешел на `0x83` в той же ассоциации. Один перерыв между ответами
  1,063 с, 1,74% потерянных тиков, 0 обрывов. После восстановления пути
  клиент снова проверил native UDP. Порог замирания 1,5 с выполнен.

Три предупреждения в отчете: два ожидаемых запуска стендового сервера без
аутентификации и одно сообщение клиента о переходе на `0x83`.

Повтор на итоговой сборке после изменений окна и проб (тот же [JSON](nativeudp-blackout-2026-09-25.json)):
обе ячейки `ok`, 0 обрывов. При блоке с начала потерь и замираний нет;
при блоке посреди сессии одно замирание 1,062 с и восстановление native UDP
после снятия фильтра. Три сообщения отчета имеют тот же ожидаемый состав.

## Короткий WAN-контроль на ARM-маршрутизаторе

Две двухминутные ячейки на отдельном стендовом VPS и ARM64-маршрутизаторе
([JSON](nativeudp-wan-smoke-2026-09-25.json)), с прямым потоком в те же минуты:

| Путь | Потери | p99 | Замирания | Прямой контроль: потери / p99 / замирания |
|---|---:|---:|---:|---:|
| 2.2.0, `0x83` | 0% | 55,67 мс | 0 | 0,22% / 53,35 мс / 0 |
| 2.3 кандидат, native UDP | 0% | 56,36 мс | 0 | 0,31% / 55,75 мс / 1 |

Обе ячейки имеют статус `ok`, 0 обрывов и 0 ошибок тихого TCP-канала.
Во время ячейки кандидата серверный счетчик подтвердил не менее 5791
принятой native UDP датаграммы. Двух минут недостаточно для приемки потерь:
расхождение 0,31 п.п. с прямым путем на этой короткой выборке чуть больше
порога 0,3 п.п. Для решения нужен часовой прогон на том же пути.

## MIPS-совместимость

Клиент под `mipsle` и `mips` с `GOMIPS=softfloat` проверен под QEMU против
сервера amd64 с включенным native UDP
([JSON](nativeudp-mips-2026-09-25.json)). Каждая пара передала 128 игровых
тиков при 64 Гц без ошибок. В логах обоих клиентов подтверждены проверка
UDP-пути и отправка игровых датаграмм через него. Это проверка совместимости
формата между архитектурами; скорость и нагрузка на реальном MIPS не
измерялись.

## Отказ UDP при 128 Гц

Отдельная двухминутная сессия, 200 байт в каждом направлении, RTT 50 мс,
UDP заблокирован с 10-й по 22-ю секунду; TCP оставался доступным
([три прогона](nativeudp-highrate-blackout-2026-09-25.json)). Начальное окно
на 128 тегов оставляло игру на `0x83` без обрыва, но native UDP не
восстановился за оставшуюся минуту. Окно 512 вернуло native UDP через 25,2 с
после разблокирования; немедленная повторная проба при переходе на `0x83`
сократила ожидание до 4,1 с. На финальном локальном прогоне 0 обрывов,
1 замирание длиной 1,055 с, p99 50,39 мс, тихий TCP-канал не падал.
Это проверка 128 Гц на локальном стенде, а не на WAN или в реальной игре.

## Час на WAN и ARM64

Первый часовой прогон на изолированном серверном стенде и ARM64-маршрутизаторе
([JSON](nativeudp-wan-hour-2026-09-25.json)) был собран до увеличения окна и
ускорения повторных проб. При 64 Гц: 230 391 тик, 0 обрывов, 89 успешных
проверок тихого TCP-канала, native UDP принял 230 630 пакетов без отказов
аутентификации. Потери 0,004% против 0,059% у прямого контроля; замираний
8 против 8. p99 56,405 мс против 54,052 мс, то есть +2,353 мс при пороге
+1 мс. В каждой из 60 минут медиана native-пути была выше прямого контроля
на 1,488-1,838 мс. Час подтверждает стабильность, но **не выполняет полевой
порог задержки У-5**. Повтор на итоговой сборке проводится отдельно.

Отдельный [бенчмарк кодека на том же ARM64](nativeudp-arm-codec-2026-09-25.json)
дал 28,6 мкс на шифрование и прием 200-байтной датаграммы, 0 аллокаций.
Это стоимость кодека без сети и без полного пути приложения; она не
объясняет сама по себе добавку p99 в 2,353 мс.

Локальная проверка [памяти таблицы сессий](nativeudp-session-memory-2026-09-25.json)
дала около 44 КБ кучи на ассоциацию при 1000 зарегистрированных сессиях и
окне 512. Это оценка процесса amd64 после сборки мусора, а не замер емкости
боевого узла; перед большим числом одновременных игроков нужен отдельный
нагрузочный тест. После ограничения очистки тегами закрываемой ассоциации
удаление 1000 сессий заняло 39,4 мс на локальном стенде.
