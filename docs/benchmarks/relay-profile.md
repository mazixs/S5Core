# Профиль релея: откуда берутся аллокации

Документ фиксирует результат задачи Ф2-6 плана.

## Проверяемая гипотеза

План формулировал ее так: буфер чтения обфускации равен удвоенному MTU
(2800 байт), а отправитель подает блоки до 32 КиБ, поэтому каждый крупный кадр
уходит в ветку с выделением памяти плюс копия хвоста. Если это так, заявленная
zero-allocation архитектура ломается на сочетании размеров, а не на алгоритме,
и лечится согласованием размеров, без изменения формата кадра.

## Как воспроизвести

```bash
PROFILE_CONNS=8 PROFILE_MB=1024 \
  go test -tags loadtest -run TestObfsRelayProfile -v -timeout 10m ./pkg/s5server/

go tool pprof -top -sample_index=alloc_space bench/profiles/obfs-relay.alloc
go tool pprof -list='Read$' -sample_index=alloc_space bench/profiles/obfs-relay.alloc
go tool pprof -top bench/profiles/obfs-relay.cpu
```

Прогон: 8 соединений, по 1 ГиБ скачивания через obfs-порт, всего 8 ГиБ,
2,29 с, 3571 МиБ/с внутри процесса (loopback, i7-11700K).

## Результат: гипотеза подтверждена с точностью до строки

```
Type: alloc_space
Showing nodes accounting for 16377.21MB, 99.93% of 16387.90MB total
      flat  flat%   sum%        cum   cum%
16376.18MB 99.93% 99.93% 16376.68MB 99.93%  pkg/obfs.(*conn).Read
```

На 8 ГиБ переданных данных приходится 16 ГБ выделенной памяти - два байта
аллокации на каждый байт полезной нагрузки. Построчно:

| Строка | Код | Выделено |
|---|---|---|
| `pkg/obfs/conn.go:235` | `frame = make([]byte, frameSize)` | 9,94 ГБ |
| `pkg/obfs/conn.go:277` | `c.readRest = append(c.readRest[:0], payload[copied:]...)` | 6,06 ГБ |

Все остальное вместе - меньше 0,1%.

### Строка 235: кадр не помещается в преаллоцированный буфер

`readBuf` создается размером `MTU * 2` (2800 байт при MTU 1400, но не меньше
4096). Релей копирует через буфер 32 КиБ (`bufferPool` в `pkg/s5server`,
`proxy` в `internal/socks5`), поэтому `obfs.Write` формирует кадры до 32 КиБ.
На приемной стороне `frameSize` всегда больше `cap(readBuf)`, и ветка,
помеченная в коде комментарием `allocate (rare)`, выполняется на **каждом**
кадре.

### Строка 277: хвост, который теряет capacity

Вторая половина - следствие того же расхождения размеров, но с отдельным
механизмом. `readRest` задуман как переиспользуемый буфер: `append(c.readRest[:0], ...)`
должен писать в уже выделенную память. Но дренаж хвоста в начале `Read`
выполняется как `c.readRest = c.readRest[n:]`, и это сдвигает начало слайса,
уменьшая `cap` на ту же величину. К моменту, когда хвост прочитан целиком,
capacity равна нулю, и следующий `append` снова выделяет память. Буфер,
написанный как переиспользуемый, не переиспользуется никогда.

Чтобы хвост вообще появлялся, читатель должен брать меньше, чем размер кадра.
В замере это `io.Copy(io.Discard, ...)`, который через `io.discard.ReadFrom`
читает блоками по 8 КиБ при кадрах 32 КиБ. В боевом релее сервера буфер чтения
равен 32 КиБ и совпадает с размером кадра, поэтому там работает только строка
235 - но стоит клиентскому приложению читать меньшими порциями, и включается
вторая.

## Профиль CPU

```
Duration: 2.29s, Total samples = 22.31s (972.46%)
    10.62s 47.60%  internal/runtime/syscall/linux.Syscall6
     2.29s 10.26%  crypto/.../gcm.gcmAesEnc
     2.22s  9.95%  crypto/.../gcm.gcmAesDec
     1.77s  7.93%  runtime.memmove
     0.50s  2.24%  runtime.memclrNoHeapPointers
```

Половина времени - системные вызовы (замер на loopback, где сеть бесплатна, а
syscall остается), шифрование - пятая часть, сборка мусора в сумме около 3-4%.
Вывод для приоритетов: на канале 100 Мбит/с узкое место не в шифровании.
Аллокации важны не как расход CPU, а как расход памяти и давление на GC на
слабом VPS.

## Что из этого следует

1. Источник назван: `pkg/obfs.(*conn).Read`, строки 235 и 277. Это **не**
   шейпер WebSocket, поэтому приоритет задачи Ф4-7 не повышается.
2. Задача **Ф4-2** (сегментация записи по MTU и согласование буферов) получает
   точную формулировку вместо общей: согласовать размер кадра с буфером релея
   так, чтобы ветка на строке 235 перестала выполняться, и переписать хранение
   хвоста на буфер с индексом вместо сдвига слайса, чтобы строка 277 перестала
   выделять память.
3. Регрессия закрыта тестом заранее: `pkg/obfs/alloc_test.go`
   (`TestOversizedPayloadAllocates`) уже фиксирует, что payload больше `readBuf`
   дает аллокацию. После Ф4-2 этот тест сменил знак и стал проверкой того, что
   аллокаций нет - `TestARelaySizedWriteIsAllocationFree`, рядом с ним
   `TestSmallReadsDoNotAllocate` для второй строки.

## Повторный замер после Ф4-2

Правка сделала три вещи: запись режется на кадры по `OBFS_MTU` (равными
частями, а не "полные кадры плюс короткий хвост"), обе стороны буферизуют
кадры пачками (запись 16 кадров или 32 КиБ, чтение 8 кадров или 16 КиБ), а
хвост непрочитанного payload хранится как буфер с индексом вместо сдвига
слайса.

обратный.
